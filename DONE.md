## File transfer: exec-based, not `docker cp` (important finding)

The spec's Stage-1 design used `docker cp`; the real e2e test caught that
Docker ≥ 29 (verified 2026-08-07 on Docker 29.2.1) refuses `docker cp` on
`--read-only` containers in **both** directions — writes fail with
"container rootfs is marked read-only" and reads cannot see tmpfs contents
("Could not find the file"), even with registered `--mount type=tmpfs`.
So files travel as bytes over `docker exec` instead: `put_file` =
`mkdir -p` + `docker exec -i tee <path>` (pure argv, no shell
interpolation, binary-safe, files land owned by `nobody` so agent code
can read/write its inputs), `get_file` = `docker exec cat <path>` raw
stdout (missing file → `FileNotFoundError`, oversized artifact → loud
raise, never silent truncation). Workspace images must ship
`mkdir`/`tee`/`cat` (busybox and coreutils both do). No host mounts,
period.
