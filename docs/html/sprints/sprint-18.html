1. Sprint thesis #

Sprint 18 closes the legal-substrate exposure that Sprint 11–16 deliberately left open. The master-product-spec at §9 commits to retrieval-time gating before Sprint 18 ships; absent the gate, the Bartz v. Anthropic, Hachette v. Anthropic, and AG MDL banned-corpus list cannot be enforced at the substrate level — only at the policy level — and policy-level enforcement is not a defensible posture for shipping the publisher dashboard.

The sprint has three primary deliverables:

  1. The retrieval-time legal gate. SQL-WHERE-level enforcement of the banned-corpus list. Every query path that reads from substrate.documents or substrate.chunks passes through it. Every write path that inserts to those tables passes through it.
  2. The publisher dashboard architecture. Stripe Connect, escrow accruing per Kalshi-pattern, KYC pipeline. Payouts gate strictly on publisher opt-in.
  3. The Brainstorming Workstation full ship. Thought-partner role, Lego-block insight slotting, PostHog notebook-pattern polish.

Plus the substrate-only precursor for the Exa / Browserbase Wedges 1 and 2: typed event payloads land ahead of the wedge work so the wedge PRs are typed from day one.

2. Mainline — retrieval-time legal gate #

Reference: master-product-spec.md §9. The single most important substrate change of the sprint.

2.1 What it is

A SQL-WHERE-level gate enforced at every read and write path against substrate.documents, substrate.chunks, substrate.nodes, and substrate.edges. The gate consults a substrate.legal_gate.banned_corpora table whose rows enumerate banned source-corpus identifiers, banned domains, banned author-publisher pairs, and banned content-hash prefixes (for the AG MDL case where specific content fingerprints are restricted regardless of domain).

The gate is structurally inside substrate/legal_gate/ with three sub-modules:

  • substrate/legal_gate/registry.py — the banned-corpora registry. Operator-edited; not auto-learned.
  • substrate/legal_gate/predicate.py — the SQL-WHERE predicate generator. Returns a parameterized WHERE clause that callers append to their queries.
  • substrate/legal_gate/gate.py — the runtime gate that wraps connect_write from runtime/db_lock.py and rejects writes that would violate the registry.

2.2 Why the gate sits at SQL-WHERE level

Two reasons, both load-bearing:

  1. Defense in depth. An application-layer gate (Python-side check before SQL) can be bypassed by anyone who finds a code path that talks to DuckDB directly. A SQL-WHERE-level gate is enforced by the database engine; no application-layer code path can bypass it.
  2. Read-path coverage. The Sprint 18 gate must reject not just writes of banned content but reads — specifically, retrieval-time queries that would return banned chunks even if those chunks were ingested before the ban list expanded. SQL-WHERE is the only mechanism that applies uniformly to existing rows.

2.3 The connection to Exa & Browserbase Wedge 1

Binding

The Exa & Browserbase spec at §6.9 commits: "Wedge 1 cannot ship before the Sprint 18 retrieval-time legal gate is in production." When Wedge 1 lands in Sprint 19, every URL it discovers passes through the gate before ingest_url writes to the graph. A discovered URL on the banned-corpus list produces DiscoverySelectedPayload{decision="rejected_by_legal_gate"} — the discovery is audited, but no graph write happens.

2.4 Operator-edited registry, not auto-learned

The banned-corpora registry is operator-edited via direct commits to substrate/legal_gate/registry.py. No "learn from negative outcomes" pattern. Reasons:

  • The registry has legal weight: each entry encodes a specific legal posture (Bartz settlement, Hachette pretrial order, AG MDL case-management order). Auto-learning would dilute that.
  • The cost of a false positive (rejecting legal content) is asymmetric with the cost of a false negative (allowing banned content into the substrate). The asymmetry favors human review on every entry.
  • The registry is small — tens of entries, not thousands. Hand-curation is feasible.

2.5 Acceptance criteria

  • Every query against substrate.documents or substrate.chunks passes through the gate predicate.
  • Every write to substrate.documents, substrate.chunks, substrate.nodes, substrate.edges via runtime/db_lock.connect_write consults the gate.
  • Integration test: a fixture URL on the banned list cannot be ingested via ingest_url(...) — the call returns IngestUrlResult{skipped_reason="rejected_by_legal_gate"}.
  • Integration test: a pre-existing chunk whose source is added to the ban list disappears from retrieval results within the same DB connection.
  • Operator can edit registry.py, run python -m substrate.legal_gate.audit, and see a list of (a) what would be newly blocked, (b) what would be newly unblocked, (c) any inconsistencies.

3. Publisher dashboard + Stripe Connect (architecture) #

Reference: master-product-spec.md §9 Phase 2, §14.1 row "Sprint 18". The IP-payout architecture ships in Sprint 18 alongside the publisher dashboard; payouts gate strictly on publisher opt-in.

3.1 What ships this sprint

  • publisher.antiek.ai — the publisher-facing surface (separate domain from the operator-facing app).
  • Stripe Connect onboarding flow — KYC, bank-account linkage, tax-form collection.
  • Escrow accrual per the Kalshi pattern — revenue accrues per attributed publisher but does not pay out until the publisher opts in.
  • Notification template — the first-cohort outreach goes out Sprint 19; this sprint ships the template + the send mechanism.
  • One manual sponsor slot in the MASTER.md viewer footer (per master-spec §14.1 row 2: "Sponsor pays flat monthly fee. Revenue routed manually to top-3 attributed publishers as proof-of-concept.").

3.2 What does NOT ship this sprint

  • Synquery integration. Per master-spec §14.3, Synquery slips to Sprint 21 — "only after creation surface PMF signal that warrants paying for expert calls."
  • Automated payouts. Manual routing for the proof-of-concept sponsor slot. Automated payouts ship Sprint 20–22.
  • Phase 4 lead-gen ad inventory. Sprint 21–22.

3.3 The connection to the Exa / Browserbase spec

The publisher dashboard work does not directly intersect Wedge 1 or Wedge 2. But the two ship in the same sprint, which creates capacity pressure. The legal gate is the absolute priority; the publisher dashboard is the second priority; the brainstorming-workstation full ship is the third. The Exa / Browserbase substrate-only precursor (§5 below) is the easiest item to slip if other work pressures.

5. Thought-partner role #

New role at roles/thought_partner/. Sprint 17 deferred this from the Brainstorming Workstation scaffold; Sprint 18 implements it.

5.1 What it is

A role specifically designed to refine an unsharpened question through dialogue. Operator types a vague question; the thought-partner asks clarifying questions, surfaces related prior investigations from the graph, proposes alternate phrasings. The output is a sharpened question ready to dispatch to Loop 1.

5.2 Why this is a new role and not a tool

The thought-partner needs its own dispatch tier configuration (likely a small fast model — DeepSeek V4 Flash or similar), its own program.md (per Sprint 17's INTEGRATE NOW), and its own typed event vocabulary (QuestionSharpened events). All three of those are role-level concerns, not tool-level. Plus the role-as-source-of-truth invariant: every role is in the trajectory; tools may not be.

6. Substrate-only precursor for Wedges 1 + 2 #

Reference: Exa & Browserbase spec §18.3. ~1 day; the easiest item to slip if other work pressures.

6.1 What it is

Three typed event payloads added to substrate/schemas/events.py:

  • DiscoveryProposedPayload — the Wedge 1 event for "we considered this URL."
  • DiscoverySelectedPayload — the Wedge 1 event for "we promoted this discovery to ingestion (or didn't)."
  • FetchFallbackEscalatedPayload — the Wedge 2 event for "httpx returned low_word_count, we escalated to Browserbase."

Plus three ActionType enum entries:

DISCOVERY_PROPOSED       = "discovery.proposed"
DISCOVERY_SELECTED       = "discovery.selected"
FETCH_FALLBACK_ESCALATED = "fetch.fallback.escalated"

Plus the TS codegen pass (tools/codegen/emit_types.py) so the frontend has the types from day one.

6.2 Why this lands in Sprint 18, not Sprint 19

Three reasons:

  1. Wedge 1 and Wedge 2 PRs are easier to review if the types are already in. Mixing event-schema additions with the adapter / fetcher code in one PR makes the diff harder to read.
  2. The TS codegen is a substrate-test that catches schema breakage. Landing it ahead of the wedge work means any subsequent breakage attributes cleanly to the wedge PR.
  3. The substrate-only PR is the "warm-up." Operator can review the event-schema additions independent of the larger wedge work, building familiarity with the discovery-event vocabulary before the adapter lands.

6.3 What it does NOT do

  • Does NOT add the Exa client.
  • Does NOT add the Browserbase client.
  • Does NOT change acquisition/urls/adapter.ingest_url's signature.
  • Does NOT emit any of the new events — the types exist, no caller writes them yet.

Strict additions, no behavior change.

7. Order of operations #

  1. Retrieval-time legal gate (first half of sprint, ~5 days). Cannot slip. Every other Sprint 18 deliverable, plus all of Sprint 19's Exa work, depends on this.
  2. Publisher dashboard architecture (parallel to legal gate, ~4 days). Sub-track on the dashboard front-end while substrate work proceeds.
  3. Brainstorming Workstation full ship (mid-sprint, ~3 days). Builds on the Sprint 17 scaffold.
  4. Thought-partner role (~1.5 days). Coupled to the brainstorming workstation full ship.
  5. Substrate-only precursor for Wedges 1 + 2 (~1 day). Land any time the legal gate is in progress — the two are independent.

If the legal gate runs long, the brainstorming workstation full ship slips to Sprint 19. The legal gate cannot slip; Wedge 1 ships in Sprint 19 depends on it.

9. Open questions for this sprint #

9.1 Which banned-corpus seed list ships in registry.py?

The Bartz settlement names specific authors; the Hachette pretrial order names specific titles; the AG MDL case-management order names specific content. The seed list must be hand-curated. Operator + lawyer-review pass required before the registry is operator-edited live.

9.2 Stripe Connect onboarding — how aggressive is the KYC?

The minimum Stripe-required KYC vs the Antiek-preferred KYC (more thorough; reduces sponsor-friction). Operator decides based on the first-cohort outreach plan for Sprint 19.

9.3 First sponsor: manual onboarding via direct sales or self-serve?

Master-spec §14.1 row 2 says "manual sponsor onboarding via direct sales" for the proof-of-concept. Sprint 18 ships the manual flow; whether Sprint 19+ moves to self-serve depends on the sponsor's experience.

9.4 Does the substrate-only precursor slip if the legal gate runs long?

It can slip to Sprint 19 with no consequence to Wedge 1 timing. The wedge PR can include the type additions if the precursor slips. Recommendation: hold a half-day reserve for the precursor; slip only if the legal gate eats > 6 days.

10. Acceptance & exit criteria #

Sprint 18 is done when:

  1. The retrieval-time legal gate is in production. Every read and write path against substrate tables passes through it. Integration tests cover the banned-corpus rejection path end-to-end.
  2. The publisher dashboard architecture is shipped: publisher.antiek.ai serves a Stripe Connect onboarding flow; escrow accrual is live; one manual sponsor slot is live in the MASTER.md viewer footer.
  3. The Brainstorming Workstation is feature-complete: thought-partner role wired, Lego-block insight slotting works, voice-note-to-question chaining works.
  4. The substrate-only precursor for Wedges 1 + 2 lands: three typed payloads, three ActionType entries, TS codegen pass clean. (May slip to Sprint 19 if the legal gate runs long.)
  5. Full test suite still green; no regression.

The operator-validation criterion: the operator can edit registry.py to add a new banned-corpus entry, restart the substrate, run a manual ingest_url(banned_url, ...) call from a Python REPL, and see the call return IngestUrlResult{skipped_reason="rejected_by_legal_gate"} with the typed event in the JSONL log.

Why this sprint is the spec's pivot

Every wedge in the Exa & Browserbase spec — integrate or reject — assumes the Sprint 18 legal gate exists. Wedge 1 depends on it for the discovery-then-gate-then-ingest flow. Wedge 6 (full agentic browsing) cites it as one of the reasons full agentic browsing is unobservable today. The nine REJECTs include "§12.6: bypass the Sprint 18 retrieval-time legal gate" as the highest-priority rejection.

If Sprint 18 ships the gate, the spec's INTEGRATE NOW pair (Wedges 1 + 2) can ship in Sprint 19. If Sprint 18 does not ship the gate — if the work slips a sprint — the Exa & Browserbase wedges slip one sprint too. There is no path to Wedge 1 that skips the gate. The spec is structured this way deliberately; do not look for shortcuts.
