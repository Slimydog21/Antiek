PROPOSED · OPERATOR-DESIRED HEADLINE

1 · Goal

Build the literate-analysis notebook surface specified in integration_posthog.md §6, but as a first-class panel instead of a route. TipTap-based block editor; block types are prose + region-embed + claim-card + note + question + cross-doc-link + chat-exchange + MASTER.md-fragment + image + LaTeX; backed by a new notebooks table. Substrate-references are stored as IDs (not denormalised) per the prior spec's architectural rule.

2 · Why this sprint exists

Operator-stated highest-leverage product upgrade (master-product-spec §4.2; integration_posthog.md §6.3). The prior spec sequenced this as Wedge 2; this sprint executes it. Doing it after the panel system exists is what unlocks the notebook living alongside the PDF + trajectory rather than replacing them.

3 · Non-goals

  • No multi-author / multiplayer. Single-operator only; conflict detection in S22+.
  • No external sharing / publishing.
  • No PDF region snipping tool itself — that already exists in PdfViewer's selection layer. S7 only consumes it.
  • No LaTeX engine ship (KaTeX import is in S7 but rendering correctness for arbitrary math is out of scope; basic equations only).

4 · Architecture

4.1 · Storage

New DuckDB table notebooks: 

CREATE TABLE notebooks (
  id              TEXT PRIMARY KEY,        -- ulid
  title           TEXT NOT NULL,
  investigation_id TEXT,                   -- nullable: notebook can be standalone
  document_id     TEXT,                    -- nullable: ditto
  content_json    JSON NOT NULL,           -- TipTap document JSON
  schema_version  INTEGER NOT NULL DEFAULT 1,
  created_at      TIMESTAMP NOT NULL,
  updated_at      TIMESTAMP NOT NULL,
  archived        BOOLEAN NOT NULL DEFAULT FALSE
);

CREATE INDEX idx_notebooks_inv ON notebooks(investigation_id);
CREATE INDEX idx_notebooks_doc ON notebooks(document_id);

Substrate-references inside content_json blocks are stored as { kind: "claim-card", claim_id: "..." } not denormalised claim payloads — substrate stays the source of truth (architecture_notes §13).

WP-7.3

Block extensions

Files: src/modes/Notebook/blocks/{ClaimCardBlock, RegionEmbedBlock, NoteBlock, …}.tsx Effort: 2.0 d

One TipTap NodeView per Antiek block kind. Each NodeView:

  • Renders the block from the stored substrate-ref (fetches via hook).
  • Provides a contextual "open as panel" button.
  • Provides a "remove" affordance.
// src/modes/Notebook/blocks/ClaimCardBlock.tsx
import { Node, mergeAttributes } from "@tiptap/core";
import { ReactNodeViewRenderer, NodeViewWrapper } from "@tiptap/react";

export const ClaimCardBlock = Node.create({
  name: "claimCard",
  group: "block",
  atom: true,
  addAttributes: () => ({ claim_id: { default: null } }),
  parseHTML: () => [{ tag: "antiek-claim-card" }],
  renderHTML: ({ HTMLAttributes }) => ["antiek-claim-card", mergeAttributes(HTMLAttributes)],
  addNodeView: () => ReactNodeViewRenderer(ClaimCardNodeView),
});

function ClaimCardNodeView({ node }: any) {
  const claim = useClaim(node.attrs.claim_id);
  return (
    <NodeViewWrapper>
      <LemonCard elevation="z1" title={`Claim · ${node.attrs.claim_id.slice(0,8)}`}>
        {claim ? <ClaimCard claim={claim} /> : <Skeleton />}
      </LemonCard>
    </NodeViewWrapper>
  );
}

6 · Acceptance criteria

  • The notebooks table exists; REST CRUD works.
  • A new notebook opens as a floating panel; typing prose persists across reloads.
  • Slash menu inserts every block kind; each renders correctly.
  • Region-embed block, when clicked, opens a floating PDF panel at the right page (uses S6 plumbing).
  • Claim-card block, when clicked, opens ClaimInspector floating panel.
  • "Add to notebook" works from MasterMdViewer + PdfViewer selections + ClaimCard contexts.
  • Substrate-ref freshness: editing a referenced claim in another panel updates the rendered claim block on the next read (no denormalised data anywhere).
  • Single-author conflict detection trips (test by opening the same notebook in two browser tabs, editing both, saving).
  • Notebook editor lazy-loads: visiting any other route does not pull TipTap into the main chunk.
  • Lost-Pixel: notebook stories committed.

7 · Risks & mitigations

  • TipTap node-view re-renders are heavy for long notebooks (50+ blocks). Mitigation: every NodeView is memo'd on attrs; substrate-ref fetches use React Query (already in tree) with stable keys.
  • Region-embed thumbnail generation is slow. Mitigation: thumbnails are rendered once into the artifact store and cached by hash; absent → falls back to "click to load".
  • Substrate-ref to deleted entity (claim removed after embed). Mitigation: NodeView shows a "removed (was a claim from {timestamp})" tombstone — never blank.
  • KaTeX bundle bloat. Mitigation: lazy-load on first /latex block insertion.
  • Save loop infinite recursion. Mitigation: autosave compares the serialised JSON to last-saved; no diff = no PATCH.

8 · Open questions

  1. Should every investigation auto-create a notebook? Default: no — operator creates one explicitly. (Auto-create reopens in a S22+ "templates" pass.)
  2. Notebook search: full-text across content_json? Default: out of scope for S7; tracked as a S10 stretch.
  3. Export formats: only Markdown for v1, or also PDF / HTML? Default: Markdown only in S7.

9 · Verification protocol

  1. Create a new notebook from NotebooksIndex; verify it opens in a floating panel.
  2. Insert every block type via slash menu; verify each renders sensibly.
  3. Insert a region-embed → click → floating PDF panel opens at the right page.
  4. Insert a claim-card; modify the claim elsewhere in another panel; reload the claim-card block; verify the update flows through (substrate-ref freshness).
  5. Open same notebook in two browser tabs; edit both; second save → toast conflict.
  6. Hard-reload during edit; autosave recovers within 2 seconds of typing pause.

10 · Rollback plan

Notebook is additive. REST endpoints can stay (no consumers without the UI). Table can stay empty. Rolling back the UI means hiding the route + block menu. The DuckDB migration adds a table only; no migrations modify existing tables, so rollback is safe.
