1 · What we're building

A wholesale visual + interaction rebuild of apps/reading/ in the style of PostHog's frontend/src/layout/panel-layout/ system: a workspace shell where the operator opens, stacks, drags, resizes, pins, and pops out independent panels — each panel being one of the existing Antiek modes or one of its sub-surfaces (investigation list, trajectory viewer, notebook, AI sidecar, chase flow, claim inspector, etc.).

Panels live in a 2.5D layout: docked left or right, free-floating with z-index depth + offset shadow, or popped out into an OS-level window. Visual language: sharp sun-yellow outlining on every surface, chunky offset shadows (ink in day / glowing sun-deep in night), layered off-white + glacial paper in day, layered off-black + dark-grey night sky after dark, JetBrains Mono for system text, Inter for UI, Charter for reading prose, sun-yellow as the in-product highlighter. The aesthetic of this document is the aesthetic of the target build.

2 · Why this redesign, in one paragraph

The current Antiek shell is a 280px-sidebar + main-pane + bottom-input layout (apps/reading/src/modes/ResearchWorkstation/index.tsx). It is functional but flat: there is exactly one place to look, one place to type, and modes are routes, not surfaces you can have open at the same time. A real research workstation needs side-by-side: the trajectory, the source PDF, the notebook, and the chat — concurrent, not modal. The PostHog panel system is the closest open-source precedent for this in production, and is MIT-licensed.

4 · What this spec reverses

Prior verdict (§5.3)This spec
"Antiek's serif / researcher's-notebook aesthetic is load-bearing for the product proposition." REVERSED. The reading body of synthesis output stays serif (Charter for prose); the shell goes layered-panel + Antarctic (Inter UI, JetBrains Mono for system, chunky offset shadows, sun-yellow outline on every surface, ten-layer night sky after dark). The notebook feel survives inside the panel that renders prose, not at the chrome level. The brand yellow doubles as the reading highlighter, so the mark "follows" the operator from the chrome into the text.
"If Lemon UI fails the visual-fit criterion, the evaluation is the defensible answer — adopting it anyway would hurt the product." BYPASSED. We don't adopt the @posthog/lemon-ui npm package; we build a parallel set of components in src/components/lemon/ that match the visual language but live in our Tailwind + strict-TS world. See S0 §3.

7 · Out of scope (explicit)

  • Substrate (Python, DuckDB, orchestration). This is frontend-only.
  • Mobile-native apps. We ship a responsive web fallback in S11, not a separate mobile app.
  • Multi-tenant / multi-user. Antiek is single-operator pre-launch (per master spec).
  • Auth / login flows. The shell is layout, not identity.
  • Replacing pdf.js or react-markdown. Engines stay; only chrome changes.
  • Replacing react-router-dom with PostHog's Kea-routed scenes. Router stays; the shell renders inside it.

8 · Operator-visible exit criteria for the whole programme

  • Cmd+B toggles the left rail in every route.
  • A panel can be docked left, docked right, made floating, or popped into a new OS-level window.
  • The trajectory of an active investigation, the source PDF being wrestled, and the notebook being authored can all be visible at once on a 24"+ display.
  • Closing and reopening the browser restores the last panel layout per-investigation.
  • No regression in Lighthouse a11y or in the 1540-test substrate suite (frontend-only change ⇒ substrate suite untouched, but frontend unit + Storybook tests pass).
  • Production bundle (main + lemon + panel system, excluding pdf.worker) ≤ 700 KB gzipped.
  • The operator can answer: "is this UI cool now?" — yes.

9 · Risk register (programme-level)

  • Aesthetic miss. The PostHog look depends on shadow + spacing + palette balance. Rendering it "almost right" looks worse than the current flat UI. Mitigation: S0 ships a moodboard + S1 ships the primitives in Storybook first, gated on operator sign-off before any mode ports.
  • pdf.js performance inside a floating panel. PDF rendering on a continually z-shifting + animated container can drop frames. Mitigation: S6 has an explicit perf budget (≥45 fps scroll inside a 1200×900 floating PDF panel on M1).
  • Substrate-spec drift. While we work on this, substrate sprints continue. A new route landed on the old shell during S5–S10 means an extra migration step. Mitigation: S0 lands a thin PanelHost wrapper that the substrate-track devs can opt into for any new route, so new routes ship on the new shell from day one.
  • Storybook + Vite + strict TS pile-up. Already in devDependencies at storybook ^8.4.7; not all primitives + lemon components will compile clean on first try. Mitigation: S1 + S2 explicitly include TS-strict pass.
  • Bundle bloat. Framer Motion + Zustand + react-resizable-panels add weight. Mitigation: S12 enforces a hard 700 KB gzipped budget on the main chunk; S0 picks lighter alternatives where the budget pressures.
  • Multi-monitor popout fragility. window.open popups need React portal + shared store hookup; some browsers throttle. Mitigation: S9 ships popout behind a feature flag with a graceful fallback to floating-in-tab.
  • Cutover regression. Switching the operator's daily-driver UI overnight is dangerous. Mitigation: S12 ships behind ANTIEK_UI=v2 env flag; old shell stays runnable for one sprint after cutover.
