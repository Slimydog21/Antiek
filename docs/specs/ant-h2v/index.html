Hard-to-Vary Execution — Cascade Auto-Decompose

Close the Research POST /research/plans auto-decompose path with mechanically verifiable gates and a reusable agent execution protocol.

Status: Ready to execute Owner: Operator + Grok executor 8 sprints · 4 waves Generated 2026-06-02

Goal

What success looks like and how we measure it.

Restore Research cascade auto-decomposition (operator submits a problem without manual sub-questions) with bounded, falsifiable claims. Every sprint produces artifacts an adversarial re-read cannot dismiss as theater.

Success criteria

  • Hermetic tests cover DispatchDecomposer and the HTTP branch that omits sub_questions (merge-bar: tests for non-test changes).
  • Repo contains docs/agent-execution/HARD_TO_VARY.md — Phase A–E protocol forbidding repeated pytest | tail, wrong Python/cwd, memory-without-test, and unbounded “platform OK”.
  • Closure dossier (SPR-08) lists each decompose entry point with tested / untested / live-LLM-required — no superlative without a row.
  • Operator can verify live decompose once via SPR-07 card without reading chat history.

Failure mode to avoid

The egghead-session pattern: correct root cause + 50× truncated pytest from wrong cwd/Python + “engine fine across platform” without scope map. That is easy-to-vary verification — remove the repetition and the conclusion unchanged.

Context & motivation

Why this, why now.

DispatchDecomposer.decompose called render_full_prompt(question) (positional) and dispatch(...) without investigation_id. Both raise TypeError before any provider request — UI shows “no result” (HTTP 500).

Fix is present in roles/cascade_planner/planner.py but production path had zero tests; cascade API tests always pass manual sub_questions. This spec closes the gap and encodes execution discipline for all future Antiek agent work.

Architecture overview

Load-bearing paths only.

Reading UI → POST /research/plans ├─ sub_questions[] → _Fixed decomposer → build_plan (no LLM) └─ (omit sub_questions) → _decompose() → DispatchDecomposer.decompose → render_full_prompt(*, investigation_id, question, context) → dispatch(..., investigation_id=...) → parse_decomposer_response → build_plan → persist_tree Parallel (out of sprint scope): Loop1 POST /investigations → DECOMPOSE_QUESTION_REQUESTED → make_decomposer_handler (already keyword-correct)

Key invariants

  • Pre-network TypeError on auto-decompose ⇒ Python contract bug, not “engine down.”
  • FakeDecomposer tests prove tree logic only — not the production adapter.
  • Error handling belongs at API boundary (create_plan), not inside dispatch (merge-bar #8).
