# R15 agent-memory promotion contract

Use this for the proposal/confirmation increment after the phase-1 containment candidate in [R15-ACCOUNT-MEMORY-EXECUTION.md](R15-ACCOUNT-MEMORY-EXECUTION.md). It is a design and acceptance spec, not an implemented API. The September 24 R15-A/B delta requires a successful agent-originated, source-attributed proposal through the actual memory tool, followed by verified owner confirmation. The broader ingest/memory contract still governs every participating product and the release proof.

## Authority at entry

Classify input before any model or extractor can produce a durable account fact. The envelope has a closed origin type: explicit owner self-report, attributed source observation, tool/retrieval output, assistant inference, hypothetical/quotation, or unknown. The signed session proves the caller; an agent service credential proves only the service. An agent may propose for an owner only through an explicit, authenticated on-behalf-of authority bound to that owner and project. Raw Thought Partner text is mixed-trust and is ineligible as an owner self-report. Source-derived first-person content remains a source observation with source identity, revision, rights, and citation opener even after owner confirmation. A source sentence saying “I” never changes its speaker to the account owner.

Enumerate actual writers before changing the route: `POST /account/memory`, `substrate/memory/interaction_extractor.py`, every registered MCP memory tool, and other graph write call sites. Decide and document which existing direct user-authored note path is a distinct closed `user_note` action, and which callers must enter the proposal flow. A client-supplied `provenance` dict or `authority_*` key cannot establish origin, source rights, project, or confirmation. Completion: every durable owner-fact path uses a server-derived authority and has a negative control that prevents a source passage from reaching the owner-self-report class.

## Immutable proposal record

Persist the proposal table in the **same DuckDB database** as its target owner graph and outbox, through the same sanctioned `connect_write` connection and lock. The current shared graph DB can support a containment-stage test, but release routing must place proposal, graph and outbox in the same physically private owner store. No separate service or database participates in the promised single commit. A pending record contains a random server-minted opaque ID, immutable owner and project/partition, producer/tool and origin kind, closed candidate kind, exact normalized candidate payload plus its canonical digest, creation and expiry, source document and immutable source revision, citation opener, source-rights identity/epoch, and current status. Use a versioned migration with unique `proposal_id` and unique `(owner, project, producer, idempotency_key)`; include proposal state and its terminal authority in backup/restore recovery. Bind a proposal to its source and owner when it is created; accepting an ID by itself grants nothing. Keep pending proposals out of promoted graph memory, memory search/index/export, model context, and ordinary recall; a complete owner data export may include them as clearly pending records. Limit payload size and expiry; log status/opaque ID but no private body. Source labels and rights are retained in the promoted item rather than rewritten by confirmation.

Creation validates the tool's on-behalf-of grant, source readability and proposed use, owner/project, and typed payload before inserting anything. The server computes digest and ID; client time, status and provenance are data, not authority. A retry carries an idempotency key scoped to owner, project and producer: same key plus same canonical request returns the same proposal, while a changed request conflicts without creating another. The proposal response shows exactly what will be confirmed, its source/citation and expiry. Pre-creation authorization failure leaves no discoverable row. Once created, owner refusal and expiry are terminal decisions that never write memory; retry returns the same terminal status without reviving a proposal. Completion: a lost create response can be recovered after restart by the same owner and idempotency key, and wrong-owner lookup reveals no existence or private metadata.

## Single promotion decision

Confirmation requires a later signed owner session and the proposal ID, with the server reloading immutable content. It verifies exact owner/project, pending status, expiry, payload digest and current source revision/rights. For in-system sources, put the rights/revocation epoch in the same owner database and update it through the same write lock; confirmation reads the epoch inside its graph transaction. If revocation commits first, confirmation denies. If confirmation commits first, revocation invalidates the resulting row before any later read or provider send. An external rights source needs a verifiable, short-lived fenced grant valid through commit and read-time revalidation; until that authority is implemented and its revoke-between-check-and-commit race is tested, source-backed promotion from that source stays blocked. Rights-service uncertainty fails closed.

`write_memory_item` currently begins and commits its own DuckDB transaction. Refactor it into a transaction-aware graph/outbox inner operation plus its existing transaction-owning public wrapper; retain the wrapper's after-commit outbox dispatch. Within one `connect_write` lease and transaction, conditionally consume the pending proposal, reconcile the current memory timeline, write the owner-scoped graph item, and commit consumed status, resulting memory ID, and outbox entries together. A unique proposal-to-memory binding makes retry and concurrent confirmation converge on one result. Dispatch external events only after commit and make retries idempotent. `route_memory_update` may return `NOOP` on matching or less-informative text without checking provenance. A `NOOP` satisfies confirmation only when its matched row is already confirmed for this **exact** proposal ID with compatible owner, project, source revision and rights; otherwise leave the proposal pending and refuse with a conflict until the old row is remediated or a separately attributable version is written. Completion: after an injected crash at each cut, restart sees either no promoted row and a safely retryable proposal, or exactly one promoted row and a consumed proposal; no pending proposal can coexist with an externally visible promoted row.

## Red controls before green

Exercise the actual agent tool and signed confirmation boundary with one accepted source-backed proposal, then later-session retrieval in another participating product, canonical HTML source reopening, correction, supersession, revocation and deletion. Use one candidate SHA and the applicable deployed revision, joining source and serving revisions explicitly. For each denial below, assert graph rows/edges, search/index, export, provider request, outbox, and pending/consumed state after restart, not only an HTTP status:

| Control | Required result |
|---|---|
| Source-labelled first-person text, quote, paste/fence, retrieved/tool text, hostile instruction, mixed trusted/untrusted spans | Remain attributed source data or refuse proposal; never owner self-report. |
| Wrong owner, project, tool grant, source rights or purpose | No proposal/private lookup or promotion; no paid provider send. |
| Changed payload, tampered digest/ID, stale source revision, revocation, expiry | No durable memory; explicit safe refusal and no private-value error. |
| Lost create response, retried idempotency key with same or changed payload, owner refusal | One retrievable proposal or terminal decision; changed payload conflicts and no second row is created. |
| Existing unconfirmed or wrong-source row with the same owner/subject/predicate/object | `NOOP` cannot return that row as a confirmed result or consume the proposal. |
| Duplicate/replayed or concurrent confirmation | Exactly one bound promotion; deterministic repeat outcome without a second graph version or event. |
| Revocation concurrent with confirmation | Lock/epoch ordering gives denial or immediately invalidated memory, never a readable revoked fact. |
| Failure before graph insert, after graph insert, before/after commit, then restart | Single-commit invariant holds and retry cannot bypass authority. |
| Pre-deletion backup restore, export import and old-event reindex | Deleted/revoked content cannot reappear before a read or provider send. |

Physical owner stores, injective or rejected account IDs, per-owner keys, J01–J10 journey/control/review joins and two-account M3 proof remain separate release gates. Passing this proposal increment does not close them.
