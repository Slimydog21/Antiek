## Next executable increments

1. **Establish the authority type before promotion.** Start from the pinned, provisional [J01–J10 source census](R15-JOURNEY-SOURCE-CENSUS.md); then inventory every producer and consumer, including `/account/memory`, Thought Partner, graph readers, export, search/index/cache, MCP, REST, and CLI. For each edge, record accepted owner identity, project, source revision and rights, origin trust, read purpose, durable target, and revocation path; cite the implementation or an explicit nonparticipation proof. Completion: the census reconciles to the actual route/tool registration and has no unclassified durable-memory writer or reader.
2. **Implement a server-owned proposal and later confirmation.** Follow the cold-executable [promotion contract](R15-MEMORY-PROMOTION-CONTRACT.md). Through the actual agent-facing memory tool, create a typed, source-attributed proposal that a later signed owner confirms by server-minted ID. A source-derived first-person sentence retains source label and rights; an agent read of a user-created note does not satisfy the write gate. Completion: wrong authority, changed content, stale/revoked source, expiry and replay leave durable memory unchanged, while one valid confirmation promotes exactly once after restart.
3. **Make confirmation and graph promotion one failure domain.** `write_memory_item` currently owns its own DuckDB transaction. A proposal-status commit on either side of it can leave a consumed proposal without a memory row or a memory row with a pending proposal after a crash. Refactor the writer's transaction boundary deliberately or use a recoverably idempotent state machine with a unique promotion key and proven restart recovery. Preserve single-writer locking and outbox semantics. Completion: injected failures before/after graph insert and transaction commit, concurrent confirmations, and restart yield either one authorized row with consumed proposal or no row with a safely retryable proposal.
4. **Close existing-data and isolation gaps.** Inventory `first_person_rules_v1` rows by owner and projection without logging private values; establish reviewed quarantine, correction, supersession, export, revocation and deletion across graph, search/index/cache, context, reader, backup, and restore. At the real authentication boundary, test two IDs whose lossy path normalization would collide (for example `alice/bob` and `alice_bob`). Either both are accepted and their catalog identity, physical store path, encryption-key identity, content, export and clean restore remain distinct, or the second is rejected at account creation and every graph call. Migrate old catalog/file/key references without opening another owner's graph. Completion: wrong-owner reads/writes, a pre-deletion backup restore, a pre-deletion export import, and reindex from an old source/event segment cannot resurrect private data before any read or provider send.
5. **Prove the release contract on the integrated build.** Run one mixed trusted-owner/untrusted-source journey plus literal quote, pasted/fenced text, retrieved/tool output, hostile instruction, stale source, wrong authority, and purpose-limited provider-context negatives. Capture serialized provider request and durable projections after restart. Through the actual agent tool, confirm one source-attributed proposal; reopen canonical HTML source, retrieve it in a later session and a different participating product, then correct, supersede, revoke and delete it. Exercise J01–J10 and M1–M3 with two real signed accounts and source-openable citations, then repeat declared CI and strict scan on the exact integration SHA and applicable deployed revision. Completion: each J01–J10 journey has a source/owner/rights path and joined control and independent-review artifact, or a source-backed nonparticipation proof; R15-A/B and M1–M3 evidence cites build SHA, deployed configuration, source/serving revisions, requests, denials and projections. Only an observed deployed revision receives production credit.

## Current implementation seams

`interfaces/research/api/account_memory_routes.py` still has a one-step `POST /account/memory` that accepts client-supplied provenance and calls `load_memory_timeline` → `route_memory_update` → `write_memory_item`. Authentication is signed-session-only, but no proposal/confirmation or source-rights verification exists there. `substrate/memory/models.py` has no closed memory kind, project partition, source revision/rights, confirmation, or deletion lineage. `substrate/memory/store.py` persists owner-filtered rows in the shared graph DuckDB; source document/chunk checks validate linkage rather than owner/project/rights. The separate `GraphRouter`/`graph_per_user` path normalization is lossy, so owner-filtered tests alone do not prove physical isolation. The Antiek Memory MCP surface has search/citation declarations but no production proposal/confirmation handlers. Draft PR #3436 closes scoped local read and write disclosures, but its process-owner environment value has no verified principal mapping and its public search candidate scan needs a latency bound. Treat each as an open gate, not as a defect repaired by phase 1.

The first safe integration unit is the containment diff. Keep its validation and claim narrowly scoped while the later authority, transaction, isolation, and deletion work proceeds as separate reviewable increments. Any new route or tool that writes durable owner facts must join the same confirmation rule and negative suite before being enabled.
