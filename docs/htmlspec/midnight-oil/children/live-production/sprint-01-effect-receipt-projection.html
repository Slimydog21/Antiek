Effect-receipt graph projection

Make “persisted to the knowledge graph” a replayable fact backed by exact identifiers, hashes, and query proof.

Wave 1Owner: primary orchestrator5 milestones

Parent context

PR #1017 persists exact paid-step evidence and deposits HTML/twins idempotently. It deliberately leaves DuckDB projection unresolved. This sprint adds only the downstream projection phase: no provider dispatch, retrieval, consent, or budget behavior changes.

The graph’s only writer is runtime.db_lock.connect_write. Existing typed insert_node/insert_edge operations and deliverable tables are reused. SQLite job state and DuckDB are separate durability domains, so deterministic identifiers and replay are mandatory.

Technical milestones

1
Close the durable receipt schema.

Add a bounded, secret-free projection receipt and pending/complete state to MidnightOilJob.

Round-trip old rows with pending defaults; reject or sanitize malformed receipt content; never persist raw prompts or API errors.
2
Implement deterministic projection.

Create one research-memo deliverable, one section per returned step, one root entity node, and content-addressed insight/question nodes with source-attributed edges.

All identifiers derive from job/step/content; rerunning produces no duplicate rows or events.
3
Fence projection behind terminal deposit.

Require terminal status, deposit_state=complete, exact step evidence, and a persistent engagement document ID before opening the write lock.

Every invalid precondition makes zero DuckDB writes.
4
Checkpoint truthful effects.

After the DuckDB transaction commits, store the deliverable ID, section/node/edge IDs, HTML hash, evidence hash, and deep links in the job receipt.

Crash after DuckDB commit but before job checkpoint is safely replayed; a checkpoint never precedes graph commit.
5
Prove queryability and recovery.

Use real temporary DuckDB and durable job stores to test rows, links, restart, duplicate suppression, foreign/missing source handling, and failure-state honesty.

pytest, Ruff, strict mypy, and diff checks pass; red tests demonstrate the gates bite.

Rigor: five values

Intellectual honestyA deliverable row is not the knowledge graph. Claim completion only when the receipt’s node/edge IDs can be queried after reopening DuckDB; keep state pending on any pre-commit failure.
FairnessSteelman projecting only engagement-spine twins: it is simpler and already powers HTML. Reject it because Midnight Oil’s source provenance would remain untraversable in the graph; preserve engagement as canonical display storage.
RigorInject failures before commit, after DuckDB commit, and before the SQLite checkpoint. Assert provider dispatch count remains zero during every projection retry.
DiligenceReuse content_addressed_id, insert_node, insert_edge, insert_deliverable, and connect_write; inspect their conflict and event semantics before extending them.
DefensibilityThe receipt must reconstruct why every row exists: job ID, step key, content/evidence hashes, source receipt references, graph deep links, and schema version. Fields without a proof job do not belong.
