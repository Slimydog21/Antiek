Project companion + agent-facing evidence base

Deep-research context — process AND outcome — stops going astray: a generated, human-facing companion document per project and per evidence document, regenerated whole from the lawful stores on every project event, beside a structured, stable-id claim→evidence→process index that agents query instead of re-walking trajectories.     Goal and proof boundary

    The operator’s words: “This sub agent deep research context of both process and outcome gets stored rather than left astray like in current workflows. I want those outcomes to be recorded as a human facing companion document to each project and each evidence document, while also maintaining an agent facing more rich version of that evidence base.” Success is: seed a project with two threads, one island, one fork — the companion reads as one coherent “where this project stands”; fire one more terminal event and a total rebuild shows the delta with ZERO hand edits; an agent asks for evidence_id X and gets claim + evidence + process, byte-stable across a from-scratch rebuild. Nothing in either artifact exists anywhere but as a projection of stores their readers already own.

    ONE projector pass over the lawful stores (graph nodes · event log · artifacts · unit-1 anchors · unit-2 islands · unit-5 forks/merges · unit-7 diligence receipts · unit-4 reading state) → evidence base: claim→evidence→process index, content-derived stable ids (rebuildable from scratch · deletable · a cache with an id contract) → human companion (per PROJECT): "where this project stands" narrative + process appendix (what was diligenced, what it cost) → human companion (per DOCUMENT): that book's islands/threads/anchors/position → rebuild triggers: thread terminal · island resolve · fork merge · diligence land TOTAL rebuild every time — no incremental drift, no companion-specific facts

    Design decisions (made — encoded)

    • The companion is a GENERATED narrative, never a store. Per project (the unit-3 workstation) and per evidence document, a human-facing companion weaving islands, threads, artifacts, diligence runs, forks, and reading state into one readable whole. Regeneration is TOTAL — an idempotent rebuild from sources on every project event — so there is no incremental drift and no companion-specific fact: anything the companion says traces to a store its reader already owns. Hand edits are impossible by construction (non-goal): edits go to the sources; the next rebuild reflects them.
    • The narrative contract: “where this project stands” — open questions and their current best answers, ordered by recency of movement, with per-claim pointers into the thread/island that produced them; plus a process appendix (what was diligenced, what it cost — the unit-7 receipts shape). The narrative SHAPE is taste and goes through the SPR-00 arena: chronological log vs question-organized map vs claim-organized ledger, measured, verdict as a decision-log edit.
    • The agent-facing evidence base is a PROJECTION, not a truth. A structured, regenerable claim→evidence→process index with content-derived evidence_ids (sha over claim text + kind + source refs — stable across rebuilds by construction, with an explicit collision contract), sourced from graph nodes + event log + artifacts. Rebuildable from scratch ⇒ deletable ⇒ a cache with a stable-id contract, never a new source of truth. Agents — the flywheel hook (investigation_start_reuse.py:33), unit-7 spawn composition, future subagents — query it instead of re-walking trajectories. The same projector pass renders the companions and the index: two renderings of one read, so they can never disagree.
    • Each evidence DOCUMENT gets its own companion — the per-document instance of the same generator: that document’s islands + threads + anchors + reading state woven into one narrative, composed through unit-4’s mounts into the reader.
    • Placement: project companion = a unit-3 workstation tab kind (companion) + an exported HTML artifact under paths.py conventions; document companion = a rail/tab in the reader (unit-4 mounts); evidence base = server-side, owner-scoped agent API, with no user surface beyond an honest inspect/debug view.

    Key invariants

    • Generated, never authored: no write path into a companion except the projector; no edit affordance exists anywhere (a test greps for one and finds none).
    • Projection, never truth: the evidence base can be deleted and rebuilt from the sources with identical ids — a from-scratch-rebuild parity test is the proof, run in CI, not a promise.
    • Total idempotent rebuild: rebuilding twice from unchanged sources is byte-identical; rebuilding after one terminal event shows exactly that delta. There is no incremental update path to drift.
    • Stable ids across rebuilds: evidence_id is content-derived; an agent holding an id across a rebuild resolves the same claim (or an honest tombstone when the claim’s source is gone — never a dangling id, never a silent re-point).
    • One pass, two renderings: companions and index come from the same projector pass over the same snapshot; they cannot tell different stories.
    • Bounded writes: rebuild writes follow the batch-and-yield convention (arxiv_oai_sync.py:44-47,105-107) — short write-lock scopes, never a lock held across a pass.
    • Rights flow through: the projector reads only what the reading owner lawfully serves; a withheld document contributes position/lineage/annotation metadata, never body — the same metadata-only degradation units 1/4 already obey.

    SPR-03 · The event wiring — total rebuild on project events

    Contract. Rebuild triggers: investigation terminal events (investigation.completed | .failed | .chase_halted), island resolution (the unit-2 anchor-link lifecycle, consumed as spec’d), fork merge commits (unit-5), diligence status transitions (unit-7) — each schedules a TOTAL rebuild of the affected scope(s) (document scope always; project scope when unit-3 lands). The wiring follows the knowledge_event_projector.py precedent (durable event-driven projection, corruption-honest) with three disciplines: (1) coalescing — a burst of events within one iteration coalesces into ONE rebuild (never N rebuilds for N events; the daemon cadence precedent, daemon.py:279-297); (2) bounded writes — the rebuild’s writes hold the write lock in short scopes per the arXiv lesson (arxiv_oai_sync.py:44-47,105-107), never across the read pass; (3) receipts — each rebuild records {scope, trigger_event_ids, rows_written, rebuilt_at} so the staleness-honesty claim (“rebuilt at T because of events E”) is data, not copy. Failure honesty: a failed rebuild leaves the previous generation serving (never a half-written companion) and surfaces the failure in the receipt — the last good projection is always lawful to show.

    Proof (real calls):
    • Event-driven end-to-end: seed → baseline rebuild → fire one terminal event through the real event log → the triggered rebuild shows exactly the delta; the receipt names the triggering event ids.
    • Coalescing: five events in one window → exactly one rebuild (receipt count asserted), all five ids on the receipt.
    • Bounded writes: a test instruments lock hold times across a large fixture rebuild and asserts each write scope under the bounded threshold (the convention is measured, not recited).
    • Failure: a poisoned fixture (corrupt event payload, the projector precedent’s corruption class knowledge_event_projector.py:42-50) → previous generation still served, failure receipt present, no half-written rows.
    • The seeded-project acceptance from the brief: two threads + one island + one fork woven by the companion; rebuild after a new terminal event shows the delta with zero hand edits; an agent query by evidence_id returns claim+evidence+process — all through the wired triggers, not manual rebuild calls.

    Non-goals: project-scope triggers before unit 3 lands (document-scope only, honestly), real-time push to surfaces (surfaces refetch on focus/load per existing conventions), incremental updates, retry/backoff redesign beyond the coalescing rule.
