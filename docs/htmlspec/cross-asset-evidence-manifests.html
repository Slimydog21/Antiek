Cycle 71: Cross-Asset Evidence Manifests

Compose several durable evidence collections into one cohesive research context without flattening provenance into browser state or prompt prose.

Spec lineage

Parent: Cycle 70 historical collection reader.

    Outcome

    An authenticated operator selects 2–8 saved evidence collections, potentially spanning assets and historical revisions, saves their order as a durable manifest, inspects the manifest without spend, and explicitly launches one research trajectory whose context and provenance are reconstructed from verified storage.

    Authority

    Nested truth

    A manifest stores collection IDs, collection digests, versions, ETags, and manifest ordinals. Collections continue to own exact passage identity; manifests never duplicate excerpts as authority.

    Owner scope

    Authentication supplies the owner. Every collection must resolve under that owner in one read snapshot. Foreign and absent manifest or collection IDs remain opaque.

    Ordered context

    Context preserves manifest order, then collection member order, with explicit collection and evidence delimiters. Duplicate collections are forbidden; repeated passages across distinct collections remain visible and attributed.

    Explicit spend

    Create, list, read, select, save, and inspect perform no provider call and emit no investigation event. Only explicit ChaseThread confirmation launches.

    Persistence

    derived_evidence_manifests stores owner, label, version, collection count, total passage count, canonical manifest digest, and timestamps. derived_evidence_manifest_collections stores ordered collection ID plus bound version/digest. derived_evidence_manifest_operations stores owner-scoped create and launch idempotency receipts, deterministic investigation identity, persisted start event, and delivery lease.

    Create protocol

    1. Require bounded idempotency key, label, and 2–8 unique collection IDs.
    2. Within one write transaction, resolve every collection under owner scope and fully revalidate its revision chain, complete index, members, digest, and locations.
    3. Bind the current immutable collection version/digest and reject a total passage count outside 4–32 or canonical context above 96 KiB.
    4. Hash a versioned canonical envelope containing ordered bound collection references.
    5. Persist manifest, ordered refs, and completed create receipt atomically.

    Read protocol

    • Owner list is bounded and summary-only.
    • Detail reopens every bound collection in one snapshot and rejects version, digest, order, cardinality, member, revision, index, or location drift.
    • Detail returns ordered collection summaries and verified nested sources/locations for inspection, plus an ETag binding manifest ID, version, and digest.
    • A newer current asset revision does not invalidate a manifest bound to historical immutable collections.

    Launch protocol

    1. Accept manifest ID in the path, exact If-Match, idempotency key, question, parent investigation, and closed research tier only.
    2. Accept no context, collection array, source array, provider, model, spend, asset, revision, or digest.
    3. Reserve a deterministic investigation and persisted deterministic event under a delivery lease.
    4. Revalidate the complete manifest after reservation and before append.
    5. Build context server-side and append one start event carrying compact evidence_manifest provenance separately from prose.
    6. Broadcast at least once by deterministic event ID; physical append and in-process handler dispatch deduplicate that ID; complete or replay the receipt.

    Event contract

    InvestigationStartRequestedPayload.evidence_manifest contains manifest ID, manifest digest/version, ordered collection references, collection count, and total passage count. It is mutually exclusive with singleton and same-revision derived_source(s). Historical events validate through a null default. Event schema version increments.

    Workstation workflow

    • The derived asset library exposes an “Evidence manifests” section that loads all owner collection summaries without excerpts.
    • Checkbox selection displays collection label, asset/revision identity, passage count, and selection ordinal.
    • Save freezes ordered IDs and label, suppresses duplicate submission, then shows the durable manifest.
    • Open/inspect fetches manifest detail only. “Research manifest” opens ChaseThread with verified display context and manifest ID/ETag; confirmation is a second gesture.
    • Navigation or panel closure invalidates stale list/create/read responses and prevents stale launch actions.

    Acceptance harness

    • Cross-asset and cross-revision collections preserve both order levels across create, remount, read, and launch.
    • Duplicate, foreign, absent, stale-bound, tampered, over-count, oversized, malformed, and mixed-owner inputs persist and emit nothing.
    • Create and launch replay byte-equivalently; conflicting key reuse fails; concurrent/crash retries append one physical start event and preserve one logical investigation.
    • Launch event context is server-built and compact provenance exactly matches bound manifest refs.
    • Opening, selecting, saving, and inspecting emit zero research events; ChaseThread mount emits zero; confirmation emits one.
    • Focused repository/API/event/React tests, schema checks, codegen, strict typing, production build, HardenX, and hostile review pass.

    Rejected alternatives

    • Widen same-revision derived_sources: destroys a useful provenance invariant.
    • Store flattened excerpts on manifests: creates a second evidence authority and drift surface.
    • Client-generated context or collection ETags at launch: lets stale browser state influence research truth.
    • Automatic launch after save/open: makes organization an implicit spend action.
    • Mutable manifest editing in this cycle: replacement/deletion need a separate concurrency contract.

    Out of scope

    Public sharing, mutable replace/delete, nested manifests, arbitrary DOM ranges, automatic synthesis, provider routing, and canonical asset mutation.

    Five-values rigor

    Honesty: nested collections remain provenance authority. Fairness: owner scope precedes existence disclosure. Rigor: both ordering levels and every immutable index are reverified. Diligence: leases and idempotency precede event mutation. Defensibility: composition remains free until explicit confirmation.

    Harness hint

    Add first-class manifest provenance without weakening derived source validation, persist bound ordered collection references, reuse deterministic event delivery, then add a no-spend workstation composer.
