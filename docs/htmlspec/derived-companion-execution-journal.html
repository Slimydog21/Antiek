Companion Execution Journal

Status: executable Cycle 64 spec. Parent: Cycle 63 settled receipt verifier.

Outcome

Persist the exact request identity before a companion provider send and preserve the normalized grounded-answer candidate in the same SQLite transaction that settles its paid hold. A process may reopen completed output and admit it through Cycles 62-63 without calling the provider again. This cycle still adds no provider adapter, route, quote, approval, reservation UI, or public answer command.

Why the spend ledger owns it

A separate database cannot atomically commit output and settlement. The canonical ResearchSpendLedger already serializes paid authority with BEGIN IMMEDIATE; schema version 7 adds one companion execution table under that transaction. The table does not replace the derived-answer artifact in DuckDB: SQLite owns execution recovery, while DuckDB owns the admitted human-readable answer.

Atomic completion

Completion validates the owner and immutable prepared row, parses canonical candidate JSON, recomputes its output digest, builds the closed Cycle 63 evidence object, settles only a dispatch-possible or unknown non-breached hold, and transitions the journal row to completed before one commit. Failure injection before commit leaves both hold and journal pre-completion; loss of the commit acknowledgment reopens the exact completed row. Changed command intent, output, cost, response digest, owner, hold, turn, or evidence pack is a conflict.

Integrity

Schema checks and triggers prohibit deletion, immutable-column changes, completed-row rewrites, partial completion fields, and duplicate hold/execution identities. Reads recompute canonical request/output/evidence hashes and cross-check the hold, run owner, provider/model, operation digest, settlement command, and Cycle 63 settled receipt. This is SQLite integrity under the existing host trust boundary, not an externally signed hostile-host log.

Acceptance evidence

  • Migration tests cover fresh install, v6 upgrade, every-statement rollback, future-version refusal, and trigger/index presence.
  • Prepare tests cover exact replay, changed intent, wrong owner, absent/wrong-state/wrong-seam holds, concurrency, and no spend mutation.
  • Completion tests inject failure before and after settlement mutation, journal mutation, command/event writes, and commit; assert atomic state and no duplicate provider-send implication.
  • Reopen tests reconstruct the exact candidate, derive the same Cycle 63 receipt, admit once through Cycle 62, and reject all persisted-column drift.
  • Reachability tests prove no HTTP route or production dependency constructs the journal executor.

Next seam

Only after a provider route passes qualification may a future adapter consume an approved reservation, call prepare, set the durable send marker, perform one provider call, normalize its output, and complete this journal. Until then execution remains unavailable.

Harness hint

Refute settlement-without-output, output-without-settlement, post-commit acknowledgment loss, changed-candidate replay, owner/hold substitution, completed-row rewrite, schema downgrade, and any accidental route or qualification promotion.
