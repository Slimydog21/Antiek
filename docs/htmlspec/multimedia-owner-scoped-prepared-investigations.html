Owner-scoped prepared investigations

Cycle: 26. Base: Cycle 25 owner-private editable research plans. Status: execution contract.

Outcome

An authenticated owner can prepare one immutable, inspectable investigation snapshot from the exact current approved version of a multimedia research plan. Preparation is durable and exactly idempotent but grants no execution authority: it emits no event, creates no legacy runnable investigation, writes no graph data, calls no provider, authorizes no spend, and schedules no work.

Prepared authority

The server creates a PreparedInvestigation with a non-runnable mpi_ plus 48-lowercase-hex ID. It contains:

  • Source plan ID, exact plan version, internal source-plan integrity digest, intent ID/digest, and evidence digest.
  • An immutable deep snapshot of the complete ordered question tree, including stable mrpn_ node identities and root provenance.
  • Derived total-node and leaf-question counts that are recomputed on every decode.
  • Preparation request digest, literal state="prepared", and server creation timestamp.
  • Literal execution_started=false, background_work_authorized=false, and null event, graph, provider, and spend authority digests.

No owner digest or idempotency key appears in the public projection. The private canonical envelope binds both.

Creation API

POST /multimedia/research-plans/{plan_id}/investigation accepts only:

  • idempotency_key: 16-128 ASCII alphanumeric, underscore, or hyphen.
  • expected_plan_version: strict positive integer.

The client does not submit owner, investigation ID, source digests, tree, counts, state, timestamps, integrity seals, routing, model, context, budget, or authority flags. The server verifies the internal plan-integrity digest transactionally; it does not expose that tamper seal as client protocol.

Read API

GET /multimedia/investigations/{investigation_id} returns the immutable prepared snapshot only to its owner. Prepared records do not appear in legacy /investigations, trajectory, cascade, graph, daemon, or event-log projections.

Storage and migration

The prepared table lives in research-plans.sqlite3, allowing source verification and insert to share one SQLite transaction. Schema v3 adds multimedia_prepared_investigations without rewriting v2 plans or mutation receipts. Migration verifies the exact v2 schema, runs under BEGIN IMMEDIATE, creates the exact v3 table, sets PRAGMA user_version=3, and commits atomically. Drift or partial migration fails closed; no repair or deletion is permitted.

The table duplicates owner, source IDs/digests, source version/integrity, request digest, canonical envelope, prepared integrity digest, and timestamp. Unique constraints cover owner-key and owner-plan. The prepared row itself is the immutable idempotency receipt.

Creation transaction

  1. Validate owner, plan ID, key, version, and canonical request size before mutation.
  2. Open the privately controlled plan ledger, verify schema v3, and enter BEGIN IMMEDIATE.
  3. Look up the owner-key prepared row before reading current plan state. Exact request replay returns its stored historical response; drift conflicts.
  4. Look up any owner-plan prepared row. A different key conflicts; preparation never mints a second snapshot for one plan.
  5. Load and fully integrity-check the current owner plan. Missing and foreign plans are equally unavailable.
  6. Require exact expected version, state="approved", valid owner approval fields, and all Cycle 25 no-execution fields.
  7. Deep-copy and strictly validate the complete tree. Compute counts and construct the immutable prepared object.
  8. Enforce 128 KiB canonical request, envelope, and response limits; insert the row and commit.
  9. Return only after commit. No callback occurs before, during, or after the transaction.

Concurrency

  • Two identical same-key prepares serialize to one 201, one exact 200, and one row.
  • Different keys for one plan produce one commit and one conflict.
  • Edit first makes the plan draft or version-stale and preparation fails. Preparation first captures history; a later edit does not mutate it.
  • Approval first may make preparation valid. Preparation first against draft fails without retry or synthesized approval.
  • Failure before commit leaves neither prepared row nor partial migration.

Integrity and limits

  • Strict canonical JSON and relational cross-binding cover every duplicated field. Unknown, missing, malformed, non-canonical, or oversized data fails closed.
  • Prepared integrity is SHA-256 over the complete prepared object. The source plan integrity digest is captured from the verified current row.
  • The snapshot reuses Cycle 25 bounds: 256 nodes, depth 8 including root, 64 children per node, 3-2000 trimmed characters per question, unique stable IDs, connected acyclic strict shape.
  • Counts, root provenance, source columns, timestamp, literal state, and every zero-authority field are re-derived or checked on every read/replay.
  • The same private-root, regular-file, ownership, mode, hard-link, and inode-race protections used by the plan ledger apply.

HTTP semantics

  • 201 first creation; 200 exact replay and owner read.
  • Opaque private 404 for malformed, absent, or foreign plan/prepared IDs.
  • 409 for draft source, stale version, idempotency drift, already prepared under another key, or stored-integrity conflict.
  • 413 for request, envelope, or response overflow; framework 422 for strict body validation; private 500 for operational storage or unexpected failure.
  • Every response includes Cache-Control: private, no-store and reveals no owner digest, key, hidden foreign question, path, SQL, or exception detail.

Non-negotiable refusals

  • No use of legacy inv-, POST /investigations, event broadcaster, trajectory, CascadeSession, InvestigationCoordinator, or research runner.
  • No event, graph node/edge/document, embedding, promotion, provider call, network request, route/model selection, budget estimate, reservation, spend record, task, queue, daemon, or scheduler.
  • No launch/start/activate/cancel/delete/list/mutate endpoint and no mutable queued/running/completed/superseded/revoked state.
  • No caller-authored snapshot, provenance, integrity digest, owner, identity, count, state, timestamp, or execution field.
  • No automatic invalidation when the source plan later changes; historical preparation remains an immutable statement about what was approved then.

Acceptance

  1. An exact current approved plan creates one owner-private immutable prepared snapshot; draft and stale-version plans cannot.
  2. Exact replay returns the historical response after later edits/reapproval; changed plan/version/key terms conflict appropriately.
  3. Concurrent same-key and different-key preparations produce exactly one row with defined outcomes.
  4. The snapshot preserves exact order, node IDs, questions, root provenance, and derived counts.
  5. Foreign and absent source/prepared IDs are indistinguishable and every route response is private/no-store.
  6. Row, envelope, tree, digest, count, timestamp, owner, source, zero-authority, canonicalization, schema, and file tampering fail closed.
  7. Exact v2 stores migrate transactionally to v3; migration failure preserves v2 bytes and no partial table.
  8. Static import checks and runtime spies prove create, replay, read, and failures touch no forbidden collaborator or external state.
  9. No legacy event file, trajectory row, graph write, provider record, spend record, or background task is created.
  10. Focused tests, all multimedia backend tests, frontend tests/typecheck/build, Ruff, HTML parsing, diff hygiene, independent reviews, and HardenX pass or any unrelated harness failure is evidenced precisely.
