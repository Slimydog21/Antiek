CYCLE 49

Twin-note creation and Write import

Close the operator workflow from durable recursive-note windows to an exact twin revision and a provenance-bound Write source scaffold, without hidden generation or owner inference.

Spec lineage

Parent: Cycle 48 authorized twin-note serving. Creation reuses Cycle 47 compression; import remains separate from the ownerless Cycle 40 investigation-composition bridge.

  • No child specs. Preview/apply and Write import share the exact V21/V22 authority boundary and one workstation flow.

Outcome

An authenticated account can preview an explicitly ordered bounded set of completed recursive-note windows for one asset, explicitly apply that frozen preview against the exact current twin revision, retry safely after response loss, and import one exact V21 revision or V22 composition into Write as a machine-note source scaffold. No route calls a model, promotes graph evidence, parses publication HTML, infers ownership from labels, silently rebases stale work, or generates prose.

Five values

Precision

Account, asset, ordered complete V20 fingerprints, predecessor, versions, preview digest, command key, and exact V21/V22 hashes remain distinct identities.

Exhaustiveness

Foreign, missing, stale, reordered, duplicate, corrupted, concurrently applied, response-lost, and replay-drift cases fail explicitly.

Craftsmanship

One admission builder feeds preview and apply; one Cycle 48 verifier feeds HTML serving and Write import. There is no weaker parallel parser.

Honesty

Imported agent notes remain machine notes with exact snapshot provenance, not graph claims, human evidence, or generated analysis.

Information

The operator sees exact order, investigation/window identity, counts, predecessor, source type, and imported member structure before irreversible commands.

Creation authority

Preview

POST /research/twin-notes/revision-previews
{asset_id, window_ids:[ordered exact IDs]}
-> {asset_id, expected_predecessor, preview_digest, members, note_count, source_count}
  • Account derives only from authenticated request.state.user_id. The client cannot submit owner, counts, hashes, investigation ownership, or current revision.
  • The preview verifies unique bounded IDs, completed V20 state, canonical source/request JSON, every stored digest, request cross-fields, parser output, note/source ceilings, and authoritative account/asset/investigation ownership.
  • The preview digest binds account, asset, predecessor, versions, and ordered byte-complete member fingerprints. Preview is advisory and non-reserving; it performs no write, repair, recovery, event, filesystem access, provider call, or model call.
  • Foreign, missing, wrong-asset, and ineligible members are one value-free unavailable response. Corrupt owned authority is one value-free integrity conflict.

Apply

POST /research/twin-notes/revisions
{asset_id, window_ids, expected_predecessor, preview_digest, idempotency_key}
-> {revision_id, asset_id, supersedes_revision_id, note_count, source_count, replayed, url}
  • Apply reruns admission and ownership; the submitted digest and predecessor must exactly match. It never accepts a stale preview or silently chooses a newer current revision.
  • (account_id,idempotency_key) binds the canonical complete request and exact resulting revision in a dedicated immutable receipt. Same key and request replays after full verification and reruns durable publication recovery; changed request conflicts.
  • Inside the single writer transaction, apply rechecks V20 bytes, then atomically commits the V21 revision, member/effect/outbox ledgers, and command receipt. A successful prior receipt replays before a stale-predecessor rejection; a new key against stale state conflicts.
  • Ownership resolution remains outside the writer lock. Publication remains post-commit recovery from DB bytes.

Write import authority

POST /write/deliverables/from-twin-note
{source:{kind:"revision"|"composition",id:"tnr-*"|"tnc-*"}, idempotency_key, title, deliverable_kind}
  • The source is exact. Asset IDs, current aliases, published paths, HTML metadata, and caller hashes are forbidden.
  • Revision import reuses the full owner-bound Cycle 48 V21 verifier. Composition import reuses the full V22 row/member/HTML verifier and retains both composition order and every exact V21 identity.
  • Create a blank Analysis section and one source section per exact revision. Each verified agent_note becomes a snapshot text block in source order; no graph node is fabricated. Analysis receives the ordered source occurrences as machine-note context, not generated prose.
  • Dedicated V23 receipts bind owner, request, source kind/id/digest, analysis section, ordered revision hashes, source sections, note ordinals, snapshot hashes, and outline block IDs. Block metadata uses twin_note_revision_v1 or twin_note_composition_member_v1.
  • Same owner/key/request reopens and verifies the complete scaffold. Changed request or drift conflicts. Foreign and absent exact sources are indistinguishable and create nothing. Import performs no model, graph promotion, publication, or spend.

Schema V23

twin_note_revision_commands(
 account_id, idempotency_key, request_sha256, preview_sha256,
 asset_id, expected_predecessor, revision_id, created_at,
 PRIMARY KEY(account_id,idempotency_key), UNIQUE(account_id,revision_id,request_sha256)
)
deliverable_twin_note_imports(
 deliverable_id PRIMARY KEY, owner_user_id, idempotency_key, request_sha256,
 source_kind CHECK revision|composition, source_id, source_digest,

)
deliverable_twin_note_sources(
 deliverable_id,source_ordinal,composition_member_ordinal,revision_id,asset_id,
 body_sha256,html_sha256,source_section_id,note_count,
 PRIMARY KEY(deliverable_id,source_ordinal), UNIQUE(deliverable_id,revision_id)
)
deliverable_twin_note_blocks(
 outline_block_id PRIMARY KEY,deliverable_id,source_ordinal,note_ordinal,snapshot_sha256,
 UNIQUE(deliverable_id,source_ordinal,note_ordinal)
)

Columns, defaults, constraints, indexes, and foreign keys are strictly fingerprinted. Empty malformed V23 tables may repair; any populated incompatibility fails without mutation. Receipts are immutable through this service.

Workstation

  • Extend the existing Twin notes panel with a compact Create revision workflow: asset ID, ordered window IDs, Preview, inspect member/count/predecessor summary, then explicit Apply.
  • Any asset/window edit invalidates preview and creates a fresh command key. Ambiguous apply failure retains the same request/key for retry. Stale conflict retains inputs and offers Refresh preview.
  • All creation controls freeze while preview/apply runs. Success refreshes owner history and exposes the exact revision.
  • Every exact revision has Create Write draft. The exact composition returned by Compose also has Create Write draft. HTML opening and import are separate commands.
  • Import asks for title and kind, retains the exact source and key across ambiguous retry, and navigates to the returned Write deliverable only after success.

Acceptance

  • Signed two-account tests prove equal labels/window investigations cannot cross owner boundaries and foreign/missing probes have identical status, headers, and value-free bodies.
  • Preview order, fingerprints, counts, predecessor, and digest are deterministic; GET/preview purity snapshots DB and forbids writer/filesystem/provider/model seams.
  • Apply proves null-to-root, leaf-to-successor, A/B order identity, stale CAS, changed preview bytes, changed ownership, same-key replay after response loss, conflicting-key reuse, and concurrent one-successor behavior.
  • Receipt, V21 rows, members, effect, and outbox are all-or-nothing at every transaction checkpoint; post-commit publication failure replays one exact revision.
  • Revision and composition imports preserve exact source/member/note order, both V22 and V21 identities, byte hashes, snapshot text, machine-note profiles, and explicit no-generation state.
  • Import replay verifies every section, relational receipt, block, metadata byte, and snapshot hash; foreign/missing/corrupt/drift cases create nothing.
  • V23 valid populated schema reopens; empty partial repairs; populated partial, constraint, default, index, or auxiliary ambiguity fails unchanged.
  • Frontend tests cover preview invalidation, explicit apply, pending freeze, stale refresh, ambiguous retry key reuse, exact revision/composition import, navigation, retained errors, and Cycle 48 regression.
  • Cycle 40 composition import, V20 replay, V21 compression, V22 serving, Write generation/edit/export, typecheck, production build, and strict security gate remain green.

Rejected alternatives

  • Reuse the Cycle 40 importer: it is ownerless filesystem composition authority and models graph evidence, not owner-bound machine-note snapshots.
  • Preview as capability: a preview is immediately stale under concurrency; apply must revalidate and CAS.
  • Automatic rebase: changes operator intent and can create an unnoticed successor from different evidence.
  • Revision identity as command idempotency: cannot detect a reused transport key with a changed request after response loss.
  • Import current asset: later successors change request meaning; only exact IDs are stable.
  • Parse HTML or trust published files: demotes verified DB authority to a replaceable external effect.
  • Create graph nodes: imported advisory notes are context, not promoted evidence.
  • Metadata-only provenance: cannot enforce relational completeness or audit replay drift.

Harness hint

Build one shared V20 admission snapshot, one command receipt boundary, and one dedicated twin-note Write importer. Use separate concurrency, owner-oracle, provenance-replay, schema, and frontend critics.
