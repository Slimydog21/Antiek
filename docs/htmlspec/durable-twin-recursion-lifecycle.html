Durable Twin Recursion Lifecycle

Status: executable Cycle 104 substrate spec. This closes the canonical lifecycle authority prerequisite for recursive note twins. It does not claim automatic model dispatch, universal asset-writer integration, graph promotion, or search indexing.

Purpose and invariant

Every registered, twinnable source revision has exactly one durable obligation and at most one canonical twin binding. A generated twin can be registered as a first-class source only by deriving it from that binding; callers cannot label arbitrary content as a twin to suppress recursion.

The complete canonical source asset, authenticated account, signed completion bytes, canonical output body, and lifecycle history must remain independently verifiable after restart.

Authority boundaries

The ledger accepts only an already completed proposal carrying the existing Ed25519 receipt. It never dispatches a model and replay never repeats receipt validation or paid work after an exact terminal binding exists.

Identity model

  • source_hash is the existing canonical asset receipt hash over identity, title, class, content, and source events. A title or provenance change is a new revision.
  • job_id, twin_id, and binding_id are deterministic domain-separated hashes.
  • completion_digest binds the model identifier, full normalized proposal value, and every receipt claim including its signature.
  • The canonical twin body is stored as sorted compact JSON and HTML is a derived view through the existing research-artifact renderer.

Lifecycle

  1. Register source: validate the complete asset and atomically create a pending obligation plus source_registered event. Exact replay is idempotent.
  2. Record failure: pending may become failed only with a closed failure code. Reset returns the same job to pending and preserves both facts in immutable events.
  3. Bind completion: verify the signed receipt using the existing materializer, persist exact completion evidence and canonical body, transition to ready, and append completion_bound in one transaction.
  4. Register twin: derive child identity and bytes from a real binding, assign a canonical provenance event, mark it non-twinnable, and append twin_registered. No caller-supplied exclusion marker exists.

Durability and corruption policy

Initialization is one immediate transaction. Exact table and trigger SQL plus a schema digest are pinned. Source identities, bindings, metadata, and events reject mutation/deletion. The integrity verifier checks SQLite, schema objects, the global event hash chain, source hashes, deterministic IDs, parent-child linkage, canonical bodies, receipt linkage, and completion evidence. Any mismatch fails closed.

Coverage semantics

Coverage is isolated by authenticated account and applies to every registered source revision. Empty or twin-only corpora are unknown; a non-empty corpus with missing bindings is partial; only a non-empty corpus where every twinnable revision is bound is universal. This is persisted-ledger coverage, not a claim that every Antiek asset writer is wired yet.

Acceptance evidence

  • Restart and duplicate registration preserve one source and one stable job.
  • Invalid receipts and injected pre-commit crashes leave no binding, ready state, or completion event.
  • Concurrent exact completions converge; altered signed bytes conflict.
  • Arbitrary twin exclusions are impossible; child registration requires and reproduces a canonical binding.
  • Failure text cannot carry secrets; reset leaves an auditable history.
  • Schema/event corruption fails startup and integrity checks.
  • Account-scoped reports distinguish unknown, partial, and universal.
