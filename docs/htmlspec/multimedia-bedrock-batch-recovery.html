Cycle 30: Bedrock batch identity recovery

Status: executable feasibility specification. Parent: Cycle 29 durable launch manifest. Base: 8017ac1ac352331dc89bf55eba1d8bdce512506a.

Spec lineage

Cycle 29 owns immutable launch operations. This child owns only a provider-neutral durable asynchronous-submission authority and a dependency-injected Amazon Bedrock batch feasibility adapter.

  • No deeper child is required until authoritative billing or production S3/IAM configuration is proven.

Verdict

Do not qualify or production-enable Amazon Bedrock in Cycle 30. Official AWS contracts prove no-more-than-once create behavior for a repeated clientRequestToken and lifecycle retrieval after a jobArn is known. They do not prove exact final USD billing. Cycle 30 therefore proves identity and lifecycle recovery while preserving the entire spend hold as unresolved through billing_pending.

A lost create response is recovered by replaying the exact durable create request with the same token. Zero list matches, a 404, provider terminal failure, empty output, or local timeout never proves no charge. Existing Exa, Tavily, Perplexity, and OpenAI refusal records remain unchanged.

Five load-bearing values

  1. Intent before effect: exact semantic create request and hold bind atomically before a submit marker or SDK call.
  2. Provider identity is separate from billing: accepted/completed does not mean settled; only future qualified billing evidence may release or settle the hold.
  3. Replay the provider contract, not local memory: recovery reuses persisted request semantics and token despite configuration or process changes.
  4. One pull, one boundary: an advance handles at most one operation and one provider transition; no polling loop, task, scheduler, event, or graph projection.
  5. Production refusal is a feature: tests may inject a stateful fake client, but normal multimedia routes remain blocked and make no AWS call.

Schema v4

Add research_provider_submissions and append-only research_provider_observations to the shared spend SQLite database. A submission binds deterministic ID, exact Cycle 29 operation and hold, owner/run/provider/model, adapter contract, account digest, region, provider model ID, AWS-valid token, complete canonical create request (including the IAM role ARN, which is an authority identifier rather than a credential), recovery strategy, mutable state, optional job ARN, attempt count, and timestamps. An observation binds deterministic ID, submission, source, normalized evidence, raw digest, optional provider identity/status, and timestamp.

Submission states: prepared, submit_possible, create_outcome_unknown, identity_bound, running, provider_terminal, billing_pending, failed_pre_acceptance, and integrity_conflict. Immutable request fields cannot update. State changes use guarded ledger commands plus append-only receipts. Cycle 29 operation rows need guarded state updates rather than their v3 blanket update trigger; immutable operation identity/payload/route columns remain trigger-protected.

Adapter contract

Prepare

Accept a typed immutable request containing job name, model ID, role ARN reference/digest, exact input/output S3 URIs, timeout, invocation type, bounded tags/VPC data, account digest, and region. Persist no credentials. Derive a 64-character lowercase SHA-256 token accepted by AWS.

Submit

Use an injected control-plane client. A future real factory must set SDK retries to zero. Explicitly pass the token; never allow SDK token generation. Validate the response ARN and bind it transactionally. Validation/access rejection may become pre-acceptance only with typed provider evidence.

Recover

After any ambiguous create result, invoke the exact same create request again. AWS idempotency must return one logical job. Changed parameters, mismatched token/ARN, or duplicate identity is an integrity conflict. Transient replay failure stays unknown with the hold retained.

Observe

After ARN binding, GET by ARN once per pull. Cross-check token, model, job name, account/region, and request fields. Running remains running. Every terminal lifecycle becomes billing pending; it never settles or releases spend.

Acceptance

  • Schema v3 migrates transactionally to v4; failure at every statement rolls back, and existing run/hold/launch data remains byte-equivalent.
  • One prepare command atomically binds exact operation, one hold, and one immutable submission; replay is exact and changed request conflicts.
  • A stateful fake Bedrock service enforces token deduplication. Response loss plus process restart causes two create attempts but exactly one provider job and one hold.
  • Changed create terms under the same token fail closed; zero/multiple discovery or GET mismatch never releases authority.
  • One observe pull records at most one observation and transition. Terminal success/failure both retain the full unresolved hold and report billing_pending.
  • No credentials, raw role authority, question text, S3 payload bytes, or provider output leak through the private API.
  • Production registry remains refused and production multimedia registry remains empty. Tests prove no CascadeSession, JSONL event, graph, asyncio task, network, or provider call outside the injected adapter boundary.

Rejected alternatives

  • Qualify Bedrock now: rejected because lifecycle evidence is not final USD billing evidence.
  • Release on terminal failure or list miss: rejected because either may still be billable or eventually consistent.
  • Store only the token: rejected because safe create replay needs every semantic parameter.
  • Reuse synchronous gateway reconciliation: rejected because it assumes lookup by key and conflates identity/lifecycle/billing reconciliation.
  • Enable a fake production adapter: rejected; dependency injection is test authority only.

Out of scope

No live AWS credentials, IAM/S3 provisioning, production route, qualification flip, provider billing claim, result ingestion, HTML research artifact, event/graph projection, scheduler, fan-out, synthesis, spend settlement/release, or exactly-once claim.
