Settled Companion Receipt Verifier

Status: executable Cycle 63 spec. Parent: Cycle 62 grounded answer contract.

Outcome

Turn an already settled, owner-bound ResearchSpendLedger hold into the frozen receipt required by Cycle 62 only when command-bound settlement evidence binds the exact companion turn, evidence pack, answer output, and provider response. This is a verification adapter, not a provider adapter, settlement writer, route registration, or public answer command.

Two authorities

LayerWhat it provesWhat it does not prove
Settled-hold projectionThe run owner, hold intent, settlement command, actual cost, and canonical resolution evidence agree with their stored hashes and command receipt.That arbitrary evidence describes a companion output.
Companion verifierThe hold was reserved for derived_companion.answer; actual cost did not breach its reservation; and versioned settlement evidence exactly matches the expected turn, evidence-pack hash, output digest, and a provider-response digest.That any current provider route is qualified or dispatchable.

Closed evidence schema

Settlement evidence has exactly five scalar fields: schema version antiek.derived-companion-settlement.v1, turn ID, evidence-pack SHA-256, output SHA-256, and provider-response SHA-256. The hold operation digest is independently derived from the schema version, turn ID, and evidence-pack hash. Unknown keys, malformed digests, non-canonical JSON, wrong owner, wrong seam/operation, released/unsettled/breached holds, inconsistent command rows, or changed output refuse verification. The provider-response digest is evidence supplied by a trusted future adapter; it is not a provider signature.

Receipt identity

The verifier derives a deterministic rex_ ID and receipt digest from domain-separated canonical data: owner, run, hold, settlement command, provider/model, operation digest, evidence digest, provider-response digest, actual cents, and resolved timestamp. Raw provider evidence, cost, owner, run, and hold IDs remain internal and are not added to the public answer projection.

Acceptance evidence

  • Ledger tests prove owner isolation, exact replay after reopen, unsettled refusal, inconsistent command/evidence row refusal, and canonical evidence enforcement.
  • Verifier tests prove deterministic receipts and refusal for every changed binding, extra evidence fields, wrong seam/operation, released and breached holds, and missing ledger files.
  • The derived companion integration uses the real verifier to admit an answer, then reopens the answer without a verifier; retrieval still creates no spend database before the explicit test settlement.
  • No HTTP route, dependency wiring, qualification change, provider call, reservation, settlement action, or model execution is added.

Next seam

A future cycle may define a qualified companion provider adapter that emits this settlement evidence from durable provider-response bytes. Until provider qualification, pinned pricing, approval, reservation, and reconciliation are all real, the current execution projection remains unavailable and no public answer admission may be mounted.

Threat boundary

This verifier detects malformed, inconsistent, or partially rewritten ledger records under the existing SQLite trigger and hash model. It does not claim tamper evidence against an actor able to coherently rewrite the database file, command rows, and schema; that requires an external signature or append-log authority and remains outside this cycle.

Harness hint

Refute owner/hold substitution, direct SQLite tampering, settlement-command collisions, over-ceiling settlement, evidence-key smuggling, and any accidental route or current-time qualification promotion.
