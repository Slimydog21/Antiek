Cycle 69: Durable Evidence Collections

Save, reopen, and explicitly research an ordered set of exact passages without reducing provenance to browser state or prompt prose.

Spec lineage

Parent: Cycle 68 curated evidence research.

    Outcome

    The operator can save a 2–6 passage selection as a durable owner-scoped collection, leave the reader, reopen the exact historical revision, and inspect the same ordered evidence. Saving and opening never launch research. “Research this collection” opens ChaseThread; only explicit confirmation invokes a collection-authoritative launch that revalidates stored provenance before emitting one existing research-start event.

    Authority

    Immutable evidence

    Collection members bind exact asset, revision, content digest, generation, citation ID, chunk ordinal, text digest, and excerpt. The derived revision and complete index remain authority.

    Owner scope

    Owner identity comes only from authentication. Foreign and absent collection IDs are indistinguishable. List responses never disclose excerpts from another owner.

    Collection launch

    Launch accepts collection ID, ETag, idempotency key, and question/options. It does not accept sources or context. The server reconstructs both from verified storage.

    Spend boundary

    Create, list, read, save, and panel open perform no model/provider call and emit no investigation event. One explicit ChaseThread confirmation is the only launch gesture.

    Persistence

    derived_evidence_collections stores owner, label, exact revision scope, version, member count, canonical collection digest, and timestamps. derived_evidence_collection_members stores ordered exact source fields with foreign keys to immutable chunks. derived_evidence_collection_operations stores owner-scoped idempotency receipts and a prepared launch identity for crash recovery. Collection digest excludes label, owner, version, and timestamps; it hashes a versioned canonical JSON envelope containing scope and ordered exact members.

    Mutation protocol

    1. Require a bounded idempotency key and canonicalize the complete request.
    2. Replay the same owner/key/hash byte-equivalently; reject key reuse with another hash.
    3. Validate Cycle 68 cardinality, same-revision scope, uniqueness, and aggregate bytes.
    4. Within one database transaction and one connection, reopen owner scope, verify revision chain, complete index receipt, and every exact member.
    5. Persist only verified server values, collection digest, ordered members, and completed receipt.
    6. Return an ETag binding collection ID, version, and digest.

    Read and replay

    • Owner list is bounded and returns summaries only.
    • Detailed read reopens the full immutable revision/index and checks every member and collection digest before returning excerpts.
    • A newer current asset revision does not invalidate a historical collection; the response marks it historical.
    • Any parent, member, order, digest, excerpt, chunk, or index drift fails closed with no partial collection.
    • Reader navigation clears unsaved selection but never deletes saved collections.

    Launch protocol

    1. Require exact If-Match and Idempotency-Key.
    2. Reserve a deterministic investigation ID in a prepared operation receipt.
    3. Reopen and fully revalidate the collection after reservation and before the first trajectory mutation.
    4. Construct Cycle 68 canonical context server-side and emit the existing start payload with ordered derived_sources.
    5. Complete the operation receipt with the start response. Retry recovers or replays the same logical launch.

    Missing precondition is 428; stale ETag is 412; foreign/absent is opaque 404; integrity conflict is 409. No provider, model, context, source array, or spend amount is accepted by this endpoint.

    Reader workflow

    • The evidence tray offers “Save collection” and “Research passages” only when 2–6 passages from one briefing are selected.
    • Save uses the briefing question as the initial bounded label and reports saved state without launching.
    • A “Saved evidence” section lists exact-revision collections for the asset. Opening performs GET only and renders ordered passages.
    • “Research this collection” opens ChaseThread with the verified server response, collection ID, and ETag.
    • Pending save/launch freezes its payload and suppresses double submission. Failure retains evidence and question.

    Acceptance harness

    • Create preserves operator order and survives process/browser remount.
    • Same idempotency key/hash replays; conflicting reuse fails; foreign owner is opaque.
    • Malformed cardinality, mixed scope, duplicates, stale generation, and final-member mismatch persist nothing.
    • Detailed read detects every stored-row and index tamper and preserves valid historical revisions.
    • Opening/saving emits zero research events; launch emits one exact ordered start event and no source/context is client-authoritative.
    • Missing/stale ETag and malformed launch input emit zero events. Retry cannot create a second logical investigation.
    • Focused backend/frontend tests, schema tests, codegen, strict typing, production build, hostile review, and HardenX pass.

    Rejected alternatives

    • LocalStorage/sessionStorage: not durable owner-scoped truth and cannot protect provenance.
    • Saving only citation IDs: omits exact text and revision claims required for later integrity checks.
    • Client resubmission on launch: makes restored browser data authoritative again.
    • Automatically launching after save/open: converts organization into unapproved spend.
    • Cross-asset members or nested collections: require a separate manifest contract.
    • Mutable patch operations in this cycle: complete replacement and deletion require their own concurrency UX; creation/read/launch establish the durable replay spine first.

    Out of scope

    Cross-asset manifests, replace/delete UI, arbitrary highlights, automatic synthesis, provider routing, and canonical asset mutation.

    Five-values rigor

    Honesty: reopened source rows, not saved prose, establish truth. Fairness: owner scope precedes distinctions. Rigor: save/read/launch share one verifier. Diligence: idempotency and preconditions precede mutation. Defensibility: the durable spine adds no provider authority and preserves explicit spend.

    Harness hint

    Extract a connection-aware Cycle 68 verifier, add schema and repository, prove create/read tamper failure, then add collection-authoritative launch and reader restore. No client context is accepted at launch.
