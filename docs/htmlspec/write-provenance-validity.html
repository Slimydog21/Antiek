Cycle 42: edited-draft provenance validity

Status: executable master sprint spec. Parent: Antiek infinite research, reading, and writing workstation. Base: Cycle 41 reviewed commit e72ec11d90a617a53e6ec1ccba760072d7a04c14.

Problem

Write currently preserves prose_provenance after arbitrary prose replacement. X-ray, JSON export, and human-readable Sources then present the old paragraph-to-block map as current. A prompt asking a model to make only a stylistic change reduces risk but cannot prove factual equivalence. The product must distinguish remembered historical provenance from provenance valid for the exact prose now displayed.

Invariant

A paragraph-to-block mapping is current only when the paragraph text is byte-identical to the text for which that mapping was established. Exact hashes prove identity, not semantic equivalence. Any changed, inserted, split, merged, moved ambiguously, or model-rewritten paragraph is not currently grounded until a generation or future verification path supplies a fresh validated map.

Storage contract

Add normalized sidecar table deliverable_section_provenance_validity through an idempotent V17 migration and require the table and its validity column in the schema fast-path sentinel. A sidecar is required because DuckDB refuses an in-place column alteration on the foreign-key-dependent deliverable_sections table. The soft section reference avoids a second ownership tree; the write primitive verifies the section and updates both rows in one transaction. Version 1 binds the full prose SHA-256 and every current paragraph's text SHA-256, status, and origin. Closed paragraph statuses are current, stale, unsupported, ungrounded, and legacy_unverified. Closed origins are generated, manual, ai_assisted, and legacy.

Fresh generation atomically replaces prose, provenance, and validity. Existing rows with provenance but no validity read as legacy_unverified; they are never backfilled as current. Rows without provenance read as ungrounded. Malformed or unknown validity fails closed as legacy_unverified.

Mutation contract

MutationRequired behavior
Exact server-side no-opNo row write, timestamp advance, invalidation, or audit claim. Preserve exact validity.
Generated draftPersist validated map and hash binding in the same database transaction. Supported paragraphs are current; reported unsupported paragraphs remain explicit.
Manual or AI-assisted editRequire the caller's exact prior prose as a compare-and-swap precondition. Return HTTP 409 without mutation on mismatch.
Paragraph preservationUse deterministic order-preserving exact paragraph matching. Remap only unambiguous byte-identical paragraphs and their mappings. All unmatched current paragraphs become stale or ungrounded. Never infer semantic equivalence.
Legacy caller without preconditionRejected at the HTTP boundary. Internal generation uses the distinct fresh-provenance path.

Read and export contract

Section detail and PATCH responses expose aggregate validity plus versioned paragraph validity. X-ray receives server-derived validity. It may trace only current mappings as present support; stale, unsupported, and legacy paragraphs receive explicit language and a section-regeneration action. It must not say “every paragraph traced” when that is false.

JSON export carries both the current-only provenance map and validity object. Human-readable Sources resolve only mappings whose paragraph status is current. Body prose still exports; stale provenance never silently mints a source attribution. Existing content-class withholding remains unchanged.

Concurrency and failure

The backend, not the debounce client, decides no-op, compare-and-swap, paragraph matching, and validity. A delayed autosave or second tab cannot overwrite newer prose. The UI updates its prose and validity state from the PATCH response. Generation gate failure writes neither prose nor validity. This sprint does not claim DuckDB rows and the file-backed typed event log are one atomic transaction; a transactional outbox is a separate future authority if durable edit history is required.

Rejected shortcuts

  • Preserve the old map and call it current after a typo or “stylistic” rewrite.
  • Mark legacy maps current without an exact authoritative prose hash.
  • Recompute validity in TypeScript or trust client-reported paragraph indices.
  • Carry mappings across duplicate, moved, split, or merged paragraphs by guess.
  • Use stale mappings to populate public Sources.
  • Add word-level or semantic provenance in this cycle.

Acceptance matrix

  • Fresh and partially migrated databases obtain the V17 sidecar idempotently; the warm sentinel rejects a missing or partial table.
  • Generation round-trips exact prose/map/hash validity; failed generation leaves no partial state.
  • An exact no-op preserves bytes and validity; stale compare-and-swap returns 409 and changes nothing.
  • A one-paragraph edit preserves only exact unaffected paragraphs. Insert/delete remaps exact unique matches. Duplicate ambiguity, split, merge, and rewrite never produce guessed current mappings.
  • Manual and Cmd+K-applied edits invalidate changed paragraphs regardless of prompt wording.
  • GET, PATCH, reload, X-ray, and JSON export agree on validity.
  • X-ray does not expose trace controls or current-grounding language for non-current paragraphs.
  • Human-readable Sources exclude stale-only and legacy-only mappings while retaining the existing rights gate.
  • Focused backend and frontend tests, TypeScript, production build, Ruff, compileall, diff hygiene, independent review, and HardenX pass.

Non-goals

No automatic model call, semantic equivalence classifier, paragraph-level regeneration endpoint, graph merge, publication transition, transactional event outbox, model training, spend, or provider routing is authorized.
