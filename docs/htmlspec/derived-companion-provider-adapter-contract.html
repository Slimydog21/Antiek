Derived Companion Provider Adapter Contract

Status: Cycle 65 executable sub-spec. Internal contract only. No route is registered or qualified by this sprint.

Objective

Define and prove the narrow trusted boundary that can turn one authoritative provider success into the canonical grounded-answer candidate and provider-response digest required by the Cycle 64 execution journal. Preserve fail-closed dispatch: qualification evidence alone never creates an executable route, and registration alone never overrides failed qualification.

Non-authority

  • No provider SDK, network call, credential lookup, model choice, pricing snapshot, reservation, or public command.
  • No change to project_derived_companion_execution: every current route remains unavailable, non-reservable, and dispatch-denied.
  • No provider response is trusted because it resembles JSON. Only an explicitly registered adapter may normalize its own response type.
  • The response digest is provenance evidence over canonical adapter-owned response material; it is not described as a provider signature.

Contract

  1. An adapter identity is immutable (provider, model, operation) and operation must be answer.
  2. Normalization accepts the adapter's private response type and returns only canonical_candidate_json plus a lowercase SHA-256 provider_response_digest.
  3. The candidate must round-trip through candidate_from_json; unknown keys, malformed claims, non-canonical text, and oversized output fail before journal completion.
  4. The digest input must be deterministic, secret-free, bounded, and explicitly documented by the adapter. Raw prompts, credentials, hidden reasoning, and mutable transport headers are excluded.
  5. A registry lookup requires an exact route identity and rejects duplicates. An empty registry is the production default.
  6. Execution eligibility is the conjunction of a fully qualified evidence record and an exact registered adapter. Neither side can promote the other.
  7. Recovery reuses the journal execution identity and existing provider idempotency key. It never creates a second send authority.

Implementation Sprints

SPR-01: Pure adapter protocol and normalized success

Add typed immutable route identity and normalized-success records plus a protocol whose only behavior is pure response normalization. Validate all public construction boundaries and export no concrete provider implementation.

SPR-02: Closed registry and dual gate

Add an injected in-memory registry with duplicate refusal and exact lookup. Add a pure eligibility function consuming checked qualification records and the registry. Keep the module disconnected from the provider gateway and HTTP routes.

SPR-03: Adversarial proof

Prove empty-default denial, registration-only denial, qualification-only denial, refused-verdict denial, route mismatch, duplicate registration, malformed normalization, deterministic digest behavior, and successful exact dual-gate selection. Reassert the existing public projection remains dispatch-denied.

Acceptance

  • All new behavior is pure or injected; importing the module performs no I/O.
  • No production adapter instance or executable route is registered.
  • No secret-shaped field can enter normalized success or digest material.
  • Strict mypy, Ruff, focused tests, existing qualification/projection tests, diff check, and HardenX pass.
  • A heterogeneous reviewer attempts to refute dual-gate fail-closed behavior; unavailable engines are recorded, never promoted to acceptance.
