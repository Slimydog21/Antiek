Rollout, operator-lane migration, UI handoff

Owner: integration/release worker · Budget: 7 milestones · Depends on SPR-01–03

Parent context

PR #2999 changes research-tier execution, #3000 introduces bootstrap BYOK→env resolution, and stacked #3001 adds operator-only certified key onboarding. These are useful operator-global increments but cannot be treated as multi-user request authority. Rollout must preserve the operator lane while preventing it from becoming implicit fallback for authenticated account actions.

The UI has Settings model inventory and advisory model-decision controls; backend usage/balance routes exist, but no frontend usage dashboard or action-bound payer receipt exists. This sprint adds those consumers from non-secret authoritative execution data, while keeping selection visually and semantically distinct from execution authority.

Goal

Move safely from operator-global dispatch to enforced request-scoped Write authority, with observable shadow comparison, reversible rollout, and honest usage/balance UX.

Technical milestones

  1. Land/rebase order: #3000 then #3001 (or squash their compatible operator lane); #2999 independently after its non-main base is reconciled. Add explicit comments/docs that these do not authorize ordinary user dispatch.
  2. Add execution mode operator_legacy | shadow_request_authority | enforce_request_authority scoped by action, not a global bypass. BYOT_ONLY remains dominant in every mode for account actions.
  3. Shadow Write: compute request authority and log only non-secret reason codes/digests while legacy operator execution remains enabled for the configured operator only. Friends/non-operator accounts never use legacy house/env keys.
  4. Define promotion gates: zero cross-owner mismatches, zero unexplained payer differences, 100% settled receipts bound, restart tests green, and operator has onboarded owner-bound keys/explicit approvals. Promote Write generation to enforce; rollback reverts to operator-only legacy, never ambient house fallback.
  5. Expose receipt/usage API grouped by provider/model/key label surrogate and payer kind; balance state is known|unknown|unsupported|stale with observed-at timestamp. Provider balance queries use the same owner credential at call time and never return raw upstream payload.
  6. UI handoff: Settings dashboard shows per-key usage and balance state; action dropdown shows availability, balance freshness, and estimated cost. Copy: “Selection is a preference; Antiek verifies your key, route, budget, and payer when you run.” Completion shows actual route/payer receipt and fallback rung.
  7. Add migration, feature-mode, operator/friend isolation, UI contract/accessibility, receipt, and rollback tests; publish a checklist for subsequent Write actions and then Research/Read/Speak.

Rigor — five values

1 · Intellectual honesty

Do not call balance “$0” when provider balance is unavailable; render unknown/unsupported/stale and timestamp all known values.

2 · Fairness

Preserve the single-operator usefulness delivered by #3000/#3001 and give it an explicit migration path rather than deleting it before the replacement is proven.

3 · Rigor

Promotion is based on enumerated metrics and fixtures, not visual confidence. A payer mismatch is a stop-ship even if the provider/model matches.

4 · Diligence

Audit every account-model dropdown consumer; label un-migrated actions clearly and do not imply the first Write slice covers all AI actions.

5 · Defensibility

Keep an operator-readable rollout record naming mode changes, evidence, approver, rollback result, and which PR semantics remain.

Dependencies and out of scope

Requires SPR-01–03. UI follows usage/UI child spec. Out of scope: production deployment without operator approval, generalized OAuth, custom endpoint certification, all-action migration, fabricated provider balances, and deleting legacy code before enforce stability.
