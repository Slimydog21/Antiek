Usage and UI handoff

Make account model choice, live eligibility, usage, balance, and actual execution legible without granting the client authority.

Spec lineage

Parent: Request-scoped BYOT/BYOK authority

Child sprint: Receipt and balance UX

Authoritative versus advisory

UI/account datumMeaningNever means
Selected provider/modelUser preference submitted with action.Credential ownership, route qualification, payer approval, or guaranteed execution.
“Available”Non-secret snapshot of current server eligibility.Authority at later click time; server revalidates.
Provider balanceProvider-reported value plus currency/status/observed-at, if supported.Antiek estimate, zero when unknown, or spend ceiling.
UsageSettled Antiek-observed usage grouped by owner key surrogate.Complete provider-account usage outside Antiek.
Execution receiptActual settled/recovering route, payer kind, and fallback rung.Secret, credential ref, owner ID, approval token, raw evidence.

Required surfaces

  • Settings: each connected key shows provider/model coverage, enabled state, Antiek-observed settled usage, balance state and timestamp.
  • Action picker: requested model, eligibility reason, estimated upper bound/rate freshness, balance state. Disabled options remain explainable.
  • Run result: requested versus actual provider/model, BYOT or approved house payer, cost, terminal/unknown state, fallback index.
  • Exact copy near action: “Selection is a preference; Antiek verifies your key, route, budget, and payer when you run.”

Rejected alternatives

  • Show stale selection as “active”: conflates account preference with execution.
  • Render unknown balance as $0: financially misleading.
  • Return credential reference for client correlation: creates unnecessary sensitive identifier exposure.
  • Optimistically show requested provider after fallback: hides actual payer/route.

Harness hint

Use contract, accessibility, and financial-honesty verifier lenses.
