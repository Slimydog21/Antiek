Receipt and balance UX

Owner: frontend/API-contract pair · Budget: 6 milestones · Depends on settled receipt API

Parent context

Antiek has a Settings model inventory and advisory ModelDecisionBar, plus backend BYOT usage/balance endpoints, but no account-facing usage dashboard or action-bound authoritative receipt today. This sprint builds those missing UI consumers from the new non-secret authority snapshot and payer receipt. It must visually distinguish a saved/default model preference from the server's call-time authorization and the route that actually ran.

Goal and milestones

Let a user choose intelligently and audit what happened, without leaking secrets or overstating balances/authority.

  1. Freeze API types for choice snapshot, balance state, usage summary, and execution receipt; reject unknown fields in fixture tests.
  2. Add Settings cards per owner key surrogate with settled Antiek usage, balance status/value/currency/observed-at, and honest unavailable states.
  3. Extend action model picker with eligibility reason, rate freshness/upper bound, balance freshness, and the authority disclaimer.
  4. On submit, send only provider/model preference plus action input; never send owner, credential ref, payer, endpoint, approval, or authority digest.
  5. Render completion/recovery receipt with requested vs actual route, payer label, fallback rung, cost and unknown-outcome next action.
  6. Add keyboard/screen-reader, stale-state refresh, cross-owner fixture, mobile layout, and visual snapshot coverage.

Five-values rigor

Honesty

Unknown, unsupported and stale balances are distinct; none render as zero or “enough.”

Fairness

Keep model selection useful and low-friction; explain server verification without presenting it as a user mistake.

Rigor

Assert the exact outbound request allowlist and exact receipt allowlist, including absence of owner/key/approval identifiers.

Diligence

Test requested=actual, fallback, house-approved, BYOT, refusal, unknown outcome, and refresh races.

Defensibility

UX copy names the provenance of usage and balances so screenshots cannot be misread as full provider accounting.

Dependencies / out of scope

Requires parent SPR-02 receipt and SPR-03 Write response. No credential onboarding redesign, OAuth, provider balance fabrication, global routing changes, or production rollout.
