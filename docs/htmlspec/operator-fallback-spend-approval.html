Let the operator approve one exact prepared fallback chain

Turn the existing durable approval API into an explicit Settings workflow without granting execution, retry, reconciliation, or provider authority.

Outcome

An authenticated operator inspecting recent fallback receipts can review the immutable manifest digest, ordered route caps, run hard ceiling, and maximum sequential exposure, then explicitly approve those exact terms. Success updates only that chain to its durable approval receipt. No hold or provider call occurs.

Authority model

  1. The owner-scoped history read is the approval preview. Each validated chain includes USD currency, run ceiling cents, maximum route exposure cents, and a derived eligibility bit.
  2. Eligibility is true only when every route is unattempted and no approval exists. The server derives it from validated ledger state; the browser never infers authority from timestamps or labels.
  3. The first gesture opens an inline review. The second explicit gesture posts the preview's exact chain ID, manifest SHA-256, and ceiling cents.
  4. The server reopens and revalidates the chain. Any changed manifest, ceiling, owner, lifecycle, existing hold, or integrity state refuses approval.
  5. Success returns the existing minimized immutable receipt. The client applies it only if the same chain and manifest remain rendered.

Interaction

  • Unapproved eligible chains show Review approval, not Execute, Run, Retry, or Start.
  • The review shows the run ceiling and maximum single-route exposure in dollars, explains that fallback attempts are sequential, and lists the manifest prefix already visible on the chain.
  • Approve exact terms is disabled while pending. A second click cannot create a second request.
  • Success displays the durable approval time and receipt suffix. Failure retains the review and exact terms for inspection or retry.
  • Approved, attempted, ambiguous, settled, exhausted, malformed, unavailable, and older-page chains expose no approval command.

Data contract

  • FallbackChainHistory and the API response add currency="USD", positive ceiling_cents, positive maximum_chain_exposure_cents, and approval_eligible.
  • The history validator recomputes maximum exposure from route caps and rejects mismatches, non-USD currency, impossible eligibility, and approval/eligibility contradiction.
  • The approval client requires an exact response shape, SHA-256 and approval ID formats, matching chain/manifest/ceiling/exposure, and no unexpected fields.

Acceptance

  • Ledger and route tests prove preview terms come from the owner-bound run and validated manifest, not request data.
  • Cross-owner, corrupt, changed, attempted, already-approved, and stale-ceiling cases expose no new authority and preserve value-free failures.
  • Component tests prove two gestures, exact POST terms, pending dedupe, matching-chain-only success, retained failure, and no execution-like controls.
  • API-client tests reject malformed terms and response substitution.
  • Approval creates zero holds, provider resolutions, sends, retries, and events.
  • Focused Python/Vitest, TypeScript, production build, Ruff, compileall, token/type lints, diff check, and hostile review pass or unrelated pre-existing failures are reported exactly.

Non-goals

No paid execution button, automatic dispatch after approval, approval revocation, ambiguous-call reconciliation, fallback reordering, model selection mutation, credential handling, invoice claim, merge, or deployment.
