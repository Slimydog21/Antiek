Cycle 72: Collective research composition launch

Status: executable specification. Base: Cycle 71, commit 0762369a4.

Outcome

An operator selects 2-8 completed investigations in the existing Research Workstation sidebar, creates one immutable HTML composition, inspects the ordered member outputs, asks a cohesive follow-up, and launches exactly one new investigation after an explicit confirmation. The server, never the browser, rebuilds the launch context from verified immutable composition members.

Five values

  1. Information density: retain each completed subagent's complete human-readable HTML artifact rather than a client summary.
  2. Provenance: persist composition ID, ordered-set digest, member investigation IDs, content hashes, rendered hashes, and ordinals on the launch event.
  3. Operator control: compose and inspect are spend-free; only the explicit Follow-up confirmation emits research.
  4. Integrity: owner authority and every immutable member are revalidated immediately before event append.
  5. HTML first: composition inspection remains canonical HTML; no PDF or markdown shadow format is introduced.

Bounds

  • Exactly 2-8 unique completed investigations, in caller-selected order.
  • Canonical collective context is at most 192 KiB UTF-8. Oversize compositions fail before persistence or launch.
  • One owner may retain at most 200 authoritative compositions.
  • Launch accepts only question, optional parent investigation ID, and fast/deep tier. It rejects context, member arrays, provider, model, spend, and digest.
  • No edit, delete, public share, nested composition, automatic launch, or implicit model choice is added in this cycle.

Persistence

Add owner-scoped composition authority, ordered member bindings, and idempotent launch-operation tables to the graph schema. Composition creation writes immutable HTML first, verifies it, then transactionally records the owner binding. Replays with the same owner and composition identity return the existing authority; foreign owners receive opaque not-found behavior.

Event contract

Event schema v37 adds research_composition provenance to investigation.start_requested. It is mutually exclusive with derived source, derived sources, and evidence manifest provenance. Exact HTML remains in the immutable composition store; the event carries compact hashes and order.

API

  • POST /research/artifacts/compose keeps its response shape but records owner authority and returns an ETag header.
  • GET /research/artifacts/compositions/{id} requires owner authority and revalidates the index and every member before serving HTML.
  • POST /research/artifacts/compositions/{id}/launch requires If-Match and Idempotency-Key; it uses deterministic event identity and crash-safe delivery receipts.
  • Error mapping: 404 opaque unavailable, 409 integrity/idempotency conflict, 412 stale ETag, 422 invalid closed body, 428 missing headers, 503 append/broadcast/receipt unavailable.

Workstation interaction

  1. Select mode exposes checkboxes only for artifact_composable completed investigations.
  2. The existing Open HTML action creates and opens the owner-bound composition without launching research.
  3. A new Research together action first creates the composition, then shows ordered investigation questions and a follow-up textarea.
  4. One explicit confirmation calls the authoritative launch endpoint. Navigation is disabled while delivery is pending; retries reuse the same idempotency key.
  5. Success navigates to the new live investigation. Stale async results cannot replace a newer selection.

Acceptance evidence

  • Repository tests: owner opacity, order, cardinality, digest/member tamper, capacity, oversize context, replay, key conflict, stale ETag, expired lease recovery, and physical event deduplication.
  • Route tests: authentication, forbidden fields, all status mappings, ETag, replay, broadcast failure, and receipt recovery.
  • Frontend tests: only composable selection, zero launch on compose/inspect, one confirmation/one launch, retry-key reuse, pending navigation lock, stale-response suppression, and error recovery.
  • TypeScript, production build, schema codegen/staleness, Ruff, diff check, HardenX strict, and independent hostile review pass.
