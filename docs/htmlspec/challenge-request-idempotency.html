Durable challenge request idempotency

A browser retry of one living-note challenge must never pay for or dispatch the same model decision twice.

Command identity

  • The browser creates one opaque ASCII idempotency key per explicit challenge gesture and retains it across transport, server, and provider failures.
  • The server binds that key to a canonical request digest containing the investigation, note, and challenge text. Reuse for different content is a conflict.
  • The first accepted command durably records its note sequence and resolving state before resolver dispatch.

Durable state machine

  • resolving: provider outcome is unknown. A retry fails closed and never dispatches again.
  • decided: the normalized resolver decision is durable. A retry applies that decision without provider work.
  • completed: the serialized challenge result is durable. A retry returns it exactly without provider or graph work.
  • unavailable: provider failure is durably classified without storing raw provider details. A retry returns the same generic unavailable response without dispatch.
  • A crash after graph commit but before completion replays the durable decision through the existing idempotent refinement/escalation operation, then completes the receipt.

Boundaries

  • The request journal uses the existing graph writer connection and lock; no parallel write authority is introduced.
  • Raw provider errors, prompts, credentials, and secret-bearing response bodies are never persisted or returned.
  • An ambiguous resolving command is not automatically reclaimed because the provider has no reconciliation contract.
  • Existing authoritative graph outcomes, outbox delivery, sequence ordering, and event schemas remain unchanged.

Acceptance

  • Concurrent or sequential calls with the same key invoke the resolver at most once.
  • A changed request under the same key returns HTTP 409 with no resolver call.
  • A retry after durable decision or graph commit returns the same semantic result with no resolver call.
  • A retry of an ambiguous in-flight command returns HTTP 409; a persisted provider failure returns HTTP 503.
  • Malformed keys are rejected before model dispatch.
  • The workstation sends the same key when its existing retry controls repeat a failed command.
