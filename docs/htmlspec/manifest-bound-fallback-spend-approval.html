Antiek / Infinite / Cycle 79

Manifest-bound fallback spend approval

Split fallback preparation from execution so no paid hold or provider send can occur without one durable operator approval of the exact immutable chain and hard ceiling.

Problem

Cycles 76-78 preflight, persist, and display paid fallback chains, but dispatch_paid_fallbacks still registers its manifest and immediately enters reservation. Cascade has an exact-plan approval precedent, yet fallback execution does not consume equivalent authority. A future caller could therefore bypass a human approval boundary even though the provider resolver is currently empty.

Authority contract

  1. Prepare: project every route, derive all hold/provider keys, and atomically persist one immutable ordered manifest. Preparation spends zero and sends nothing.
  2. Approve: the authenticated owner confirms the exact chain_id, manifest_sha256, run hard ceiling, currency, and maximum independently reserved route exposure. Approval is refused if any chain hold already exists.
  3. Dispatch: recompute the same manifest and require its exact approval before the first and every later reservation. Changed plan, route, pricing, workload, owner, run binding, ceiling, or approval identifier fails before transport.
  4. Replay: one immutable approval remains valid only for recovery of that exact chain. Existing hold/provider idempotency still decides whether to recover, reconcile, or send once.

The approved exposure is max(route.projected_max_cents), never the sum, because routes reserve sequentially and an unresolved outcome halts fallback. The run ceiling remains the aggregate authorization boundary.

Persistence

Add schema v9 research_fallback_approvals: immutable approval_id, unique chain_id, owner/run binding, manifest SHA-256, currency, run ceiling cents, maximum chain exposure cents, command receipt key, and timestamp. Foreign keys bind the chain and run. Update/delete triggers make approval durable. Registration and command receipt commit in one BEGIN IMMEDIATE transaction.

Approval JSON and public responses contain routing metadata and digests only. They never contain prompts, operation payloads, credentials, reservation keys, provider idempotency keys, evidence bodies, or another owner's identifiers.

API boundary

POST /settings/fallback-receipts/{chain_id}/approval accepts only expected_manifest_sha256 and expected_ceiling_cents. Owner identity comes from authentication. The server derives every other field from the ledger, returns a minimized immutable approval receipt, and uses no provider resolver or dispatch adapter. The existing history route remains read-only and gains only approval status and digest when safe.

No execution, retry, provider qualification, route-selection, credential, or revocation control is added in this cycle.

Failure and concurrency invariants

Crash during approval writeApproval row and command receipt both commit or both roll back.

Changed manifest, ceiling, owner, run, or currencyFail before reserve and before provider transport.
Approval after any chain holdRefuse. Legacy or bypassed execution cannot be retroactively blessed.

Process dies after provider acceptanceExisting unknown/reconciliation semantics remain authoritative; approval never permits blind resend.
Cross-owner API requestReturn not found; disclose neither chain nor approval existence.

Implementation sprints

  1. Ledger: schema v9, strict approval types, atomic issue/replay, exact validation, history projection, migration and corruption tests.
  2. Gateway: extract deterministic preparation, require approval for dispatch, prove zero reserve/send before approval, crash replay, and concurrent convergence.
  3. API: owner-derived approval endpoint with no-store responses, expected-digest CAS, value-free failures, and cross-owner concealment.
  4. Verification: broad research suite, API tests, Ruff, typecheck/build if UI contracts change, HardenX strict, and independent hostile review.

Done bar

  • A test proves direct dispatch without exact approval performs zero holds and zero sends.
  • A test proves changed route/pricing/workload/ceiling cannot reuse approval.
  • A kill-point test proves approval row and command receipt atomicity.
  • API tests prove owner isolation, digest CAS, no retroactive approval, minimized output, and value-free corruption handling.
  • The checked production provider resolver remains empty and no paid execution UI exists.

Harness hint

Attack retroactive blessing, approval substitution, max-versus-sum confusion, direct gateway bypass, command replay conflicts, stale ceiling changes, and cross-owner enumeration before accepting the implementation.
