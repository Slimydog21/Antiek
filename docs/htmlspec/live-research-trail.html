Keep the approved research trail alive after launch

The operator-approved hierarchy must remain the map of the work while its leaves run. Restore it from durable session truth on launch, direct route, refresh, and process restart; steer each mapped leaf through the existing runner authority.

Executing

Verified gap

Before launchPlanEditor renders the real persisted roles.cascade_planner.PlanTree, including nested sub-questions and operator approval.
After launchMonitor renders a flat card grid. The hierarchy, rationale, and focus boundaries disappear; a direct session route never loads the plan.
Durability defectThe session event records plan_root_node_id but recovery discards it. It also does not preserve the leaf-to-question-node mapping, so a restarted UI cannot attach controls to plan leaves without guessing.
Prior artPR #2055 is advisory-only, accepts a caller-supplied alternate tree, performs no persistence or execution, and is stacked on a closed substrate. This episode does not import or duplicate that model.

Hard-to-vary episode

  1. The durable cascade.launched event snapshots the exact approved PlanTree, plan version, root, and each launched research's investigation ID, plan-local node ID, and graph question-node ID. This immutable receipt—not a later mutable graph read—is what the session displays.
  2. Live and reconstructed session status return one optional canonical plan envelope containing that launch receipt. A legacy event without a snapshot returns null; flat research status still works.
  3. The monitor renders a dense Research trail rail beside the research cards at desktop width and above them below desktop. It preserves hierarchy, rationale, focus boundary, and human state.
  4. Each leaf maps only by its durable plan-local node ID. A live mapped leaf can pause/resume, redirect, deepen, or stop through the existing steerResearch route. No string/question matching, suffix parsing, optimistic state, or fabricated branch state.
  5. Recovered work has control_available:false. A nonterminal leaf reads “disconnected” and cannot expose controls; structural parent nodes never pretend to be running researches.
  6. Choosing a trail leaf focuses its matching research card and moves keyboard focus there. Card controls remain available only for the live runner; the rail is a second view over one runner authority, not a second execution authority.
  7. Once every leaf is terminal, the trail remains as the completed research provenance map.

Design direction

Subject: an alpine observatory's expedition log: one ink spine, nested brass waypoints, restrained status lamps, Charter questions, mono state stamps. Single job: understand and redirect what the research is doing without losing the whole. The rail is HTML-native, dense, and calm—no generic dashboard cards, gradients, glass, node-canvas spectacle, decorative animation, or image generation. The existing observatory atmosphere and sole Werner remain background narrative authority.

Acceptance

  1. Launch-event and recovery tests prove exact plan root and leaf mapping survive restart; malformed or old event payloads degrade safely.
  2. API tests prove live and recovered status return the same canonical plan hierarchy and mappings; missing plans return plan:null without hiding researches.
  3. UI tests prove direct-route recovery, nested hierarchy, exact graph-ID mapping, legacy unmapped honesty, semantic state labels, focus handoff, and existing steer calls.
  4. Failure never changes a visible leaf state optimistically; the next authoritative poll remains truth.
  5. Keyboard access, reduced motion, narrow/desktop layouts, focused tests, TypeScript, design lints, builds, axe, security, and independent refutation pass.

Non-goals

No alternate plan model, caller-supplied tree, new status vocabulary, pre-launch editing after launch, plan mutation, new research spawn/branch/deprioritize semantics, generated image, canvas rewrite, websocket/video/provider call, model routing, spend change, mascot pose/reaction, merge, or deployment. Those require separate execution contracts.

Critic mandate

Try to prove guessed mapping, duplicate execution authority, plan/session drift, lost restart identity, stale optimistic state, hidden legacy degradation, inaccessible leaf controls, hierarchy flattening, internal-ID leakage, or mobile overflow.
