Anchor-first highlights

A FloatMenu highlight stops being a transient selection rect and becomes a durable, server-persisted passage anchor: it survives reload, repagination, and layout drift, degrades honestly when the underlying text moves, and carries the one nullable seam a future research-thread island will hang from.

Evidence-backed4 sprintsStack base 15e78e276

Spec lineage

Root spec. It stands beside Research evidence reader window (which owns the reader window itself) and owns what that reader currently lacks: persistent semantic anchors on served book text. Children can later split the sprints into their own pages; this page is the single contract until then.

    Goal and proof boundary

    Success is not a painted highlight. Success is: an operator highlights a passage in the canonical BookReader, picks any FloatMenu action (or the new Pin), reloads the page days later — after a repagination and after a source-merge body rewrite — and the same passage is still marked, re-resolved by the server against the current text, with an honest status (active / drifted / orphaned) when the text moved. Nothing about a withheld (non-servable) book's body is ever persisted.

    select text in BookReader → FloatMenu action (Note · Dialogue · Search · Deep-research · Pin) → POST /books/{id}/anchors {quote, prefix, suffix, page_index_hint} → server resolves (chunk_id, start, end) authoritatively against its chunk store → row persisted (DuckDB, write lock) — quote only when the book is servable → reload: GET /books/{id}/anchors → passage anchors → layout-map decorations → text edited / merged: re-resolution pass → active | drifted | orphaned (never deleted)

    The gap, with evidence

    The shared FloatMenu is transient by design. Its own docblock states the boundary: a text selection is "a TRANSIENT user input, not a semantic persistent anchor", positioned from a raw pixel rect and deliberately decoupled from the reading-physics layout-map (apps/reading/src/modes/shared/FloatMenu/FloatMenu.tsx:33-40; the selection hook repeats it at useFloatMenuSelection.ts:18-40). The four actions — Note, Dialogue, Search, Deep-research (FloatMenu.tsx:194-206) — all consume that transient selection; when the page reloads, the highlight and everything spawned from it are gone and cannot be re-addressed. The in-book host proves the second half of the gap: the reader client has no chunk identity at all — representativeChunkId is hard-coded null with an explicit "HONEST GAP" comment because BookDetail/FullTextResponse never expose per-chunk ids (apps/reading/src/modes/Reading/index.tsx:132-150). A persistent anchor is impossible today on both sides: nothing to pin to, nowhere to persist.

    The vision this serves: highlight → persistent anchored artifact → later, an island that holds a whole research thread off that anchor. This spec lands the anchor and its seam; the island is a future spec (see Non-goals).

    Key invariants

    • One anchor schema: the persisted shape IS NodeTextAnchor (substrate/feedback/domain.py:23-32). Any field the highlight store needs beyond it (status, source, investigation link) is a separate column, never a forked anchor type.
    • Server-authoritative resolution: the client sends quote/prefix/suffix (+ optional page hint); the server locates the unique (chunk_id, start, end) against its own chunk store using the same unicode-nfc-v1 normalization. An ambiguous match is a 422 with an honest reason, never a guess.
    • Rights truth at rest: quote/prefix/suffix are persisted only when is_servable_full_text(servability_of(content_class)) holds for the document. Metadata-only anchors are a first-class, documented degradation — not an error.
    • Never silently lost: re-resolution can move an anchor (drifted) or strand it (orphaned); nothing but an explicit owner DELETE removes a row.
    • One reader: standalone /read/:documentId (apps/reading/src/App.tsx:209) and the embedded reader window (apps/reading/src/components/windows/openWindow.ts:106-108) render the same BookReader (apps/reading/src/modes/Reading/index.tsx:48) — anchor loading and painting live in that one component, not in two forks.
    • Calm annotation layer: anchored highlights read as part of the text, not as UI. Tokens and motion come only from the design system (apps/reading/src/design/DESIGN_LANGUAGE.md, FEEL_CONTRACT.md); no new chrome, shadow, or animation engine.
    • Seam, not island: an anchor owns at most one research-thread link (investigation_id, nullable). This spec exposes it; it builds no island UI.

    Anchor record and lifecycle

    pin ──▶ ACTIVE (node_id + node_text_sha256 match current chunk text) │ ├─ body edited / re-chunked / source-merge commit (source_merge.py:311) │ └─ re-resolution pass, per anchor, in order: │ 1. exact: node_id present AND node_text_sha256 matches → ACTIVE │ 2. migrate: hash matches a DIFFERENT chunk (re-chunk remint) → ACTIVE, node_id rewritten, migration event │ 3. fuzzy: quote+prefix+suffix locate a unique span → DRIFTED (offsets rewritten, quote kept, visible) │ 4. none of the above → ORPHANED (row kept, listed, never painted in body, never deleted) │ └─ metadata-only anchor (withheld book): only steps 1 and 4 exist — without a stored quote there is no fuzzy path; stated, accepted, documented.

    Re-resolution runs eagerly after every body rewrite that touches the document (source-merge commit, re-ingest, re-chunk) under the write lock. A GET is read-only: it reports the stored status plus a live exact-validity flag (cheap sha comparison); only when that exact check fails does the handler escalate to the full re-resolution pass under the write lock (write-on-read precedent: books.py:247). Every transition emits a metadata-only audit event via substrate/event_log.log_event — the event payload carries ids, hashes, and statuses, never quote text.

    SPR-02 · FloatMenu integration + anchored rendering

    Contract. Every FloatMenu highlight action auto-pins: Note, Dialogue, Search, and Deep-research each fire the pin call alongside their existing behavior (FloatMenu.tsx:194-206); a fifth Pin button pins without acting. The menu's own transient positioning is untouched (FloatMenu.tsx:33-40 stays true — the menu positions from the raw rect; what changes is that acting on a selection now ALSO persists an anchor). Withheld selections pin metadata-only: the client sends no quote, exactly as outboundText returns null today (floatMenuActions.ts:51-54). Rendering: a new makeHighlightAnchorAugmentation modeled line-for-line on makeChaseLauncherAugmentation (chase-launcher.ts:105-143) — it imports only React + ../types, declares an anchored widget pinned to {kind:"passage", chunkId, start, end} (types.ts:54-63) in a dedicated lane, and resolves through the layout-map (types.ts:86-102) so decorations follow the passage under any transform. The surface work that makes this possible in the book reader — stamping the served body with chunk identity and feeding the layout-map's BaseGeometry — consumes the SPR-03 anchor-map endpoint and closes the HONEST GAP (Reading/index.tsx:132-150) rather than working around it.

    Visual contract. An active anchor paints a text-level wash + 2px underline in the sun token at reduced emphasis — part of the text, no card, border, shadow, or motion beyond the design system (DESIGN_LANGUAGE.md, FEEL_CONTRACT.md). A drifted anchor paints the same mark dashed at lower opacity with an honest "moved" affordance on hover/focus. An orphaned anchor never paints in the body; it appears only in the reader's anchor list with its page hint and an honest "text no longer found" label. Metadata-only anchors paint identically — the degradation is a storage fact, not a visual punishment.

    Proof (real calls):
    • Vitest over FloatMenu: each of the four actions fires exactly one pin with the selection's quote/prefix/suffix; Pin fires one pin and no action; a withheld selection (servable === false) sends a metadata-only pin (no quote field) and the Search/Deep-research refusal behavior is unchanged.
    • Vitest over the reader: after load with seeded anchors, decorations render with stable data-anchor-id attributes at the correct passage on the correct page — in BOTH the standalone route and the window-mounted reader (the existing renderWindowReader harness, Reading.test.tsx:262), proving one implementation covers both.
    • Repagination (font-size change / window resize) keeps decorations on the same passage (layout-map re-resolve), where the old raw-rect menu would have stranded.
    • A drifted seeded anchor renders the dashed/low-emphasis treatment; an orphaned one renders nothing in the body and one honest list row.
    • Pin → reload → the same decoration returns (end-to-end against the real client hook + mocked transport, and one real round-trip in the API test suite).

    Non-goals: changing the menu's transient positioning model, island UI on click, anchor editing UI beyond delete, synthesis/Write-surface anchoring (book reader only this wave).

    SPR-04 · The island seam (contract only)

    Contract. investigation_id ships as a nullable column in SPR-01's table and a nullable field in every anchor payload from SPR-03 — the island spec can hang a research thread off an anchor with zero schema change. At most one thread per anchor by construction (it is a column, not a relation). Write-back: when Deep-research spawns a child investigation from a highlight (Reading/index.tsx:243-259 → spinResearch), the spawned id is written onto the anchor that was auto-pinned for that action. First link wins: a second Deep-research from an already-linked anchor creates its investigation normally but does NOT overwrite the link — merge/retarget semantics belong to the island spec, which will read this field, not reinvent it.

    Proof (real calls):
    • API test: deep-research pin flow → anchor payload subsequently carries the spawned investigation_id.
    • Second spawn from the same anchor: new investigation created, anchor payload unchanged (asserted, not reviewed).
    • Payload shape test: investigation_id present and null on anchors with no thread — the field exists from day one, so the island spec needs no migration.

    Non-goals: everything the island is — thread UI, island rendering, workstation tabs, thread merging, link editing.

    Explicit non-goals (what this spec does NOT do)

    • Island UI — no island rendering, thread panel, or click-through from anchor to research thread. SPR-04 is a field and a write-back, nothing visible.
    • Workstation tabs — no changes to the research workstation's tab model.
    • Thread merging — no merge/retarget semantics for investigation_id; first link wins, the island spec decides the rest.
    • Anchoring on non-book surfaces (Research synthesis, Write deliverables, Speak) — those hosts keep the FloatMenu unchanged and gain nothing visible this wave.
    • Cross-document or corpus-wide anchors; anchor sharing/collaboration between owners; presence or real-time co-editing.
    • Changing servability, takedown, or serve-gate decisions; changing the FloatMenu's transient positioning model; any new Werner asset or motion engine.
    • Migrating or backfilling existing marginalia notes into anchors.
