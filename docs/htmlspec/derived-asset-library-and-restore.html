Cycle 56: Derived Asset Library and Restore

Make applied canonical HTML assets readable and historically inspectable without creating a second mutation authority.

Spec lineage

Parent: Cycle 55 twin-note merge workstation handoff

    Outcome

    An authenticated operator can discover only their derived assets, inspect the exact current HTML and every verified historical revision, compare one historical revision with the current head, and explicitly create an append-only restore revision through the existing generation-bound restore authority.

    Authority boundaries

    Read model only

    Cycle 56 adds no pointer write, delete, replacement, or alternate merge endpoint. merge_commit.restore() remains the sole restore authority.

    Owner derived

    Discovery accepts no parameters. Asset and revision reads join through the authenticated owner. Foreign and missing resources are indistinguishable.

    Exact HTML

    Previews return exact stored canonical bytes after hash, byte-count, manifest, member, policy, lineage, and current-pointer verification.

    Bounded complete chains

    At most 200 assets and 400 revisions per asset. Exceeding either ceiling is an integrity refusal, never silent truncation.

    API contract

    • GET /research/derived-assets: parameter-free owner discovery.
    • GET /research/derived-assets/assets/{asset_id}/revisions: complete verified current-to-root chain.
    • GET /research/derived-assets/assets/{asset_id}/current/frame-preview: exact current HTML.
    • GET /research/derived-assets/assets/{asset_id}/revisions/{revision_id}/frame-preview: exact historical HTML.
    • POST /research/derived-assets/merge/assets/{asset_id}/restore: unchanged exact operation ID, selected revision, expected head revision/hash/generation.

    All reads are private/no-store. HTML frames use default-src 'none', frame-ancestors 'self', sandbox, nosniff, and no referrer.

    Workstation state machine

    1. Discover assets without caller filters.
    2. Select an asset and load its verified complete history.
    3. Inspect current and selected exact revision in separate empty-sandbox frames.
    4. Explicitly restore a non-current revision using the exact current tuple and one retained operation ID.
    5. On success, require exact response identity/generation and refresh. On ambiguous failure, retain the command for exact retry.

    Asset switch, refresh, or revision selection invalidates downstream state. Monotonic generations refuse late responses. Related workstation controls freeze during commands.

    Acceptance harness

    • Owner-only discovery/history/current/exact preview; foreign equals missing.
    • Query and GET-body rejection; bounded asset and revision counts.
    • Hash, byte count, manifest, member order, parent chain, restore lineage, policy, acknowledgement, and pointer drift all fail closed.
    • Restore is append-only, generation-CAS bound, idempotently replayable, and creates no residue on refusal.
    • UI retains operation identity after ambiguous failure and rejects stale discovery, history, and restore responses.
    • Frontend tests, TypeScript, production build, backend compatibility matrix, hostile review, and HardenX pass.

    Rejected alternatives

    • Client owner IDs, filters, locators, or HTML: expands authority and foreign-oracle surface.
    • Directly setting the current pointer: destroys append-only provenance and bypasses CAS receipts.
    • Regenerating previews from manifests: no longer proves the exact reviewed and committed bytes.
    • Returning timestamps, manifests, storage paths, provider metadata, or investigation IDs: irrelevant disclosure.
    • Silent pagination or truncation: falsely presents partial history as complete authority.
    • Restore on selection: collapses inspection and irreversible authority into one action.

    Five-values rigor

    Honesty: only verified persisted bytes are shown. Fairness: missing and foreign states are identical. Rigor: restore binds the exact observed head. Diligence: every revision and member is re-opened. Defensibility: one append-only authority and explicit acknowledgement preserve an auditable history.

    Harness hint

    Implement service, routes, client, and UI in dependency order; then refute ownership, chain integrity, stale-response, and restore-replay claims before publication.
