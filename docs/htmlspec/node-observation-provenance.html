Cycle 87: Node Observation Provenance

Status: executable specification.

Problem

A global content-addressed node can be observed more than once inside one investigation. Cycle 86 correctly models node membership, but its single local origin field cannot represent repeated observations. It may reject a second valid note and cannot tell a refinement event which live note occurrence the user challenged.

Model

  • Membership answers whether an investigation may discover and operate on a global node.
  • Observation answers which investigation-local emerged note and source document witnessed that node.
  • Observation identity is unique on node id, investigation id, and non-empty origin note id.
  • Canonical text, sequence, and authoritative history remain one global node aggregate.
  • Legacy membership origins migrate to observations without inventing absent identities.

Command Semantics

  • Promotion records membership and every supplied origin observation in the same transaction, including exact and near-dedup reuse.
  • The challenge API accepts an optional origin note id.
  • A supplied origin must match the exact node and investigation before idempotency claim or resolver invocation.
  • Without a supplied origin, the server deterministically selects the earliest observation; legacy graph metadata is used only when no observation exists.
  • Challenge request and refinement operation identities include the selected origin so retries cannot substitute another live occurrence.
  • The resulting note.refined event carries the selected origin and observation source document.

Surface Semantics

  • Live NotesPanel sends its note id as the observation target.
  • Completed DistillView may omit an observation target and receives deterministic server selection.
  • A refinement folds only into the selected live note occurrence; another same-node occurrence remains a distinct observation until its own authoritative event arrives.

Acceptance Criteria

  1. Two distinct emerged-note ids with identical text in one investigation produce one node, one membership, and two observations without conflict.
  2. Challenging the second observation emits its origin id and local document id.
  3. An origin belonging to another node or investigation is rejected before resolver and journal mutation.
  4. Reusing one idempotency key with a different origin conflicts.
  5. An origin-less completed-view challenge remains compatible and deterministic.
  6. Fresh install, legacy backfill, repeated initialization, focused backend/UI tests, lint, typecheck, and build pass.
