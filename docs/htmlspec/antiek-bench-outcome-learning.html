Gap spec · ANTIEK-BENCH-OUTCOME-V1

Outcome-grounded recursive Antiek-bench

Learn next-week benchmark emphasis from attributable, operator-graded production outcomes without accepting caller-injected success labels or silently changing dispatch authority.

Status: ready for execution4 sprints · 3 wavesGenerated 2026-07-15

Spec lineage

Root gap spec discovered while auditing PR #804. Parent product evidence: the validated weekly report exposed by corrected #799 and the existing event-log/outcomes substrates on main.

  • No child specs yet. Hatch one only if provider receipt normalization or operator grading exceeds one sprint.

Problem and non-negotiable outcome

Antiek currently has benchmark measurements and generic research outcomes, but no authoritative join across task → chosen model/route → immutable execution → cost/receipt → operator grade. PR #804 accepts arbitrary posted booleans and therefore permits benchmark poisoning, duplicate votes, unauthenticated attribution, and circular self-evaluation.

Do not implement weight learning until the attribution join exists. Empty evidence must yield “insufficient evidence,” never Laplace-smoothed confidence that looks measured.

Success criteria

  • Every eligible learning row is derived from append-only server events and names an immutable run, decision receipt, model route, task taxonomy version, grader, and grade timestamp.
  • Operator grades are idempotent, auditable, revisable by supersession rather than mutation, and excluded when provenance is incomplete.
  • Weekly proposals are advisory artifacts with cohort counts, uncertainty, exclusion reasons, drift bounds, and explicit operator approval before benchmark configuration changes.
  • Replay from the same event-log cutoff produces byte-identical proposal JSON.

Architecture and invariants

model decision receipt ─┐
provider execution close ├─► attributed_run_v1 ─► operator_grade_v1 ─► weekly cohort
task taxonomy/version ───┘                                      │
                                                                ▼
validated bench report ◄── operator approval ◄── advisory proposal_v1
  • No public API accepts a model score, success boolean, benchmark weight, or arbitrary prior weight.
  • Only operator-authenticated grading may affect learning; automated quality signals are separate evidence, never silently promoted to user success.
  • One effective grade per run and rubric version; later grades supersede earlier IDs while retaining history.
  • A proposal cannot mutate dispatch config or benchmark definitions. Approval and application are distinct events.
  • Minimum cohorts and confidence rules are versioned configuration, not magic constants hidden in UI code.

SPR-01 operating manual — attribution receipt

Goal: close the identity seam before collecting opinions.

  1. Define antiek.bench.attributed_run.v1 with run ID, decision receipt ID, task + taxonomy version, provider/model/tier, prompt digest (never prompt body), terminal status, provider receipt/cost reference, started/closed timestamps.
  2. Emit only from the server execution close boundary; reject client-authored model identity and duplicate run IDs.
  3. Build replay projection with explicit exclusion codes: missing decision, missing terminal receipt, unknown task version, unqualified provider, cancelled-before-call.
  4. Add migration/replay and reachability proof from production app wiring.

Files to inspect first: substrate/schemas/events.py, substrate/research_spend/ledger.py, interfaces/research/api/settings_budget.py, provider gateways and research runner close paths.

Verification: adversarial tests for duplicate close, mismatched route, forged client fields, restart replay, and identical digest output.

Honesty: terminal execution is not success; record status and attribution only. Fairness: preserve local/BYOK providers when they can produce equivalent receipts. Rigor: prove the event is emitted from every qualified text-model close path. Diligence: reuse the existing spend receipt identity rather than inventing a parallel run key. Defensibility: version every taxonomy and exclusion code.

Out of scope: scoring models, changing benchmark weights, UI.

SPR-02 operating manual — operator grade

Goal: capture what worked without conflating clicks, latency, or automated judges with user value.

  1. Define a compact rubric: useful, grounded, task-complete, and optional free-text reason; allow “not enough evidence.”
  2. Require operator authentication and an eligible attributed run. Create new grade IDs; corrections supersede prior grade IDs.
  3. Bind grade to rubric version and artifact/run visibility so deleted or quarantined outputs cannot remain silently eligible.
  4. Add a low-friction grade affordance at completed research/reading/writing outputs; disclose how it influences weekly evaluation.

Verification: unauthenticated 401, cross-run grade rejection, duplicate idempotency, supersession replay, not-enough-evidence exclusion, accessibility keyboard path.

Honesty: absence of a grade is missing data, not failure. Fairness: do not punish models used on harder tasks without task-stratified cohorts. Rigor: keep automated quality signals in separate fields. Diligence: reuse operator middleware and append-only event patterns. Defensibility: make rubric copy/version visible in the grade event and Settings.

Out of scope: inferred sentiment, passive engagement scoring, reward-model training.

SPR-03 operating manual — deterministic weekly learner

Goal: propose, never self-authorize, next-week benchmark emphasis.

  1. Select an immutable event-log cutoff and materialize eligible attributed-run/grade joins with counts and exclusion reasons.
  2. Require configurable minimum effective sample size per task/model; withhold proposals below it.
  3. Estimate failure/weakness concentration with uncertainty and cap week-over-week task-weight movement. Do not normalize tiny cohorts into 100% mass.
  4. Emit canonical antiek.bench.proposal.v1 JSON containing input cutoff/digest, algorithm/config versions, current weights, proposed weights, confidence, exclusions, and suggested sub-benchmarks.
  5. Prove byte-identical replay and property-test nonnegative weights, exact sum, bounded drift, and monotonic response to added failures within the same cohort.

Verification command target: uv run pytest tests/test_antiek_bench_outcome_learning.py -q plus a replay fixture run twice with identical SHA-256.

Honesty: “insufficient evidence” is a first-class output. Fairness: stratify by task and compare like-for-like routes before up-weighting. Rigor: property tests must attack cohort imbalance and superseded grades. Diligence: source current weights from the validated benchmark definition, never request JSON. Defensibility: publish the full derivation ledger alongside each proposal.

Out of scope: online reinforcement learning, automatic provider routing, mutation of dispatch config.

SPR-04 operating manual — review and approval

Goal: make recursive learning inspectable and reversible.

  1. Add a Settings evidence view showing cohort sizes, excluded rows by reason, uncertainty, old/new weights, movement caps, and suggested sub-benchmarks.
  2. Require operator confirmation that creates antiek.bench.proposal.approved.v1; approval references exact proposal digest.
  3. Publish a new versioned benchmark definition artifact; never edit the prior definition in place.
  4. Show applied/not-applied state and rollback-by-selecting-prior-version. Keep dispatch use advisory until separately authorized.

Verification: stale-digest approval conflict, double approval idempotency, inaccessible proposal refusal, visual/a11y states for insufficient evidence, pending, approved, rejected, superseded.

Honesty: display uncertainty and exclusions beside recommendations. Fairness: the operator can inspect which providers/tasks lose weight. Rigor: approval must bind the exact digest tested in UI. Diligence: integrate the corrected #799 panel instead of adding a second Settings surface. Defensibility: retain proposal, decision, approver, and rollback target as immutable artifacts.

Out of scope: automatic approval, provider billing changes, NotDiamond production routing.
