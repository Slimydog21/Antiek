Thread merge + document fork

The operator forks a document into a named, first-class divergent version with queryable lineage — then merges selected insights and open-question outcomes from one or more research threads INTO the fork, resolving every claim conflict by hand, with the original untouched throughout. Contexts merge as reviewed composition this wave; graph surgery is a documented non-goal.

    Goal and proof boundary

    The operator’s words: “the user can use those insights from those deep researches that enriched an insight or enhanced the clarity on a set of open questions… merge their data into the document and create a forked version” — and subagent contexts “can be merged manually or automatically over the course of the document or project.” Success is one honest round trip: fork a book, pick outcome items from two research threads in a composed view, preview the merge into the fork, resolve one real conflict by hand, commit — the fork carries the merged outcomes with an audit trail, the original is byte-identical, and lineage answers “what forked from this?” and “what did this fork from?” in both directions.

    Design decisions (made — encoded)

    • The fork primitive. A document fork is a named, first-class divergent version: a real library document with a lineage row (fork id · parent document id · fork-point locator · note · created_at · owner). The body is COPIED IN FULL at fork time — operator-scale data, and the capture reuses the source-merge snapshot discipline (before/after hashes + byte counts, source_merge.py:55-69,118-160) so a fork’s provenance is as auditable as a merge commit. A fork is NOT a source-merge commit: no before/after restore semantics against the original, no acked-body-rewrite theatre — the original is never touched. Lineage is queryable both directions (forks-of-this, parent-of-this). Registration goes through the rights chokepoint (register.py:201-213): a fork inherits its parent’s rights posture, deny-by-default, so a fork of a non-servable document stays owner-only under the same gates.
    • Selective thread-outcome merge into a fork. The operator picks insight / open-question items — stable node_ids from one or more threads in the composed evidence view — and merges them INTO a fork through the shipped preview → receipt → commit SHAPE (source_merge.py:286,310; the acknowledgement discipline of artifact_routes.py:399-543) retargeted at the fork document via a new fork-merge route family and substrate module. Claim conflicts — same passage, different assertion — are detected by unit-1’s anchor/hash machinery where anchors exist (a merge item grounding to the same passage with a different hash) and by compose’s hash-conflict pairs (compose.py:27) across members, ELSE by explicit operator selection. Conflicts land in a conflict list the operator resolves item-by-item (accept incoming / keep fork / skip); nothing auto-resolves silently, and every resolution is recorded (who, what, which way, when — audit table).
    • Thread-context merging, v1 honest scope. MANUAL = the extended composed-evidence view: two or more investigations’ outcomes reviewed side by side, items selectable for merge into a fork (this is “contexts merged manually over the course of the project,” delivered). AUTOMATIC = unit-7’s diligence path may compose related threads into its spawn context — already gate-safe, already shipped-shaped; this spec cites it and changes nothing. GRAPH-LEVEL investigation merging — re-parenting, node grafting, claim auto-unification — is a documented NON-GOAL for v1: the composed view + selective document merge delivers the vision’s value without inventing a graph-surgery discipline whose conflict semantics nobody has specified.
    • Prototype gate (SPR-00, the unit-3 pattern). Fork UX and conflict-picking UX carry taste decisions that must not be chosen on paper. Fork presentation: (A) first-class library document with a lineage banner; (B) fork card hanging off the original in the reader; (C) fork as a unit-3 workstation tab kind. Conflict picking: (i) side-by-side diff picker; (ii) list with per-item accept/theirs/skip. Criteria below; the verdict lands as a decision-log edit replacing the OPEN row before SPR-01 begins.

    Key invariants

    • Originals are immutable by forks: no fork operation, merge-into-fork, or lineage query ever writes the parent document. Asserted by before/after body hash in the proofs, not by review.
    • Conflicts never auto-resolve: every conflicted item waits for a human choice; the resolution record is the only way a conflicted item changes state, and the audit row is written in the same commit scope.
    • Refs and lineage beyond the body copy: the one sanctioned bulk copy is the fork capture itself; everything else — merge items, conflict entries, resolutions, lineage — stores refs (node ids, anchor refs, hashes), never thread content beyond the item’s own text as rendered in its source artifact.
    • Gate-safe on withheld documents: forks of non-servable documents stay owner-only (rights chokepoint, deny-by-default); merge previews and conflict views render only what the existing gates serve; no fork route becomes a second fetch path around serve_full_text_guarded (serve_guard.py:233).
    • source_merge’s shipped behavior is unchanged: the in-place book-merge contract (its acks, receipts, restore) keeps its semantics and its tests; the fork-merge REUSES the shape in a new module and never edits the old one’s behavior.
    • Compose stays what it is: no new load on /artifacts/compose (whose API-layer default is mutating, artifact_routes.py:103-105) — fork-merge has its own routes, and the composed evidence view is a client composition over the existing distill/artifact reads.

    SPR-02 · Selective thread-outcome merge into a fork

    Contract. New substrate module substrate/research_artifact/fork_merge.py REUSING the shipped shape — preview (no writes, full receipt with before/after hashes + conflicts) → commit (write-lock scope, body rewrite of the FORK ONLY, ledger row) — with the acknowledgement discipline of the source-merge routes (artifact_routes.py:399-543) carried into a new /artifacts/fork-merge/preview|commit family. Input: a fork id + a list of selected items (investigation id + node id, from DistilledNode identity, lib/api.ts:1223-1238). Preview renders the would-be fork body (items appended under an honest provenance marker naming their source investigation, the source-merge marker pattern source_merge.py:214-225) and the conflict list: (a) cross-member hash conflicts from compose’s pair model (compose.py:27), (b) passage conflicts via unit-1 anchors where the item grounds to an anchored passage with a differing hash, (c) operator-flagged conflicts. Commit requires per-item resolutions for EVERY conflicted item (accept | keep_fork | skip); each resolution writes an audit row (fork_merge_resolutions: flag of the choice, the item ref, the conflict ref, operator, timestamp) in the same scope. Zero-conflict merges still pass preview (the receipt is the contract, not the conflict).

    Proof (real calls — the brief’s round trip):
    • Against a real fixture: fork a document, select outcome items from TWO threads, preview → receipt with honest after-hash; commit → the fork body carries both items under provenance markers naming their threads; the ORIGINAL’s body hash is unchanged end-to-end.
    • One FORCED conflict (two items asserting differently over the same passage): preview lists it; commit without a resolution is REFUSED (409, no partial write — body hash unchanged); commit with accept lands the incoming claim and the audit row; commit with keep_fork leaves the passage and still audits.
    • Anchor-based detection: with a unit-1 anchor fixture on the passage, the differing-hash item is auto-LISTED as a conflict (detection works where anchors exist); without anchors, only (a)/(c) fire — the degradation is asserted, not assumed.
    • Withheld-source item: an item grounding to a non-servable document merges only its own text (what the operator lawfully sees in the artifact), never source body — asserted on the committed fork body.
    • Audit completeness: every resolution row recomputes against the commit ledger (count + refs match).

    Non-goals: the composed view UI (SPR-03 supplies the selection surface; this sprint’s proofs drive the API directly), merge-back, auto-resolution of any kind, reordering/editing merged items post-commit (a later wave), in-place (non-fork) targets.

    SPR-03 · The v1 context composition — extended composed evidence view

    Contract. The client composition that makes “contexts merged manually over the project” real: an extended composed-evidence view over two or more investigations — each thread’s insights and open questions (the existing distill reads, api.ts:1506-1516) rendered side by side with per-item selection, the compose hash-conflict pairs shown honestly where members disagree, and “merge selected into fork…” flowing into SPR-02’s preview. The honest boundary is displayed, not implied: the view composes OUTCOMES for review and selective document merge — it does not merge the investigations themselves (their graphs, trajectories, and lineages stay distinct), and an honest label says so where the operator selects. AUTOMATIC composition stays unit-7’s (gate-safe spawn contexts), cross-referenced, untouched.

    Proof (real calls):
    • Vitest over the view against a mocked transport: two threads’ items render side by side with stable node-id identity; selection carries exact (investigation, node) refs into the SPR-02 preview call (request body asserted); hash-conflict pairs render as conflicts, not as merged text.

    • Fetch discipline: the view issues only existing distill/artifact reads + SPR-02 routes (network mock surface asserted — no new read endpoints).

    Non-goals: graph-surgery of any kind (re-parenting, node grafting, claim auto-unification), live collaboration, saving named compositions (client-local selection this wave), changes to unit 7’s spawn composition.
