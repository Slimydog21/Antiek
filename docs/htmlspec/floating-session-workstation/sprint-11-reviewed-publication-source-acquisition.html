Technical milestones

1
Freeze reviewed source and connector authority

Derive one closed canonical manifest from the immutable collective unit and select an independently loaded, signed, expiring connector capability. The capability commits the compiled adapter contract, exact destination, transport policy, response limits, T1-only rights policy, evidence reference, validity interval, signing key id, content hash, and signature.

Acceptance: The manifest and capability hashes are pinned through preparation, context binding, owner authority, JobConsentConfig v5, enqueue delivery, worker startup, durable acquisition identity, and evidence receipts. API and worker verify the same artifact independently and permit overlapping validity windows for safe rotation. Nonempty publication scope requires signed swarm authority. Capability coverage is checked at preparation, inside the locked consent CAS, at run/delivery, before the durable crossing, and after governor wait immediately before each request.
2
Acquire arXiv abstracts through fixed egress

The production connector exposes no generic URL method. It permits only https://export.arxiv.org:443/api/query with one exact id_list, disables proxies, redirects, compression, credentials and subresources, resolves once inside connect, rejects the entire DNS answer set when any address is non-global, dials a selected numeric address, verifies the connected peer, then performs strict CA and hostname TLS using export.arxiv.org as SNI.

Acceptance: Only one exact Atom entry and non-truncated T1 abstract are evidence. Destination audit records capability/host/port/resolved/selected/transport-result/time without source identity, query, body, token, or secret. Known blockers stop before consent/enqueue; an acquisition failure stops before every paid provider. Applied checkpoints replay after expiry without egress, while claim-without-result is reconciliation-only and never refetched.
3
Extend canonical evidence receipts

Use a discriminated corpus/publication receipt union. Bind each publication receipt to owner digest, execution/job, manifest and capability hashes, stage key/role, question, reviewed ref, signed plan, connector id/version, canonical URL, extraction mode, rights tier/use, byte length, and excerpt SHA-256. Treat source text as inert evidence input.

Acceptance: Gatherer output accounts for every supplied receipt once; cross-owner/job/manifest/capability/stage/ref/question substitution, connector-version drift, kind confusion, changed bytes, prompt injection, duplicate identity, and off-manifest material are rejected on first result and applied replay. Substack remains production-disabled until a separate exact-post authorization and bounded-range receipt proves scope; a byte cap alone is insufficient.
4
Show scope, attestation, and limitations before consent

Render the exact reviewed publication list, acquisition mode, cap, capability hash and validity horizon, readiness, and exclusions in the cohesive-execution panel. Require preparation to return manifest and capability identities and invalidate prepared authority when either reviewed context or signed connector authority changes.

Acceptance: The UI says arXiv abstract, never claims full-text access, never offers generic web, keeps the consent token ephemeral, disables consent when any required source lacks an attested connector, and projects terminal limitations honestly.

Rigor — operating manual

1 · Intellectual honesty

A source reference proves reviewed intent, not successful acquisition or redistribution permission. The manifest and UI must distinguish arXiv metadata/abstract, bounded Substack excerpt, connector unavailable, truncated/paywalled, and rights-denied; never turn identity-only material into evidence.

2 · Fairness

Steelman querying the whole operator corpus: it improves recall and remains useful as a separate signed policy, but it does not satisfy the user's exact-source request. Preserve corpus retrieval while ensuring external connector traffic is limited to the confirmed unit; publishers absorb no hidden scrape or paywall-bypass behavior.

3 · Rigor

Test manifest ordering, ref-id recomputation, custom/generic host rejection, 64-ref/256-KB caps, redirect and DNS/private-IP egress attempts, Unicode byte caps, license unknown, unproven Substack excerpt scope, connector absence, crash checkpoints, changed retry bytes, cross-execution receipt substitution, and provider-call count zero—including planner—for every source failure.

4 · Diligence

Reuse SourceReference normalization, collective_preview_sha256, JobConsentConfig v3 binding, signed SwarmLivePlan authority, acquisition.arxiv metadata client, explicit Substack injector seam, arxiv_tiers deny-by-default resolution, and live-stage receipt joins. Do not reuse hydrate's exception-swallowing identity fallback in a paid gather path.

5 · Defensibility

Persist the manifest JSON/hash, connector identity, canonical URL, use mode, rights/truncation fields, exact excerpt hash/bytes, question lineage, and terminal limitations. A future auditor must prove which reviewed source was requested and what bounded bytes reached a model without retaining secrets or an unauthorized full body.

Rejected alternatives

  • Pre-resolve then call an ordinary hostname HTTP client: rejected because a second resolver lookup reopens DNS rebinding.
  • Use an IP URL, forged Host header, disabled hostname verification, redirects, or ambient proxies: rejected because each weakens destination or TLS identity.
  • Treat a self-hash/readiness boolean as authorization: rejected; the independently verified signed capability is the egress authority.
  • Reuse the interactive hydrate adapters: rejected because their identity-oriented fallback and exception handling are not a paid exact-source boundary.
  • Admit T2, T3, unknown rights, truncation, or partial source success: rejected for this slice; only authoritative T1 abstracts proceed.
  • Reuse arXiv authority for Substack: rejected. Future Substack work requires signed owner and collective review, exact-post identity, permitted byte range, policy evidence, expiry, and a capability-bound receipt; scraping and paywall bypass remain forbidden.

Known cryptographic limit: v1 uses the existing HMAC verification-key composition, so holders of a verification key can also sign. A future asymmetric key rotation may replace it without weakening the content-addressed lifecycle contract.
