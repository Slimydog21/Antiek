Falsifiable minimum and exact lookup rule

The store admits one immutable encrypted bundle under a CSPRNG 256-bit opaque_source_bundle_id and an authenticated owner-path discriminator supplied by the owner-authentication boundary. A resolution attempt must supply that random selector plus every expected ordered (receipt_id, receipt_sha256) pair. The selector alone, either member of a pair alone, a caller-supplied receipt object, a content-derived database key, a deterministic blind index or an enumerable owner listing is never authority. The store selects at most one bounded ciphertext, authenticates and decrypts it inside the store boundary, reparses the closed bundle, recomputes every predecessor identity and then compares both exact pair members in constant time. Only after all joins succeed may it mint one content-free nonportable witness. It returns no receipt, V4/V5 object, CoreV2, EnvelopeV2, source byte, ciphertext, plaintext callback, arbitrary continuation or generic getter result.

Honest lookup boundary: pair-only lookup cannot coexist with both zero decrypt and zero secret-derived index material. Cycle 31 therefore requires the random opaque selector in addition to the exact pairs and permits one bounded internal authenticated open solely to compare the requested bundle. This is not a generic decrypt method or a trusted immutable V5 resolver for the Cycle 29 adapter. The adapter remains on its certified supplied-resolver trust boundary until a separately versioned production composition exists.

First-byte and last-byte rules

  • First durable byte: no secret or secret-derived byte may reach SQLite, a journal, WAL, shared-memory file, temp file, exception, diagnostic or backup before the complete canonical bundle has been validated, encrypted and reduced to the frozen plaintext-column allowlist. The first permitted durable content-bearing byte is randomized authenticated ciphertext inserted inside the same BEGIN IMMEDIATE transaction that appends its opaque source-head successor and advances the exact current pointer.
  • First plaintext byte on resolution: plaintext may appear only after owner-path authorization, selector syntax, expected head/revision, freshness and bounded ciphertext-length checks pass. AEAD open and canonical parse occur in one store-owned bounded frame; pair and anchor comparison precede witness creation.
  • Last plaintext byte: the store destroys all mutable plaintext buffers and references before returning or raising. No naked str, bytes, model, generator, memoryview, traceback local, callback capture or cache survives the frame. Python cannot prove physical zeroization of immutable interpreter copies, so tests prove reachability/API/log closure and the residual in-process memory limitation is explicit rather than claiming cryptographic erasure.
  • Last authority check: the operation re-reads the source current pointer and row revision in its final read transaction. The returned witness reports only that instant; it cannot authorize a later transition.

Opaque rollback-floored source head

OwnerPrivateSourceAuthorityHeadV1 is signed with a source-head-only Ed25519 purpose and contains a per-owner registry id, strictly increasing epoch and issuance time, exact predecessor head hash, an opaque snapshot of random bundle ids and row revisions plus cumulative opaque tombstones, key id, issuer role, signature scheme, head hash/signature and non-conferral literals. Receipt ids, receipt hashes and other private commitments never enter the plaintext head. The durable store uses a separate exact-schema SQLite root, restrictive directory/file permissions, canonical non-symlink path, WAL, foreign keys, synchronous=FULL, busy timeout, a bounded append-only chain and one current pointer. Every read walks and verifies current-to-floor, rejecting missing floor, cycle, fork, orphan, invalid signature, row/document conflict, epoch gap/regression, time regression, future head, stale head or non-monotonic tombstone history. Writers use BEGIN IMMEDIATE, exact expected head and exact expected row revision; one concurrent successor wins.

External floor and rollback limit: rollback resistance exists only relative to a trusted floor hash configured outside the source database and its backups. Rolling the database and its colocated floor configuration or key-provider state back together is not detected. Cycle 31 provides no transparency log, remote monotonic counter, hardware root, cross-device quorum or automatic re-anchoring. Backup/restore is quarantined until an external-floor restore ceremony is specified and tested; a local backup must never silently become its own trusted floor.

7. Rejected alternatives and explicit non-goals

Rejected: amend or mutate v1

V1 precommits no successor key and denies every sink. Adding PASS, attaching an external activation, or interpreting v1 through v2 rewrites signed meaning. Only new capability-v2/receipt-v5 authority can enter this lane.

Rejected: generic optional fields

Generic readers, recovery, hashes, deposits, flywheel, graph, and telemetry remain leak paths even if a checkpoint accepts optional taint. Guards resolve durable authority.

Rejected: hash-only compliance

A caller output hash, PASS boolean, paraphrase score, semantic similarity, or first-match scan cannot authorize a sink.

Rejected: tags or shared plaintext

personal_reading, owner filename hashes, privileged tags, shared engagement roots, and per-owner paths without content encryption are not sufficient owner-private storage.

Out of scope

No production transport/admission, provider-response recovery API, public/share/export, marketplace, team ACL, cross-owner merge, or legal-clearance claim. These remain denied or F/later work.

Movability

Capability/policy, extractor/normalizer/checker, storage envelope, sink receipts, and graph projection have separate identities. Later checkers, key rotation, or shared ACLs cannot silently alter them.
