Falsifiable minimum and exact lookup rule

The store admits one immutable encrypted bundle under a CSPRNG 256-bit opaque_source_bundle_id and an authenticated owner-path discriminator supplied by the owner-authentication boundary. A resolution attempt must supply that random selector plus every expected ordered (receipt_id, receipt_sha256) pair. The selector alone, either member of a pair alone, a caller-supplied receipt object, a content-derived database key, a deterministic blind index or an enumerable owner listing is never authority. The store selects at most one bounded ciphertext, authenticates and decrypts it inside the store boundary, reparses the closed bundle, recomputes every predecessor identity and then compares both exact pair members in constant time. Only after all joins succeed may it mint one content-free nonportable witness. It returns no receipt, V4/V5 object, CoreV2, EnvelopeV2, source byte, ciphertext, plaintext callback, arbitrary continuation or generic getter result.

Honest lookup boundary: pair-only lookup cannot coexist with both zero decrypt and zero secret-derived index material. Cycle 31 therefore requires the random opaque selector in addition to the exact pairs and permits one bounded internal authenticated open solely to compare the requested bundle. This is not a generic decrypt method or a trusted immutable V5 resolver for the Cycle 29 adapter. Source-specific AES-256-GCM vault contract

The source vault is a new contract, not an implementation claim derived from the older output-envelope material. It uses AES-256-GCM with a 32-byte externally supplied owner key, a CSPRNG 12-byte nonce unique per key version, a 16-byte tag, canonical versioned framing and first-writer-wins immutable ciphertext. The key provider is injected and returns a key only for the authenticated owner path and exact key version; database, WAL, backup, errors and witnesses contain no key, key URI or owner credential. Exact replay returns the original row identity, nonce and ciphertext internally without rewrite; key rotation is a separately revisioned expected-head compare and is not implemented by this checkpoint.

Canonical AAD contains only: the exact vault domain and schema version; random opaque bundle id; opaque owner-path discriminator; categorical state; AEAD suite and key version; nonce length; ciphertext schema/type; ciphertext length; and row revision. Owner id/scope, operation lineage, V4/V5 ids or hashes, source/excerpt/representation hashes, aggregate commitments, rosters, anchor material and every exact byte remain inside ciphertext. No hash, HMAC, prefix or reversible/guessable surrogate of secret material may appear in AAD, a column, index, constraint, log, outbox, temporary file or backup manifest.

One authority database and a source-only key boundary: bundle records, signed source heads and the current pointer are separate exact tables in one SQLite database so record insert, head append and pointer CAS share one BEGIN IMMEDIATE transaction. Separate bundle/head databases are forbidden. The source-only key provider resolves exactly (opaque owner path, key version) to 32 bytes; existing graph key placeholders and generic stores are not compatible. Key URI, provider identity, credentials and provider failures never enter AAD, storage, witnesses or public errors. Rotation, rewrap and purge remain absent.

The exact key-provider protocol is open_aes256gcm_key(*, owner_path_authority: object, owner_path_discriminator: str, key_version: str) -> AbstractContextManager[bytearray]. The authority object is authenticated by the provider and never serialized; the discriminator alone is not authentication. The context yields exactly 32 mutable bytes for the exact historical version and clears them on exit; the store rejects a plain bytes, wrong length, fallback version or provider diagnostic. The store still disclaims physical erasure of immutable copies made inside the interpreter or cryptography library.

Bundle plaintext is the strict UTF-8 compact JSON emitted from the revalidated 31A model in declared field order with Pydantic JSON-mode byte encoding; parsing is bounded, duplicate-key rejecting, strict, and must round-trip to byte-identical canonical encoding. Plaintext is at most 67,108,864 bytes. AAD is the exact source-AEAD domain followed by compact sorted-key UTF-8 JSON for the 31A allowlist and no other key; integers are exact JSON integers and strings are NFC-agnostic byte-exact ASCII under their frozen regexes. AES-256-GCM receives one 12-byte CSPRNG nonce and returns ciphertext concatenated with the 16-byte tag; ciphertext length is exactly plaintext length plus 16 and at most 67,108,880. No alternate framing, detached tag, compression, padding, fallback suite or parser exists.

Exact replay under current authority: replay performs no rewrite and preserves the original nonce and ciphertext, but succeeds only when the caller supplies the current expected head and exact row revision. A stale historical head rejects even when it originally admitted the immutable row. No secret-derived index exists, so the store makes no claim that a semantically identical bundle cannot be sealed under a separately minted selector.

The database is single-owner and contains exactly four tables and no view or trigger: a singleton schema table; encrypted bundles keyed only by selector; signed source heads keyed by head hash with unique epoch; and one registry current pointer with a foreign key to the head table. The bundle columns are exactly selector, owner-path discriminator, categorical state sealed, AEAD suite, key version, nonce length, nonce, ciphertext schema owner_private_encrypted_source_bundle_v1_json, ciphertext type application/json, ciphertext length, immutable row revision one and ciphertext. Checks bind categorical/schema/type/suite/revision/nonce/cipher lengths; the only secondary uniqueness is (owner_path_discriminator,key_version,nonce). Head columns are head hash, registry id, owner-path discriminator, epoch, predecessor hash, issuance time and canonical document JSON. The current columns are registry id, owner-path discriminator and head hash. No owner id/scope, receipt pair, bundle semantic id/hash, operation lineage, commitment, blind index, log, outbox or floor value is stored.

The path is nonempty, durable and outside symlinked parents; the dedicated parent is mode 0700 and the non-hardlinked database plus live sidecars are mode 0600. Page size is fixed at 4096, max_page_count=1048576 caps the database at 4 GiB, and every reopen audits exact table/column/PK/FK/UNIQUE/CHECK/index SQL plus absence of extras before authority use. Selector collision checks cover live pending handles, every stored row and every active snapshot member. Nonce collision retry is bounded at eight and the database uniqueness constraint is the final backstop.

First-byte and last-byte rules

  • First durable byte: no secret or secret-derived byte may reach SQLite, a journal, WAL, shared-memory file, temp file, exception, diagnostic or backup before the complete canonical bundle has been validated, encrypted and reduced to the frozen plaintext-column allowlist. The first permitted durable content-bearing byte is randomized authenticated ciphertext inserted inside the same BEGIN IMMEDIATE transaction that appends its opaque source-head successor and advances the exact current pointer.
  • First plaintext byte on resolution: plaintext may appear only after owner-path authorization, selector syntax, expected head/revision, freshness and bounded ciphertext-length checks pass.   • Last plaintext byte: the store destroys all mutable plaintext buffers and references before returning or raising. No naked str, bytes, model, generator, memoryview, traceback local, callback capture or cache survives the frame. Python cannot prove physical zeroization of immutable interpreter copies, so tests prove reachability/API/log closure and the residual in-process memory limitation is explicit rather than claiming cryptographic erasure.

External floor and rollback limit: rollback resistance exists only relative to a trusted floor hash configured outside the source database and its backups. Rolling the database and its colocated floor configuration or key-provider state back together is not detected. Cycle 31 provides no transparency log, remote monotonic counter, hardware root, cross-device quorum or automatic re-anchoring. Backup/restore is quarantined until an external-floor restore ceremony is specified and tested; a local backup must never silently become its own trusted floor.
Recent whole-state rollback remains detectable only with external current expectations. The signed chain detects history below the external floor, missing/forked/orphaned rows and pointer rollback while descendants remain. A complete restore to a still-fresh signed ancestor above the floor is not distinguishable from current state when the caller's expected head and every external authority are rolled back with it. Tests must preserve this limitation rather than claiming universal rollback detection. Structural audit applies to every retained ancestor, while future-time and freshness requirements apply only to the current head; otherwise an honest chain would expire merely because its ancestors age.

Both NFKC stages use the Unicode 16.0.0 UAX #15 attributed-scalar algorithm: recursively apply compatibility decomposition (including algorithmic Hangul), retain each emitted scalar’s ordered original half-open UTF-8 span set, perform stable canonical combining-class reorder, then canonical composition with the UAX blocking and Hangul rules while unioning contributor spans. Casefold/map expansions inherit their input span set; composition unions, reorder preserves, and removal drops contributor sets. The produced string must equal the locked runtime’s whole-string transform at each stage or offset-map failure rejects. Per-codepoint normalize(), prefix-quadratic normalization and covering a removed gap as matched provenance are forbidden.
  5. Token provenance is an ordered, sorted, coalesced tuple of disjoint half-open spans relative to the decoded leaf re-encoded as strict UTF-8; source provenance is relative to exact committed source bytes. Tokens are maximal Unicode category L* or N* runs and carry the union of contributing scalar spans. Unmapped C0/C1 controls, NUL, surrogates, noncharacters FDD0..FDEF or any scalar ending FFFE/FFFF, invalid UTF-8, non-monotone spans, or empty aggregate normalization reject. CR and LF are mapped individually to spaces; whitespace runs are not collapsed. Unicode version, table hash, exhaustive mapping/removal tables and attributed-normalizer algorithm identity are checker material.
  6. Bounds are policy material: at most 1,000,000 output bytes, eight sources, 32,000 bytes/source, 256 content leaves, value depth 32, 200,000 output tokens, 256,000 aggregate source tokens including every duplicate ordinal, 100,000 canonical match rows, 25,000,000 candidate pairs, and 1,000,000 canonical ledger bytes. Candidate pairs are computed before matching as sum(content_leaf_token_count × source_token_count) across every leaf and every ordinal; boundaries are absent and duplicates count. Exceeding any bound raises one fixed content-free rejection with no partial result.

7. Rejected alternatives and explicit non-goals

Rejected: amend or mutate v1

V1 precommits no successor key and denies every sink. Adding PASS, attaching an external activation, or interpreting v1 through v2 rewrites signed meaning. Only new capability-v2/receipt-v5 authority can enter this lane.

Rejected: generic optional fields

Generic readers, recovery, hashes, deposits, flywheel, graph, and telemetry remain leak paths even if a checkpoint accepts optional taint. Guards resolve durable authority.

Rejected: hash-only compliance

A caller output hash, PASS boolean, paraphrase score, semantic similarity, or first-match scan cannot authorize a sink.

Rejected: tags or shared plaintext

personal_reading, owner filename hashes, privileged tags, shared engagement roots, and per-owner paths without content encryption are not sufficient owner-private storage.

Out of scope

No production transport/admission, provider-response recovery API, public/share/export, marketplace, team ACL, cross-owner merge, or legal-clearance claim. These remain denied or F/later work.

Movability

Capability/policy, extractor/normalizer/checker, storage envelope, sink receipts, and graph projection have separate identities. Later checkers, key rotation, or shared ACLs cannot silently alter them.
