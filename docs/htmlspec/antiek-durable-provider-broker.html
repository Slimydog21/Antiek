Antiek Durable Provider Broker

Status: Proposed execution master spec. No provider is qualified by this document.

Problem

Direct model APIs commonly return their durable operation identity only after accepting a billable request. If that response is lost, Antiek cannot distinguish charged from not sent. Provider idempotency prevents duplicate work but is insufficient unless the provider also supports authoritative lookup and not-found by the same caller key.

Boundary decision

Create an Antiek-owned broker as the qualified provider boundary. The broker durably records Antiek's idempotency identity and maximum authorization before upstream transport, owns the upstream ambiguity risk, and exposes exact reconciliation by the original key. The research gateway remains unchanged and continues to treat unknown as fully held.

  • The broker is not a pass-through HTTP proxy.
  • The broker never trusts client-supplied provider outcome or cost.
  • The broker cannot increase the approved ceiling or switch provider/model after authorization.
  • The broker's qualified charge is bounded by the authorization it accepted, even if its upstream cost is higher.

Durable state machine

  1. authorized: exact owner, operation digest, provider route, maximum cents, expiry, and idempotency key committed; no upstream boundary crossed.
  2. dispatch_possible: committed before the one upstream call. This state can never return authoritative not-found.
  3. upstream_bound: provider operation identity and accepted timestamp durably recorded.
  4. unknown: upstream outcome cannot yet be proven; full client authorization remains reserved.
  5. charged: terminal signed evidence includes exact client charge cents, upstream evidence digest, output digest, and completion identity.
  6. not_found: terminal only from an unexpired authorized record with a database-proven absence of the upstream-send marker.

Every transition is conditional, append-audited, idempotent, and bound to one canonical operation digest. Terminal rows are immutable.

API contract

Create

POST /v1/provider-operations requires a provider-authenticated caller, deterministic idempotency key, canonical operation digest, exact qualified route, bounded usage, maximum charge cents, and signed Antiek authorization. Replaying identical bytes returns the same operation; changed bytes return conflict.

Lookup

GET /v1/provider-operations/by-idempotency/{key} returns one signed redacted state and exact charge evidence. Create and lookup serialize on the same tenant/key lock. Missing is authoritative only after acquiring that lock and a primary-database transaction proves no row ever existed for that tenant/key; access failures, lock timeout, replica lag, integrity failure, and timeout are unknown, never not-found.

Output

Generated content is fetched separately through an expiring owner-scoped artifact reference. Reconciliation responses never include prompts, credentials, raw provider errors, or content.

One-send transport

  1. Acquire a per-operation process and database lease.
  2. Re-read authorization and route qualification from the primary database.
  3. Commit dispatch_possible and an immutable attempt identity.
  4. Call upstream exactly once with SDK retries disabled and a provider idempotency token where supported.
  5. Persist provider identity and evidence before publishing completion.
  6. On any exception after the send marker, retain unknown. Recovery may replay the byte-identical upstream create only when the qualified provider durably enforces the same idempotency token and returns the original operation identity; otherwise the route is ineligible. No generic worker may alter or independently retry the request.

Charge policy

The broker accepts a maximum client charge before dispatch. Terminal client charge is the lesser of that authorization and the deterministic price function over provider evidence. Upstream overage is broker loss, not a retroactive user charge. Pricing snapshots are signed, versioned, currency-pinned, and expire. Zero, malformed, missing, or contradictory usage remains unknown until operator-reviewed recovery.

Security and tenancy

  • Mutual service authentication; tenant derives from credentials, never request body.
  • Per-tenant uniqueness on idempotency key and operation digest.
  • Envelope-encrypted upstream credentials with provider- and environment-scoped access.
  • Outbound endpoint allowlist and DNS/TLS pinning policy; no request-selected URL.
  • Signed reconciliation receipts bind issuer, audience, tenant, idempotency key, operation digest, provider route, authorization cents/currency, pricing snapshot/version, state, charge evidence digest, issued/not-before/expiry times, nonce, key ID, algorithm, and rotation overlap.
  • Redacted structured logs; prompts, outputs, secrets, and raw headers excluded.
  • Rate, concurrency, and maximum-authorization limits enforced before durable acceptance.

Execution sprints

  1. BRK-01: Protocol and canonicalization. Typed request/receipt schemas, canonical digests, signature envelope, enum-closed parsing, and golden vectors.
  2. BRK-02: Primary ledger. Transactional schema, state transitions, idempotent commands, tenant/key serialization shared by create and lookup, primary-only authoritative lookup, migrations, and integrity verifier.
  3. BRK-03: Worker lease. Per-operation flock/database lease, dispatch marker, cancellation-safe release, crash recovery, and no-resend invariant.
  4. BRK-04: First upstream adapter. One exact provider/model/region/currency/pricing route with fixed endpoint, bounded request, automatic retries disabled, provider-enforced idempotent replay for ambiguous creates, evidence parser, and no generic recovery claims.
  5. BRK-05: Signed reconciliation API. Tenant auth, exact-key lookup, terminal evidence, unknown behavior, key rotation, replay protection, and redaction.
  6. BRK-06: Antiek resolver composition. Verify broker qualification, signatures, pricing snapshot, and route identity before exposing Cycle 98 capability.
  7. BRK-07: Fault campaign. Kill process at every checkpoint and socket boundary; corrupt, delay, duplicate, reorder, and substitute every identity and evidence field.
  8. BRK-08: Shadow rollout. Zero-cost fixtures, then broker-funded capped canary, manual reconciliation comparison, kill switch, and reviewed qualification expiry.

Qualification gate

No route becomes qualified until every sprint is merged, a live sandbox fault campaign proves deterministic recovery, signed evidence independently recomputes charge, security review has zero unwaived real findings, and the machine-readable qualification has five passing dimensions with a short expiry. A broker deployment alone is not qualification.
