SPR-01 · Truthful model evidence

Owner: isolated builder · Wave 1 · 7 milestones · status: executable

Parent context and goal

Current Settings assigns hand-authored task-tier affinities, exposes them as numeric quality, and names a recommended tier. Pricing and readiness are real facts, but cannot validate a quality ordering.

Remove fabricated authority while preserving useful operational evidence, then extract a production component whose Storybook states are the visual-test source of truth.

Technical milestones

  1. Delete static affinities and define nullable benchmark evidence plus operational eligibility.
  2. Require a current comparable cohort of at least two operationally eligible measured candidates before emitting a measured pick.
  3. Expose bounded recommendation status and benchmark provenance/coverage through the existing Settings API.
  4. Update TypeScript contracts and extract ModelEvidenceInstrument from the Settings monolith.
  5. Implement the sunline rail, truthful null states, keyboard semantics, narrow layout, dark theme, and reduced motion.
  6. Add backend/API/UI tests for missing, partial, complete, unavailable, over-budget, unknown-budget, stale, malformed, and wrong-route evidence.
  7. Add production-component Storybook stories and blocking LostPixel baselines; run all gates.

Five-values operating manual

Intellectual honesty. Assert that absent and partial reports return null recommendation and null scores; never preserve a legacy number merely to keep snapshots green.
Fairness. A route with one measured score must not silently outrank ready unmeasured routes. Tests must prove that a comparison needs at least two eligible members from the same cohort.
Rigor. Bind score attachment to task, exact provider/model route, schema, timestamp freshness, finite score, and positive samples; add negative tests for each boundary.
Diligence. Read and reuse the landed report validator, pricing projection, provider registry, Settings tokens, and Cycle 593 visual gate before adding code.
Defensibility. The UI must render why judgment is withheld—coverage, generated date, sample count, readiness, and budget posture—so the result can be reconstructed without chat context.
