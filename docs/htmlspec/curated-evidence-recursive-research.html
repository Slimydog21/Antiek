Cycle 68: Curated Evidence Research

Turn two to six exact passages from one immutable evidence briefing into one cohesive recursive investigation without flattening provenance into prompt prose.

Spec lineage

Parents: Cycle 67 offline evidence briefing and Cycle 60 structured citation research.

    Outcome

    The reading rail lets the operator curate an ordered set of two to six briefing citations. One command opens ChaseThread with the exact passages and an editable question; opening performs no network request. Explicit launch posts one derived_sources array. The server reopens the owner-scoped immutable revision once, verifies the complete set before any event, binds canonical context to its ordered excerpts, and persists every source as typed provenance.

    Contract

    Additive API

    Keep legacy derived_source unchanged. Add optional ordered derived_sources. Neither means ordinary research; both is invalid; the collection must contain 2–6 members.

    One revision

    Every member must share asset, revision, content digest, and generation. Cross-document synthesis needs a later manifest contract and is rejected here.

    Exact order

    Selection order is semantic and survives request, verification, canonical context, event JSON, replay, and panel display. The server never sorts or merges passages.

    Bounded bytes

    Existing per-excerpt bounds remain. Canonical combined context is capped at 32 KiB UTF-8. Duplicate citation identity or chunk identity is rejected.

    Verification transaction

    1. Authenticate the owner only from middleware.
    2. Validate collection cardinality, uniqueness, common revision identity, and aggregate bytes.
    3. Open one read connection and verify owner access before citation-specific distinctions.
    4. Reopen and integrity-check the exact immutable revision and complete chunk index once.
    5. Resolve all requested chunks in one bounded query; compare citation ID, ordinal, text hash, and exact excerpt while restoring caller order.
    6. Only after every member passes emit investigation.start_requested, followed by lineage emission.

    The defensible guarantee is one database snapshot before any trajectory mutation, not ACID across DuckDB and the event filesystem.

    Canonical context

    For a curated set the server-owned representation is [Evidence i of N]\n<exact excerpt>, separated by two newlines. The request must supply exact equality; arbitrary prose stays in question. The typed array, never parsed context, remains provenance authority. Legacy singleton context continues to equal its exact excerpt.

    Reader workflow

    • Each briefing passage retains “Follow this” for singleton research and gains a checkbox for curated research.
    • Checkboxes are persistent across the current hydrated briefing, numbered by selection order, keyboard operable, and capped at six.
    • A compact rail command reports the selection count and is enabled only at two selections.
    • The command opens one ChaseThread carrying exact passage/provenance pairs; selection alone never launches or spends.
    • ChaseThread renders the ordered evidence, freezes the launch payload while pending, and performs one POST only on explicit confirmation.
    • Changing revision or briefing identity clears stale selection. A failed launch retains evidence for correction and retry.

    Persistence

    InvestigationStartRequestedPayload gains an ordered derived_sources tuple defaulting empty. Historical and legacy singleton events remain valid and unchanged; multi-source events set singular provenance null and persist the complete tuple. Consumers treat the tuple as authoritative when present and fall back to the singular field for history.

    Acceptance harness

    • Valid ordered 2- and 6-source launches persist exact order and canonical context.
    • Both fields, 0/1/7 members, duplicates, mixed asset/revision/hash/generation, and context mismatch fail before event emission.
    • Foreign owner and any missing, stale, or mismatched final member produce no start/spawn event.
    • Database row order cannot alter caller order; event JSON round-trips without loss.
    • Ordinary and legacy singleton launches remain compatible.
    • Reader add/remove/cap/reset and ChaseThread no-auto-launch/one-explicit-POST behavior have focused tests.
    • Schema codegen, backend tests, frontend tests, strict typing, production builds, HTML parse, hostile review, and HardenX pass.

    Rejected alternatives

    • One investigation per passage: destroys cohesive reasoning and shared lineage.
    • Client-only concatenation: prose cannot prove source authority.
    • Embedding extra citations beside one typed source: verifies only the first.
    • Separate per-member database opens: weakens snapshot consistency and all-or-nothing admission.
    • Mixed revisions: hides a future cross-asset manifest problem inside a narrow endpoint.
    • Fuzzy matching, whitespace normalization, sorting, or adjacent-chunk merging: changes operator-selected evidence.
    • Auto-launch on selection or panel open: turns curation into unapproved spend.
    • Malformed provenance fallback to ordinary research: silently discards the requested trust boundary.

    Out of scope

    Cross-revision evidence manifests, arbitrary DOM-range proof, automatic synthesis, model routing changes, multimedia generation, and budget-policy redesign.

    Five-values rigor

    Honesty: only reopened rows establish provenance. Fairness: owner scope is checked before detailed failures. Rigor: the complete ordered set verifies in one snapshot. Diligence: all failures precede mutation or spend. Defensibility: an additive bounded contract preserves singleton and ordinary launches.

    Harness hint

    Implement the pure collection invariants and batch verifier first, integrate them before event emission, regenerate types, then wire ordered reader selection and the explicit ChaseThread launch. Prove a failure in the final member emits zero events.
