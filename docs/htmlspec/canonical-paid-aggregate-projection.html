Cycle 109: Canonical Paid Aggregate Projection

Parent: Cycle 108 budgeted crash-safe twin dispatch. Outcome: one oversized canonical source can acquire one canonical advisory twin binding from its verified paid aggregate completion.

1. Product Truth

Segmentation is an execution detail. The user owns one source asset and receives one advisory twin information asset. Segment proposals are private intermediate reasoning: they are never canonical documents, grounded graph claims, search results, or independent twins.

2. Authorities

AuthorityRequired proof
Canonical source bytesExact account, asset, title, content class, source events and complete oversized body.
Segmentation registryCurrent deterministic manifest covers every source character exactly once.
Completion ledgerEvery ordered segment has trusted paid-v2 proof and one trusted paid-v2 aggregate binds their exact ordered completion set.
Canonical twin lifecycleOne immutable source revision, one job, one binding, one advisory body, one derived non-recursive twin.

3. Distinct Provenance

The importer MUST NOT manufacture a TwinGenerationReceipt from an aggregate receipt. Canonical completion JSON is tagged as either direct_v1 or paid_aggregate_v2. The aggregate form retains the exact manifest, aggregate binding, proposal, signed receipt and canonical body commitments.

The existing SQLite schema remains pinned. Historical direct bindings are interpreted as direct_v1; new aggregate bindings carry an explicit kind inside immutable canonical completion JSON.

4. Import Protocol

  1. Reverify complete source bytes and derive the exact SourceRevision.
  2. Reverify the manifest and current segmentation registry.
  3. Read the completion ledger through an export method that rechecks schema, all paid segment receipts, the paid aggregate receipt, ordered hashes, body and proposal.
  4. Require account and asset equality, then rederive the segmentation parent identity from the canonical revision's title, class, events and body commitments. The account-scoped segmentation parent hash and canonical receipt-compatible source hash remain distinct, explicitly bound identities.
  5. Register or exact-replay the oversized source in the canonical lifecycle.
  6. Inside one canonical-ledger write transaction, bind the aggregate export to the existing deterministic job and twin identities, persist the canonical advisory body, transition the source to ready and append one hash-chained completion event.
  7. Re-read and verify both authorities before returning success. Any substitution fails closed.

5. Replay, Crash, and Concurrency

  • Crash before canonical commit leaves the source pending and no binding/event.
  • Exact replay returns the same binding and performs no provider work or spend.
  • Concurrent exact imports converge on one job, binding, twin and event.
  • Changed source, manifest, segment set, aggregate proposal, receipt, body, account or asset conflicts.
  • Completion-ledger unavailability or corruption cannot be replaced by caller claims.

6. Integrity

Canonical integrity verification accepts oversized source commitments, detects completion kind, and independently re-derives identity, proposal hash, receipt claims, manifest/source commitments, canonical advisory body, completion digest and event lifecycle. Historical direct bindings retain their existing verifier.

7. Acceptance

  1. A complete paid aggregate imports one canonical parent binding and renders HTML.
  2. Pending or legacy/unpaid aggregate state refuses.
  3. Exact replay after key rotation succeeds only while historical public-key trust remains configured.
  4. Crash and concurrent imports preserve one binding/event.
  5. Offline mutation of kind, manifest, proposal, receipt, body or digest is detected.
  6. The derived twin remains non-twinnable.
  7. No segment proposal is inserted into the canonical lifecycle or graph.
  8. Coupled Cycle104-108 tests, Ruff, HTML parse and HardenX pass; type blockers are reported honestly.

8. Non-Goals

No provider call, reservation, settlement, signing, retry, API/UI, production corpus mutation, grounded claim promotion, merge, deployment or live spend. Graph document insertion and search indexing require a later same-row/outbox authority if they cannot be made atomic with the canonical graph store; this cycle does not claim them from a separate SQLite commit.

9. Next

Mount the canonical parent binding into the graph document write boundary through a durable same-store declaration/outbox, then expose the one HTML twin in the reader while keeping all advisory statements visibly ungrounded until evidence-backed promotion.
