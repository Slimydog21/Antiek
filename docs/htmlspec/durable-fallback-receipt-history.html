Cycle 78: Durable Paid Fallback Receipt History

Status: executable. Parent: Cycle 77 operator-visible fallback plan.

Outcome

Persist one immutable, owner-bound fallback-chain manifest before the first paid hold can exist, then project recent chain history by joining every declared route to its exact deterministic hold identity. The projection is read-only evidence, never execution authority.

Manifest authority

  • The gateway preflights every route before registration. Registration records one to sixteen unique ordered routes in the same transaction as an immutable command receipt.
  • The chain identity is stable for one run and logical operation. Reusing it with a changed operation, route order, provider, model, seam, operation, projection digest, rate snapshot, projected maximum, reservation key, or provider idempotency key is an idempotency conflict.
  • The manifest stores digests and routing/accounting metadata only. It never stores prompts, operation payloads, provider evidence, credentials, endpoints, or API keys.
  • Each route declares the exact reservation identity that the existing gateway will use. Reads never infer fallback membership from timestamps or opaque hash similarity.

Durability and ordering

  • A crash after manifest commit and before reserve yields an honest unattempted chain. Replay uses the same manifest and may continue.
  • A crash after reserve is visible through the exact manifest-to-hold join. Existing hold recovery semantics remain authoritative.
  • Later attempts may exist only when all earlier attempts are authoritatively released. At most one attempt may be settled, and no later attempt may exist after settlement.
  • Concurrent equivalent registration converges. Concurrent changed registration conflicts before an additional provider send.
  • Manifest and route tables are immutable and non-deletable under the existing SQLite host-trust boundary. Reads recompute canonical manifests and validate every joined hold field.

Read model

Each route has exactly one state: unattempted, reserved_not_sent, dispatch_possible, unknown, released, or settled. A settled route exposes actual cents, resolution time, settlement evidence SHA-256, and settlement intent SHA-256, but never evidence JSON or command keys.

Each chain has one derived outcome: unattempted, in_progress, ambiguous, settled, or exhausted. Any malformed manifest, missing/extra route, mismatched hold, impossible order, duplicate settlement, or receipt conflict fails value-free as an integrity error.

History is owner-scoped, newest first, bounded to at most 50 rows, and keyset-paginated by immutable creation time plus chain identity. A cursor can select a position but cannot override the owner predicate.

Operator surface

  • GET /settings/fallback-receipts reads the authenticated request identity and never accepts an owner ID.
  • The Decision tree presents recent execution history separately from the advisory preview, including ordered route states, projected/actual cents, and truncated receipt digests.
  • Unknown, unavailable, empty, and integrity-conflict states remain distinct. Failure to load history does not disable model comparison or the advisory preview.
  • No button, approval token, retry control, hold identifier, provider idempotency key, raw evidence, or dispatch input is exposed.

Acceptance evidence

  • Fresh-schema and v7-to-v8 migration tests prove immutable tables, indexes, triggers, rollback on injected migration failure, and legacy ledger replay.
  • Gateway tests prove manifest-before-hold, primary settlement, released fallback settlement, exhaustion, ambiguity, crash at every manifest/reserve boundary, equivalent replay, changed-chain conflict, and concurrent convergence.
  • Ledger read tests refute cross-owner reads, malformed canonical JSON/hash, route cardinality/index corruption, hold substitution, field substitution, impossible ordering, duplicate settlement, and receipt-evidence mutation.
  • API and frontend tests prove value-free errors, bounded pagination, strict client validation, independent loading, accessible empty/error/history states, and no execution controls.
  • Adjacent gateway, ledger, Settings, composer projection, typecheck, build, Ruff, security, and hostile-review gates remain green.

Out of scope

No provider qualification, paid consumer mounting, approval, dispatch route, reconciliation action, retry, settlement mutation, evidence-body serving, invoice claim, refund accounting, prompt retention, merge, or deployment.

Five-values rigor

Truth comes from exact persisted identities, fairness keeps provider evidence private, rigor rejects impossible histories, diligence covers crash and migration boundaries, and defensibility keeps advisory planning separate from execution receipts.

Harness hint

Use separate storage/accounting, privacy/API, and frontend refuters. A reviewer must attempt to manufacture a plausible settled history from corrupted or cross-owner rows.
