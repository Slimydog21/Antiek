Cycle 28: One-shot investigation activation consumption

Status: executable specification. Base: Cycle 27 head 53bf62336c46461403c23939231af7e6ed8de809.

Outcome

An authenticated owner may consume one unexpired mia_ activation authorization exactly once. Consumption creates one immutable mlr_ launch reservation that fixes the complete approved integer-cent band, deterministic spend-run and session identities, exact prepared and authorization integrity, and current server-owned routing, model, configuration, pricing, and workload authority.

The launch reservation commits before a separate research-spend run is replayably created or reopened and read back with the exact binding and ceiling. The spend ledger's mandatory run_created or run_reopened audit row records that authority bootstrap; it is not a research execution event. The resulting receipt may become ready, but this cycle does not start research, construct or call a provider, create a task or thread, emit a research execution event, write graph state, debit money, or schedule background work.

Five load-bearing values

  1. One-shot authority: existence of the unique launch-reservation row is consumption. The immutable Cycle 27 authorization is never backpatched, so dual mutable states cannot disagree.
  2. Complete-band honesty: reserved cents equal the authorization's complete approved ceiling, never its quote, a partial caller amount, or a synthetic provider hold.
  3. Commit before effect: launch reservation commit and exact spend-run verification precede every event, graph, provider, scheduler, task, thread, or network seam.
  4. Recoverable cross-database boundary: a committed reservation with a missing spend run is permanently consumed but setup-incomplete. Exact replay creates or reopens only the fixed run; it never mints a second launch.
  5. Owner privacy and exact replay: owner scope participates in every lookup and uniqueness boundary. Foreign and missing resources are indistinguishable; exact retries return the historical reservation even after authorization expiry.

Domain contract

InvestigationLaunchReservation contains: opaque mlr_ identity; authorization and investigation identity; prepared and authorization integrity digests; exact source plan, intent, evidence, counts, route, tier, provider, model, dispatch, pricing, workload, quote, and approved-ceiling bindings; persisted consumption request digest; deterministic spend_run_id and session_id; reserved cents; reservation timestamp; state launch_reserved; and literal false/null execution authority fields. Canonical JSON and an integrity digest bind the complete record.

Request identity is (owner_digest, authorization_id, idempotency_key). The first exact request returns 201; replay returns the byte-equivalent historical reservation with 200. Reusing a key for another authorization, or using another key after consumption, conflicts.

Launch, spend-run, and session identities are deterministic SHA-256 derivations over domain labels, owner digest, authorization ID, authorization integrity digest, and prepared integrity digest. They are generated before insert and verified on every read; replay-time request data cannot alter them.

Current authority revalidation

The server resolves a fresh quote outside the SQLite write transaction. First consumption requires the fresh quote's route policy, tier, provider, model, dispatch-config digest, pricing source and digest, workload digest, and quoted ceiling to exactly equal the authorization. Quote identity and timestamps may refresh, but the quote must itself pass integrity and freshness validation. Any semantic drift rejects consumption and requires a new authorization.

Under BEGIN IMMEDIATE, the ledger re-reads and fully validates the authorization and prepared investigation, proves the preflight rows are unchanged, captures one UTC reservation time, and rejects when reserved_at >= authorization.expires_at. Existing exact reservations replay before current expiry or quote checks.

Storage and migration

Migrate the private research-plan SQLite ledger transactionally from schema v4 to v5. Add one immutable multimedia_investigation_launch_reservations table with explicit scalar bindings, canonical JSON, integrity digest, owner-scoped key uniqueness, owner-scoped authorization uniqueness, owner-scoped investigation uniqueness, globally unique deterministic spend-run and session identities, and foreign keys to the exact authorization and prepared investigation.

Reads decode the exact dataclass shape, require canonical JSON, recompute request, deterministic identity, manifest, and reservation integrity digests, compare every scalar column, and re-open the referenced authorization and prepared row. UPDATE and DELETE are outside the API and treated as tamper if observed.

Spend-run bootstrap

After reservation commit, the route derives one RunBinding exclusively from the stored reservation, using launch_manifest_digest as its plan digest, and calls ResearchSpendLedger.create_or_reopen_run with a deterministic command key and ceiling exactly equal to reserved_cents. It then reads the run and verifies the complete binding, hard-ceiling USD mode, exact ceiling, zero authorized spend, zero observed provider spend, zero holds, active status, and no breach.

The launch reservation is not a synthetic research_spend_holds row. Provider-operation holds remain the exclusive responsibility of ResearchProviderGateway. A missing or temporarily unavailable spend ledger returns a private value-free 503; replay resumes setup for the same reservation. A conflicting or non-pristine existing run returns 409 and no execution authority.

Private API

  • POST /multimedia/investigations/{investigation_id}/activation-consumptions: strict body with authorization_id and 16..128 ASCII idempotency key. Owner is derived only from authentication.
  • GET /multimedia/investigations/{investigation_id}/launch-reservation: owner-private immutable receipt read. Readiness is derived by exact spend-run verification, not persisted as mutable plan-ledger state.

Success and failure responses use Cache-Control: private, no-store. Owner digests, internal idempotency keys, and spend-ledger command keys are never returned. Missing and foreign resources return the same 404 investigation is unavailable; validation is 422; expiry, drift, replay mismatch, duplicate consumption, or integrity conflict is 409; unavailable storage, resolver, or spend bootstrap is value-free 500/503.

Acceptance evidence

  • Domain tests prove first consumption, exact replay after expiry, changed-key conflict, owner isolation, complete-band equality, deterministic identities, inclusive expiry, semantic quote drift rejection, refreshed quote metadata acceptance, prepared/authorization drift rejection, transaction rollback, concurrent one-winner behavior, v4-to-v5 migration, canonical and scalar tamper detection, and exact historical reads.
  • Spend-bootstrap tests prove exact run binding and ceiling, replay after post-commit bootstrap failure, missing-run recovery, conflicting/non-pristine run refusal, and that no provider hold is created.
  • API tests prove private status/error taxonomy, strict inputs, owner privacy, response projection, and unavailable resolver/spend-ledger behavior.
  • Side-effect spies prove no provider construction/call, network access, event emission, graph write, debit, task/thread creation, scheduler call, or background launch occurs.
  • Focused and full multimedia tests, Ruff, compileall, HTML parsing, HardenX strict, independent review, and frontend typecheck/build are green before publication.

Explicit non-goals and next boundary

Cycle 28 stops at a verified ready receipt. Cycle 29 may add an idempotent launch executor that transitions the existing spend run through gateway-controlled per-operation holds and durable downstream receipts. It must prove recovery at every event, graph, task, and provider boundary. No execution behavior may be smuggled into Cycle 28.
