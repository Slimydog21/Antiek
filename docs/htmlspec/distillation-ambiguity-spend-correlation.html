Distillation ambiguity spend correlation

Status: Cycle 93 execution spec. Parent: Cycle 92 approved distillation spend gateway, PR #2732 at 3a92d652a.

Problem

The command journal can say a distillation is ambiguous while knowing only its request identity. The paid gateway separately retains an exact provider hold, but the current handler discards ProviderOutcomeUnknown.hold_id. A crash-derived ambiguous command may therefore be shown to an operator without proof of which run, fallback manifest, or held exposure it controls. No reconciliation command is defensible until those authorities are durably joined.

Invariant

Before a provider send marker, provider request, or provider reconciliation lookup can occur, the command journal must durably bind the exact request to the approved spend run, fallback chain, manifest digest, and paid hold. The provider gateway may proceed only after an idempotent observer confirms that binding. Any identity drift, observer failure, absent correlation, or substituted unknown hold fails closed.

State contract

  1. An approved ticket carries run_id, chain_id, and lowercase SHA-256 manifest digest in addition to request, prompt, approval, and disclosed terms.
  2. The gateway reserves or reloads the exact hold, then invokes on_hold_authorized(fallback_index, hold) before changing a reserved hold to dispatch_possible and before reconciling a previously sent hold.
  3. The observer atomically transitions the command from reserved to sending while storing exact spend and hold identity. Ordered fallback advancement persists each index/hold pair in an append-only lineage; skipped indices and same-index substitution conflict.
  4. Correlated sending replay returns through the same qualified gateway. Already released historical routes must replay exactly before the current route may be sent or reconciled.
  5. An unknown provider exception must name the same current hold before the command can become ambiguous.
  6. A process death before observer success leaves the command reserved. A process death after observer success leaves a correlated sending command whose provider state is reconciled authoritatively; an unavailable recovered output becomes ambiguous without another send.
  7. Legacy rows migrate with nullable correlation fields. They remain readable but cannot be represented as safely reconcilable.

Failure semantics

  • Observer failure occurs before any new provider send. A newly reserved hold remains provably unsent.
  • No local command, timeout, operator assertion, or abandonment releases a correlated ambiguous hold.
  • If every approved route returns authoritative ProviderNotSent evidence and every hold is released, distillation completes with an explicit local zero-token “no provider accepted” result; it is not mislabeled as unknown and contains no provider-generated claims.
  • Capability drift before first correlation is a hard trajectory error. Capability drift during correlated recovery becomes ambiguous and retains the current hold identity.
  • No provider is called by this sprint and no generic adapter is declared qualified.
  • Completed and delivered commands retain immutable correlation provenance.

Acceptance evidence

  • Fresh schema and existing-database migration tests.
  • Observer ordering test proves callback before send and before reconciliation.
  • Observer failure proves zero provider sends.
  • Changed run, chain, manifest, or hold conflicts without mutation.
  • Unknown outcome persists the exact exception hold and rejects substitution.
  • Crash/reopen and concurrent duplicate execution converge on one correlation.
  • Ruff, strict mypy, focused tests, HTML parse, diff check, HardenX with zero REAL findings, and a different-lineage hostile review.

Explicit next sprint

After correlation is proven, add an authenticated owner-scoped read model and evidence-only reconciliation command. A reserved hold with no send marker may be released through ledger proof; a dispatched or unknown hold may change only from authoritative provider lookup evidence. “Abandon” may close UX work but must retain exposure indefinitely.
