Cycle 32 / Cycle 33

Bedrock S3 immutable-version publication

Publish the exact bounded JSONL as one checksum-verified, COMPLIANCE-retained S3 object version without claiming that an unversioned Bedrock URI selects it.

Status: executableProduction: refusedSettlement: refused

Spec lineage

Cycle 32 proved exact workload bytes and a conservative pre-dispatch maximum but treated the content-addressed S3 key as naming evidence only. Official AWS contracts establish that single-part PutObject supports conditional creation, full-object SHA-256, version IDs, and COMPLIANCE Object Lock, while HeadObject can reopen checksum, length, version, and retention. Bedrock CreateModelInvocationJob accepts only an unversioned s3Uri, not a version ID.

  • A future child must prove an independently controlled namespace policy that prevents every later version, delete marker, copy, restore, lifecycle, or replication substitution before claiming immutable Bedrock input.

Verdict

Prove immutable object-version publication; refuse immutable Bedrock selection. A locked version is durable evidence that exact bytes existed and remain protected. It does not prove that the locked version stays current or that Bedrock read it. Do not exhaust, settle, release, qualify, or production-enable Bedrock.

Five load-bearing values

  1. Exact bytes: reopen the Cycle 32 workload bound before any S3 call; one single-part body and one full-object SHA-256 only.
  2. Conditional publication: use IfNoneMatch="*"; never overwrite, multipart-upload, copy, or silently adopt mismatched state.
  3. Immutable version: require versioning enabled, Object Lock enabled, a non-null version ID, COMPLIANCE mode, and retention beyond the complete Bedrock timeout plus margin.
  4. Two heads: reopen the exact version and the current key with checksums enabled; both must identify the same exact object at verification time.
  5. Truthful scope: persist version_immutable=true, current_at_verification=true, and bedrock_version_selected=false as distinct facts.

Publication profile

Server-owned route

Bind general-purpose bucket, exact owner account, region, server-owned prefix, minimum retention margin, profile version, and namespace-policy digest. Reject directory-bucket forms, caller metadata, ACLs, and arbitrary keys.

Derived key

Derive the key from the prefix, workload SHA-256 as a full segment, and fixed manifest.jsonl. The receipt URI must exactly equal that bucket and key.

Request

PutObject receives exact bytes, expected owner, JSON content type, ChecksumAlgorithm=SHA256, exact Base64 ChecksumSHA256, IfNoneMatch=*, ObjectLockMode=COMPLIANCE, and exact retention.

Receipt

Canonical redacted JSON binds workload-bound digest, byte digest and length, profile digest, bucket/key/URI, owner digest, checksum, version ID, lock mode, retention, and the three truthful scope booleans.

Exact replay and concurrent publishers converge only when both observe the same complete version authority. Workload bytes remain caller-held until receipt verification; prompts never enter the spend ledger or receipt.

Adapter binding

  • Add canonical publication receipt JSON and digest to the bound request identity; bind them into client token, submission ID, hold operation digest, and adapter contract version.
  • Persist the redacted receipt in an existing immutable hold/submission authority surface without persisting JSONL.
  • Before every initial or recovery Bedrock create call, reopen the receipt and HEAD both its version and current key. Any drift prevents the call.
  • The adapter remains explicitly injected test authority. No default registry, route, factory, scheduler, or production credential source gains it.
  • Pre-create HEAD narrows accidental drift but does not close the HEAD-to-Bedrock-read race. Only a separately qualified namespace invariant can do so.

  • BedrockS3VersionPublicationReceipt: strict canonical immutable-version evidence with explicit refusal booleans.

Acceptance criteria

  1. Exact workload/profile/time produce deterministic request terms; successful publish returns one receipt whose digest changes for any workload, route, version, retention, or policy change.
  2. PUT uses exact body and all required owner/checksum/conditional/COMPLIANCE fields; no multipart, copy, delete, ACL, metadata, or fallback operation exists.
  3. Success, lost response plus exact adoption, 412 exact adoption, concurrent exact publication, and restart verification converge to one receipt without a second accepted version.
  4. 409, different existing bytes, absent/wrong checksum, composite checksum, wrong length, null version, GOVERNANCE/no lock, short retention, wrong owner, disabled/suspended versioning, disabled lock, malformed timestamps, and missing permissions fail closed.
  5. A locked old version plus a different current version is explicitly rejected and proves Object Lock alone is insufficient.
  6. Receipt/workload/profile/bucket/key/URI/version/checksum/retention/policy/model/region/token/submission substitution fails before Bedrock call or spend mutation.
  7. No prompt or workload body is persisted in spend, event, graph, task, receipt, log, or exception evidence.
  8. Cycle 30-32 identity, billing refusal, and workload tests remain green; no settlement, release, exhaustion, observed-spend, qualification, production, result ingestion, event, graph, task, scheduler, worker, route, or UI mutation is added.

Official evidence

  • S3 PutObject API: conditional create, checksums, version ID, and Object Lock request/response fields.
  • S3 HeadObject API: checksum, version, length, and retention evidence.
  • S3 conditional writes: If-None-Match applies to the current version.
  • Bedrock CreateModelInvocationJob API: input exposes s3Uri without version selection.

Rejected alternatives

  • Object Lock alone proves Bedrock input: rejected because a newer version can become current.
  • HEAD current once is enough: rejected because it is an observation, not a namespace invariant.
  • ETag proves bytes: rejected; use explicit full-object SHA-256 and exact length.
  • 412 means our prior PUT won: rejected; only complete exact HEAD evidence permits adoption.
  • Persist workload bytes in spend: rejected for prompt privacy and authority separation.
