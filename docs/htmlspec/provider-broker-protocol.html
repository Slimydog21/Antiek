BRK-01: Provider broker protocol and canonical authority

Status: Executed protocol foundation. It qualifies no provider and sends no request.

Spec lineage

Parent: Antiek Durable Provider Broker.

    Outcome

    Antiek has a transport-free, enum-closed protocol for one bounded provider authorization and its signed reconciliation receipt. Canonical ASCII JSON and SHA-256 digests make field substitution independently detectable before later ledger, worker, API, or adapter work begins.

    Five-values rigor

    ValueBRK-01 obligation
    HonestyProtocol validity is not provider qualification, signature verification, durable persistence, or proof of execution.
    FairnessA receipt cannot increase the user-approved cent ceiling; upstream overage cannot become retroactive user debt.
    RigorExact field sets, closed enums, canonical timestamps, bounded integers, canonical route ordering, and golden bytes fail closed.
    DiligenceEvery receipt binds tenant, idempotency key, operation, route, authorization, ceiling, currency, pricing snapshot, evidence, validity, and signing identity.
    DefensibilityGolden vectors and substitution tests let independent implementations recompute authority without trusting Python object order.

    Executable contract

    1. BrokerAuthorization binds one tenant/key and operation digest to one HTTPS-origin route, exact billing units and positive usage bounds, USD cent ceiling, pricing snapshot, and validity interval no longer than 24 hours.
    2. BrokerReceipt uses only authorized, dispatch_possible, upstream_bound, unknown, charged, or not_found.
    3. Pre-upstream states contain no evidence or output. upstream_bound requires identity evidence and no output. unknown cannot claim output. charged requires evidence and output and cannot exceed authority. not_found requires evidence, zero charge, and no output.
    4. assert_receipt_authority exact-matches all authorization identity and pricing fields and requires the receipt validity window to remain inside authorization validity.
    5. Ed25519-v1 signatures are represented as canonical unpadded base64url encoding of exactly 64 bytes. Cryptographic key lookup and signature verification belong to BRK-05.

    Canonicalization

    Signing and digest bytes are ASCII JSON with lexicographically sorted keys, compact separators, escaped non-ASCII, no floats, and enum values serialized as closed strings. Route and authorization SHA-256 digests use those exact bytes. The checked-in vector fixture freezes authorization bytes, route digest, authorization digest, receipt signing bytes, and a structurally canonical signature.

    Rejected alternatives

    • Mutable or open-ended dictionaries: rejected because omitted, duplicated, or invented authority fields become ambiguous.
    • Unsigned route or pricing metadata: rejected because a valid receipt could be replayed against a different cost or provider boundary.
    • Floating-point currency: rejected because cross-runtime rounding is not canonical or defensible.
    • Receipt validity independent of authorization: rejected because the broker could extend delegated authority after approval.
    • Implementing transport now: rejected because no adapter has yet proved durable idempotency, lookup, pricing evidence, and crash recovery.
