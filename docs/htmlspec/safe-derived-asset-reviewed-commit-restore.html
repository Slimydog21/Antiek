Reviewed commit and restore

V18 commits only an owner-bound reviewed draft or restores an existing owned revision. HTTP commands contain opaque IDs and concurrency proofs, never content.

Invariants

  • The reviewed draft alone supplies create/revise title, kind, canonical HTML, sanitizer fields, and canonical ordered manifest.
  • Restore appends a revision with the selected revision's exact canonical fields and ordered members.
  • Revise/restore compare expected revision, SHA-256, and generation; pointer mutation uses UPDATE RETURNING and must affect exactly one row.
  • Asset, revision, members, receipt, outbox, current pointer, and timestamps share one explicit transaction under connect_write.
  • Every stage exposes a fault hook. Any fault or stale proof leaves no residue.
  • operation_id binds canonical command bytes to all result rows. Exact replay returns the receipt; command or stored-result drift fails closed.

API

POST /reviews/{review_id}/apply accepts operation_id plus expected_generation only for revise, because V17 reviews seal the parent revision and hash but not its generation. Create rejects a generation. POST /assets/{asset_id}/restore accepts operation ID, selected revision ID, and exact expected pointer proof. Both are authenticated owner-only, extra-forbid, and Cache-Control: no-store.

Rejected alternatives

  • Mutating source documents was rejected because source evidence is immutable.
  • Moving the pointer directly to an old revision was rejected because restore must preserve an append-only audit trail.
  • Using DuckDB rowcount for CAS was rejected because it is not a reliable match signal; UPDATE RETURNING is authoritative.

Out of scope

Outbox delivery, generic revision mutation APIs, source/projection writes, and multimedia bridge publication are later sprints.

Acceptance

Tests cover create, revise, restore, stale rollback, every fault stage, replay and drift, schema constraints, ownership, and unknown fields; focused pytest, Ruff, and bytecode compilation pass.
