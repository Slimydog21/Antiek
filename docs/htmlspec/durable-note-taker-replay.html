CYCLE 46

Durable recursive note-taker replay

Replace volatile event counters and fire-and-forget synthesis with deterministic windows, recoverable provider evidence, and byte-identical note delivery.

Spec lineage

Parent program: Antiek Infinite. Predecessors: transactional event outbox and durable knowledge consumers.

  • No child specs. This sprint is one atomic durability boundary.

Outcome

For every investigation, each non-overlapping group of N qualifying physical trajectory events produces at most one paid synthesis request and at most one byte identity for each resulting note.emerged event. Restarts may delay progress; they must not silently lose cadence, duplicate spend, or reinterpret stored provider output.

Five values

Precision

Window identity includes consumer version, investigation, threshold, and ordered qualifying event IDs.

Exhaustiveness

Tests interrupt before/after request commit, provider return, result commit, outbox append, and delivery receipt.

Craftsmanship

Use the existing DuckDB lock, event schema, physical reader, and write outbox. No parallel persistence dialect.

Honesty

An abandoned calling state is uncertain; without provider reconciliation it cannot be retried automatically.

Information maximization

Backfill historical qualifying windows once under consumer v2 so missed insights become durable knowledge.

Authoritative inputs

  • Read with iter_physical_events, never the logical merged reader.
  • Qualifying types: delivered distillations and passed/failed grounding checks.
  • Exclude note-taker-authored events defensively.
  • Reject conflicting physical event identities and incomplete JSONL tails; do not advance state.
  • Group from the beginning of the qualifying sequence into fixed, non-overlapping windows. Leave a suffix shorter than the configured threshold pending.

Schema V20

note_taker_windows(
  window_id PRIMARY KEY, consumer_version, investigation_id,
  threshold, ordinal, first_event_id, last_event_id,
  source_event_ids_json, source_digest,
  request_json, request_sha256, provider_idempotency_key,
  state CHECK IN ('prepared','calling','result_stored','materialized','completed','uncertain'),
  raw_result, raw_result_sha256, provider, model, policy_id,
  attempt_count, uncertainty_reason, created_at, updated_at,
  UNIQUE(consumer_version, investigation_id, threshold, ordinal),
  UNIQUE(consumer_version, investigation_id, source_digest)
)

Strict fingerprint validation is mandatory on every open. Partial or incompatible tables fail closed unless empty and safely repairable. Output events use the existing write_event_outbox; operation_id is note-taker-v2:<window_id>:<note-index>.

Determinism

  • window_id = sha256(canonical consumer/version/investigation/threshold/ordered event IDs).
  • Request JSON and digest are frozen at discovery. Context-pack telemetry is not allowed to mutate the prompt on replay.
  • note_id and event ID derive from window ID, stable parsed note index, normalized text, confidence, and validated source IDs.
  • emitted_at is chosen once while materializing and persisted inside outbox bytes.
  • Any reused identity with different bytes is corruption and fails closed.

Execution slices

  1. Add V20 schema, repair/fingerprint checks, and migration tests.
  2. Add a framework-neutral durable replay service with injected dispatcher and crash checkpoints.
  3. Replace the volatile handler with a thin async bridge that asks the service to catch up.
  4. Wire startup catch-up before live subscriptions where the API lifecycle permits.
  5. Add restart, duplicate-trigger, process-death, malformed-result, incomplete-tail, and outbox-race tests.

Acceptance

  • Three qualifying events before restart plus two after restart form exactly one threshold-five window.
  • Two concurrent catch-up callers cause one provider call.
  • Death before provider call leaves a retryable prepared request.
  • Death during/after an unreceipted provider call becomes uncertain and causes zero automatic calls.
  • Death after raw-result commit performs zero additional provider calls and emits deterministic notes.
  • Death after JSONL append but before receipt produces no duplicate line.
  • Sealed Parquet plus JSONL tail preserves chronological windows and refuses incomplete tails.
  • Existing note-taker behavior remains available through the handler API; broadcasts are best effort after durable delivery.

Rejected alternatives

  • Persist only a counter: cannot prove which events were synthesized or rebuild a prompt.
  • Retry provider errors naturally: duplicates spend when transport outcome is unknown.
  • Emit directly: duplicates or loses notes across append/receipt crashes.
  • Use logical trajectory: hides sealed-plus-tail ordering and physical corruption.
  • Random note IDs: makes stored-result replay non-idempotent.
  • Exactly-once marketing claim: impossible without provider idempotency/reconciliation; the honest contract is at-most-once automatic dispatch with explicit uncertainty.

Out of scope

Cross-document compression, remote multi-host leases, provider-specific reconciliation adapters, UI controls for uncertain windows, and semantic note deduplication belong to later cycles.

Harness hint

Implement schema and service together, then run a hostile reviewer against every transition and identity boundary. Do not publish while an untested external side effect exists.
