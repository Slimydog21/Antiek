Multi-Chapter Narration Run

Admit an ordered set of signed chapter TTS calls atomically, execute each paid call at most once, resume from durable child receipts, and publish one renderer-ready narration authority.

Authority Phases

PhaseBindingFailure behavior
PrepareOne canonical request per spoken chapter, with deterministic child revision, route, voice, speed, media shape, text, and grounding.No database or spend mutation.
Authorize setOrdered request digests, signed authorization IDs, and ceilings form one set digest and run ID.Missing, extra, reordered, or substituted authority fails before reservation.
AdmitEvery one-shot claim and full spend band plus the parent run receipt commit in one DuckDB transaction.Any invalid or unaffordable chapter rolls back the complete set.
ExecuteEach child uses the chapter TTS send marker, received-byte receipt, provider observation, and sealed child narration.Known received bytes resume locally; ambiguous sends never retry automatically.
AggregateOrdered child output hashes, durations, chapter IDs, script lines, and source chunks become one sealed narration.Incomplete or conflicting children cannot publish.

Invariants

Atomic admission is not atomic provider execution. Partial successful provider calls are expected after admission. The run resumes missing chapters from their independent receipts; it never rolls successful calls back or repeats ambiguous calls.
  • One through 64 spoken chapters; authorization and route maps exactly cover them.
  • Parent revision and chapter order determine bounded child revisions.
  • The parent MAC covers run identity, asset, revision, set digest, status, and aggregate artifact.
  • Aggregate timing comes from probed child narration bytes, not planner estimates.
  • Final publication is idempotent: an existing aggregate must reopen and match the parent authority.
  • No built-in provider client, credentials, HTTP route, or automatic reconciliation.
