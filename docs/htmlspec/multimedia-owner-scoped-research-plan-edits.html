Owner-scoped research plan edits

Cycle: 25. Base: Cycle 24 opaque owner-plan authority. Status: execution contract.

Outcome

An authenticated owner can manually shape a multimedia research plan as an ordered question tree. Every committed edit is owner-bound, exactly idempotent, version-CAS protected, and approval reopening. Editing remains a local planning operation: it cannot decompose automatically, project into the graph, launch research, emit events, call providers, or authorize spend.

Five values

ValueRequired consequence
TruthAn edit response reports only a historical mutation result and literal no-execution authority.
OwnershipPlan lookup, mutation receipt, and approval reopening bind the authenticated owner digest.
DeterminismAn exact mutation replay returns its original stored result even after later edits; changed input under the same key conflicts.
ControlExact version CAS rejects lost updates. Every real edit advances once and requires fresh approval.
Least authorityThe edit module imports or invokes no graph, event, investigation, provider, spend, embedding, network, or background-work collaborator.

Tree authority

  • Every node has a server-generated immutable mrpn_ plus 48-lowercase-hex ID. Clients reference existing IDs but never mint new IDs.
  • The root retains immutable source intent and evidence provenance and cannot be reworded, moved, or removed.
  • Sibling order is array order. IDs remain stable through question updates and moves.
  • Bounds: 256 nodes, depth 8 including root, 64 children per node, 64 operations per batch, 3-2000 characters per trimmed question, 128 KiB canonical plan and mutation response.
  • Node IDs are unique within a tree. Trees are acyclic, connected, rooted, and strictly shaped; unknown fields and malformed decoded types fail closed.

Edit contract

POST /multimedia/research-plans/{plan_id}/edits accepts a strict body with idempotency_key, expected_plan_version, and one to 64 ordered operations. The batch is all-or-nothing.

OperationRequired fields and semantics
add_childparent_node_id, required insertion position, and question. The server generates the child ID.
update_questionnode_id and question. Non-root only; unchanged normalized text is rejected.
move_subtreenode_id, new_parent_node_id, and post-removal destination position. Non-root; cycles and no-op moves are rejected.
remove_subtreenode_id. Non-root; removes the complete descendant subtree.

Cycle 25 deliberately excludes split, merge, full-tree replacement, budgets, depth policy, client-generated node IDs, and references to nodes created earlier in the same batch.

Transaction order

  1. Validate owner, opaque IDs, key syntax, strict body, operation count, and canonical request size.
  2. Inside BEGIN IMMEDIATE, check the owner-plan-key mutation receipt before current-version CAS.
  3. An exact receipt replay returns the stored historical response without mutating current state. Request drift conflicts.
  4. Load and integrity-check the current owner plan; require exact expected version.
  5. Apply all operations to a deep copy, validating targets and intermediate/final bounds. Any failure rolls back the entire batch.
  6. Increment plan version exactly once, set state to draft, and clear both approval fields.
  7. CAS-update the plan row and insert the mutation receipt in the same transaction.

Mutation receipt

The private mutation table binds owner, plan ID, key, canonical request digest, base/result versions, before/after plan integrity digests, canonical historical response, and server timestamp. Unique constraints cover owner-plan-key and owner-plan-result-version. Receipt drift fails closed.

Schema evolution

Fresh stores create schema v2 with root node identity, plan integrity digest, mutation receipts, checks, and PRAGMA user_version=2. Existing exact v1 stores migrate transactionally: verify the complete old schema and every record, generate one root node ID, preserve owner/plan/source/approval/version/timestamps, rebuild canonical authority, create mutation storage, and commit only when every row proves valid. Migration is idempotent and never repairs or deletes unprovable records.

HTTP semantics

  • 200 for a new mutation and exact replay.
  • Opaque private 404 for absent and foreign plans.
  • 409 for version, idempotency, or stored-integrity conflicts.
  • 422 for invalid operation, target, root restriction, cycle, no-op, position, or tree bound.
  • 413 for canonical request/result size overflow; private 500 for operational storage failure.
  • Every success, validation error, and failure includes Cache-Control: private, no-store and discloses no owner digest or hidden question.

Non-negotiable refusals

  • No legacy PlanTree, graph root ID, graph persistence, embedding, or decomposition adapter.
  • No event, investigation/session, provider, spend, launch, network, or background scheduling operation.
  • No stale-write merge, automatic rebase, partial batch, no-op success, or approval inheritance.
  • No caller-authored owner, node identity, approval principal, timestamp, integrity digest, or mutation result.

Acceptance

  1. Fresh handoff and v1 migration produce one stable opaque root ID and preserve all Cycle 24 authority.
  2. Add, update, move/reorder, and remove preserve unaffected IDs and exact sibling order.
  3. Root mutations, cycles, unknown targets, invalid positions, no-ops, malformed unions, and every limit+1 fail without state change.
  4. A batch advances version once; any failed operation leaves plan, approval, and receipt storage unchanged.
  5. Two concurrent same-version edits produce one commit and one conflict.
  6. Exact replay after later edits or reapproval returns the historical result and changes nothing current.
  7. Changed expected version, operation order, target, position, or text under one key conflicts.
  8. Editing approved state clears approval; old-version approval fails and new-version approval succeeds.
  9. Foreign and absent plan behavior is indistinguishable. Storage and all route responses remain private.
  10. Row/envelope/tree/digest/receipt tampering, duplicate node IDs, malformed types, unsafe paths, schema drift, and oversized records fail closed.
  11. Spies prove no forbidden collaborator is called by handoff, read, edit, replay, or approval.
  12. Focused tests, full multimedia backend/frontend tests, TypeScript, build, Ruff, HTML parse, diff hygiene, independent reviews, and HardenX pass.
