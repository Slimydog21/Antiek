Atomic unresolved-challenge escalation

When the challenger cannot resolve a living note, create one durable recursive research handoff whose graph state, lineage, and reserved child cannot separate on crash or retry.

Five values

  • Truth: the workstation never renders an escalated question whose graph node or asks-about edge failed to commit.
  • Identity: identical question text raised against different notes remains two distinct recursive threads.
  • Recovery: exact retries return the same question and reserved child and drain pending events.
  • Causality: graph discovery events precede the escalation event in one ordered outbox aggregate.
  • Restraint: reserving a child does not launch research, call another model, or authorize spend.

Identity contract

IdentityDerivation
Escalation operationSHA-256 over investigation, challenged note, normalized challenge text, sequence, and source document.
Question nodeExisting content identity scoped by investigation plus challenged-note identity, preventing cross-note collapse.
Reserved childDeterministic prefix of the escalation operation digest; no random second child on retry.
Outbox aggregateliving_note / challenged note ID, preserving graph-node, edge, then escalation order.

Atomic write

  1. The existing challenger resolver runs once for the call and returns unresolved. This cycle does not add a provider call.
  2. Under the global DuckDB writer and configured investigation-stream lock, check for an exact stored escalation operation.
  3. On replay, validate and return its immutable question/child identities without graph mutation.
  4. On first decision, promote a note-scoped question and its asks_about edge while graph helpers send their existing typed payloads to a caller-owned collector instead of JSONL.
  5. Enqueue graph payloads followed by question.escalated_to_research in the same transaction as node and edge rows.
  6. After commit, dispatch only this living-note aggregate. Failure remains pending for exact retry or startup recovery.

Graph event sink

  • insert_node and insert_edge accept an optional payload sink only when event emission is enabled.
  • Without a sink, current direct typed-event behavior is byte-for-byte unchanged.
  • With a sink, helpers construct the same validated payload but perform no file append; the transaction owner chooses the envelope and outbox operation identity.
  • Question promotion passes the sink through node and provenance-edge writes. Insight promotion and all existing callers remain source-compatible.

Authority boundary

No child investigation launch, provider routing, extra model call, embedding beyond existing question promotion, spend, cross-investigation retrieval, UI redesign, merge, or deployment. The watch-for-later launch and read-passage linkage are separate workflows and remain unchanged.

Acceptance

  • A pre-commit fault leaves no question row, asks-about edge, outbox row, graph event, or escalation event.
  • A post-commit/pre-delivery fault leaves node, edge, and ordered pending intents; exact retry returns the original child and delivers one copy of each event.
  • Two exact calls yield one question, one edge, one reserved child, and one physical three-event escalation bundle.
  • Same challenge text against two different notes yields distinct question and child identities.
  • distillation_for discovers the question and reserved child from the delivered authoritative events.
  • No investigation.start_requested event is emitted.
  • Focused and coupled tests, Ruff, compileall, frontend type/build, independent review, HardenX, and diff checks pass.

Harness hint

Attack custom event directories, graph-payload/direct-emission duplication, pre-commit rollback, post-commit delivery loss, same-operation byte substitution, identical text on different notes, old global question identity collisions, changed source document, outbox ordering, and accidental child launch.
