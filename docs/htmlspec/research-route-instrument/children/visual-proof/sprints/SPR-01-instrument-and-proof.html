SPR-01 — Research route instrument and proof

Owner: one isolated implementation lane · Wave: 1 · Status: ready

Goal and context

The production route choice and budget readout are embedded in StartResearch.tsx, so their critical states cannot be rendered independently in Storybook or held to direct LostPixel evidence. Extract the production markup and behavior into one controlled component without moving launch authority.

Give the component a specific field-instrument hierarchy: selected-lens registration rail, restrained policy engraving, readiness status, subordinate calibration ledger, and no decorative generated art.

Milestones

  1. Create ResearchRouteInstrument.tsx with typed preview, selection, busy, and selection callback props; keep question/fetch/launch state outside.
  2. Move roving-radio keyboard interaction and budget rendering intact, then apply the lens-rail visual hierarchy using existing tokens.
  3. Replace the inline block in StartResearch and prove the exact server-issued candidate still reaches launch.
  4. Add component tests for all four budget cells, disabled routes, click, arrows, Home, End, and focus.
  5. Add production-component Storybook stories for the four cells plus unavailable route, with narrow and dark visual variants and deterministic play assertions.
  6. Run focused tests, TypeScript, production build, Storybook build, visual inspection, heterogeneous review, and HardenX.

Rigor

  • Intellectual honesty: if Storybook cannot render the production component without a story-only behavioral fork, stop and report that boundary rather than snapshot a duplicate.
  • Fairness: assert the two partial-truth states independently—configured/unknown and unconfigured/known—because each serves a different operator need.
  • Rigor: make the meter queryable only when present and assert exact ratio clamping at 0, normal, and over-cap values; keyboard tests must verify focus as well as selection.
  • Diligence: inspect existing Storybook titles, dark backgrounds, LostPixel wait conventions, and StartResearch tests before creating fixtures.
  • Defensibility: the handoff must show the before/after responsibility boundary and prove that route proof construction, legacy fallback, and synthesis behavior did not move.

Dependencies and out of scope

Depends on: PR #2138 exact e8dbeffab924149dd2c4fae92f0af9a7ec703346. Out: API changes, new model/provider fields, recommendation logic, pricing, budget writes, route launch changes, Werner, cursor, atmosphere, generated images, modal/Krea, arcade, or synthesis.

Verification gates

  • Focused component + StartResearch + hook Vitest suites.
  • npm run typecheck, npm run build, and npm run build-storybook.
  • LostPixel/story screenshots at desktop, 375px narrow, and dark; manual inspection if an in-app browser target exists.
  • git diff --check; two different-lineage adversarial reviews; HardenX strict with zero REAL.

Handoff packet

Record files, exact test counts, story IDs/viewports, keyboard matrix, visual evidence paths, authority boundary, review findings and repairs, security verdict, engine gaps, and any unclaimed browser evidence.

Harness hint

Build inline; judge separately. Reject the work if it is only a rename/refactor or if the stories diverge from production.
