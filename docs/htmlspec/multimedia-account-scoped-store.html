Multimedia Account-Scoped Asset Store

TR executable sub-spec. Stacked on PR #929. The selected multimedia asset becomes owner-authoritative across planning, jobs, recovery, and paid execution authorization.

Five Values

  1. One ownership fact: every route uses the authenticated operator identity and every file is bound to the same owner digest.
  2. No silent claims: legacy global files are invisible until an operator explicitly assigns one migration owner.
  3. Crash honesty: atomic publication, directory fsync, and replayable migration make a restart observable and repairable without duplicate or lost assets.
  4. Private by construction: raw account identity never appears in paths or envelopes; account directories are 0700 and records are 0600.
  5. Authority follows data: reconciliation and execution authorization resolve the current revision through the same owner-scoped store, not a parallel global lookup.

Storage Contract

root/accounts/<sha256(normalized operator id)>/<asset id>.json

HTTP Ownership

All asset create, list, get, approve, steer, harden, jobs, and live-preparation routes require authenticated_multimedia_operator. Wrong-owner and missing records share opaque HTTP 404. Lists expose only the current owner partition.

The reconciliation runtime resolver takes both asset_id and authenticated operator_id. The execution-authorization router authenticates first and reads the asset under that owner before it can issue spend authority. A valid asset ID from another account is therefore not usable as a capability.

Legacy Migration

  1. Root-level v0 JSON remains inaccessible to all account reads.
  2. Migration runs only when ANTIEK_MULTIMEDIA_LEGACY_OWNER_ID is explicitly configured or the store method is invoked by an operator-controlled migration.
  3. Every legacy record is bounded, regular, unaliased, parseable, and filename-bound before publication.
  4. If the destination is absent, publish the owner envelope durably, then unlink the legacy file and fsync root.
  5. If a crash leaves both copies, replay verifies semantic equality, removes the legacy copy, and completes. A conflicting destination blocks migration.
  6. No first-login, first-read, route parameter, or browser claim may select the migration owner.

Acceptance and Rollout

  1. Focused store/routes/execution/reconciliation tests prove every threat row, restart, and concurrent append.
  2. Complete multimedia backend suite and frontend compatibility tests/build pass.
  3. Ruff, strict scoped mypy, HTML parse, diff check, hardenx zero real findings, and different-lineage critic pass.
  4. Production migration is NOT RUN until the operator identifies the exact legacy owner, backs up the root, records pre/post counts and hashes, and runs a two-account canary.
  5. Rollback restores the backed-up root and disables the migration owner variable; no reverse migration is automatic.

Non-Goals and Next Seam

No provider call, spend, refund, routing change, graph mutation, general authentication redesign, research-artifact migration, merge, or deploy. The next seam is to account-scope provider gateway configuration and execute a non-paid live recovery canary with audit evidence.
