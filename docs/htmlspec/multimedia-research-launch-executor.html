Cycle 29: Durable research launch executor

Status: executable specification. Base: Cycle 28 reviewed head c74d012c8df93442f011fec326be6e814b59ed7a.

Architecture verdict

Cycle 29 does not call the legacy cascade launch route. Its JSONL events are best-effort, graph promotion and task queues are process-local, and no production provider adapter currently proves the durable idempotency, hidden-retry, result-recovery, and authoritative reconciliation contract required by ResearchProviderGateway. Treating those mechanisms as execution authority would make crash recovery guess whether work or spend occurred.

The first truthful executor boundary is a durable, pull-driven operation manifest in the same research-spend SQLite authority as the Cycle 28 run. Materialization fixes every leaf operation before work may be claimed. Advancement processes at most one operation and may only dispatch through an exact eligible adapter; otherwise it records a stable blocked state without a provider call.

Five load-bearing values

  1. One authority domain: executable state, operation identity, spend holds, and recovery evidence live in the shared spend SQLite database.
  2. Effectively-once honesty: local transitions are transactional; external effects are at-least-once recovery attempts made effectively once only where a provider enforces the same immutable key and supports reconciliation.
  3. Intent before effect: the complete operation manifest commits before a lease, hold, event, task, graph mutation, network request, or provider call.
  4. Unknown is durable: uncertainty after the dispatch-possible marker is never retried blindly, released from local inference, or projected as failure/success.
  5. Projection is not authority: JSONL, DuckDB, UI state, asyncio registries, and future HTML output may project execution but cannot determine what runs next.

Spend-ledger schema v3

Add one research_launch_executions row per Cycle 28 run and one ordered research_launch_operations row per prepared-tree leaf. Both use explicit scalar columns, bounded canonical JSON, SHA-256 integrity digests, append-only command receipts, and foreign keys to research_spend_runs. Schema v2 migrates transactionally without rewriting existing runs, holds, attempts, commands, or audit events.

The execution binds owner, launch reservation, run, session, launch manifest, prepared integrity, provider, model, route/config/pricing/workload digests, operation count, request digest, and creation time. Its state is derived from operations: materialized, runnable, active, blocked, recovery_required, or terminal.

Each operation has a deterministic mlop_ identity over the launch reservation, manifest digest, stable leaf node ID, ordinal, and contract version. It binds the exact question and provider-visible payload digest, provider/model, deterministic gateway logical-operation identity, state, optional hold/result authority, and timestamps. Valid states are pending, blocked_provider_ineligible, claimed, dispatch_possible, unknown, settled, succeeded, and failed_terminal.

Atomic materialization

  1. Authenticate the owner and reopen the exact Cycle 28 launch reservation, prepared snapshot, and spend run.
  2. Require the run binding and ceiling to match the reservation. Unlike Cycle 28 readiness, an existing execution may legitimately have holds or spend; replay validates rather than requires pristine balances.
  3. Derive ordered leaves only from the immutable prepared tree. Reject missing/duplicate leaf node IDs, count drift, malformed questions, or any manifest/source mismatch.
  4. Build the complete bounded execution and operation records before entering the transaction.
  5. Under one spend-ledger BEGIN IMMEDIATE, replay the exact command or insert the execution plus every operation. Any failure rolls back the complete manifest.
  6. Classify the exact bound provider/model route through a server-owned adapter registry. Absence or ineligibility creates durable blocked operations; it never reroutes or calls a provider.

Materialization creates no asyncio task, scheduler entry, JSONL event, graph row, provider hold, network request, or provider call.

One-operation advancement

advance is synchronous and advances at most one lowest-ordinal nonterminal operation. A deterministic command key and short durable lease prevent routine concurrent claims. Leases coordinate workers but do not prove provider exactly-once behavior.

For an eligible route, the executor uses ResearchProviderGateway.dispatch_paid with the existing run binding, exact logical operation ID, server-owned projection, immutable operation payload, and exact adapter. The gateway remains the sole creator of provider holds and dispatch-possible markers. Settled responses persist only a bounded canonical result envelope or content-addressed artifact reference before the operation becomes succeeded.

On restart: expired claims without a hold return to pending; reserved holds without a dispatch marker are safely released by the existing ledger recovery rule; dispatch-possible or unknown holds reconcile and never resend blindly; settled work missing a recoverable result remains blocked; succeeded and failed-terminal operations never call the provider again.

Private API

  • POST /multimedia/investigations/{investigation_id}/launch-executions accepts only launch_reservation_id and a strict 16-128 character idempotency key. It returns 201 for first materialization and 200 for exact replay.
  • POST /multimedia/investigations/{investigation_id}/launch-execution/advance accepts a strict command key and advances no more than one operation.
  • GET /multimedia/investigations/{investigation_id}/launch-execution verifies and projects the durable execution without mutation.

The public receipt exposes execution state, operation totals by state, next ordinal, blocked/recovery reason, execution-started truth, and bounded spend totals. It omits owner digests, internal commands, leases, raw provider idempotency keys/evidence, private paths, and exceptions. Every response is private, no-store; missing and foreign resources are indistinguishable.

Acceptance evidence

  • Migration, rollback, exact replay, changed-intent conflict, owner isolation, concurrency, deterministic identity, strict canonical decoding, scalar tamper, tree/count drift, and bounded-record tests pass.
  • Materialization tests prove exactly one execution and the complete ordered leaf set commit together, with no task, event, graph, hold, network, or provider side effect.
  • Blocked-route tests prove missing, mismatched, hidden-retry, non-idempotent, or non-reconcilable adapters persist stable refusal and make zero provider calls.
  • Advancement tests cover at most one operation, exact command replay, concurrent claims, hold reservation, dispatch-possible crash, provider acceptance timeout, reconciliation, settlement, breach, bounded result persistence, and terminal replay.
  • Fresh-executor crash tests after every durable checkpoint prove no rematerialization, blind resend, double hold, double settlement, fabricated result, or authority widening.
  • JSONL disabled/failing, DuckDB unavailable, and all asyncio tasks destroyed do not alter executable state or spend truth.
  • Focused and full multimedia/cascade/spend/provider tests, Ruff, compileall, HTML parsing, frontend typecheck/build, HardenX strict, and heterogeneous adversarial review pass before publication.

Explicit exclusions

This cycle does not call CascadeSession.launch, create background tasks, fan out leaves concurrently, run Exa/Browserbase, use an adapter that cannot reconcile, append authoritative JSONL lifecycle events, promote into DuckDB, create graph edges, run synthesis, close the spend run, or claim exactly-once. If no eligible production adapter exists, the shipped product truth is an inspectable blocked execution manifest ready for a later adapter cycle.
