# DECISION 1: A (one registry, one identity across modes) with the three tightenings stated in the decision

## decision
Option A, tightened: ONE project registry (TC §1.5 over write_folders) in which a project is one identity across the three cockpit MODES (research, writing, books) and is never a per-product object. Registry row: home_product (birth product, immutable, values research|writing|books; drives the create page and default mode), presence products[] (subset of {research, writing, books}, never empty; drives homes, mode.cycle and transfer eligibility), kind (shape: project|book|interest, `reading` input alias), derived_from_project_id (single parent pointer) plus per-transfer typed events. WHOLE transfer = append to_product to products[] + one project.transferred event; the same id opens in the target mode with its own (owner, project, mothership) tree per T9. PARTIAL transfer = a new or named target registry project holding member REFERENCES only (member_kind node|investigation|document|deliverable|project) + project.transferred{transfer_id, from_project_id, to_project_id, to_product, scope, selection_digest}; never a content copy. Three tightenings that make this a precise hybrid rather than the advocates' Option A as written: (1) Speak and Autonomous are NOT presence values. Speak requests live in interview_projects and touch the registry only through member_kind speak_project links (ruling 4, TC §1.0:128); Speak → Writing is create-or-reuse of a registry project (home_product writing) plus that link and reuse of interview_projects.deliverable_id, and the UI never calls it the same object. Autonomous is a door over managed threads (ruling 10, lane B O-8): Research → Autonomous promotes selected threads in place with member_role managed inside their existing project; there is no autonomous product on the row and no autonomous create seed until LB-10 lands. (2) R33 (Books selects a Research project) follows ruling 11 exactly: the book project keeps its own id, the research project gains a member {member_kind: project, ref: book_project_id, role: context}, the book carries the link back, aggregates never recurse through project members (LB-17). The Research-side R28 pair (Research → Books, choose long-form assets) is the whole transfer: same id gains books plus a shelf (member_role shelf). Promote-in-place is kept only for "turn this book into a new project" (ruling 11), and TC §1.5:337, §2.1:1105, §2.9:1433 are amended to that scope. (3) Every §1.13 hold and settlement records mothership alongside thread_id and project_id, so per-product spend is an equality filter and an A→B split stays mechanical later.

# DECISION 2: Option A (agent = promoted thread, narrow explicit reach), with three precisions: (1) charter as a derived asset `agent:<thread_id>` for CAS revisions; (2) turns live on one session dialogue thread per (agent, project), never on the agent's own log, so solo and group dialogue share one memory rule; (3) membership rows carry `reach` CHECK-constrained to `attached_only` so the deferred per-project toggle is a value change, not a migration.

## decision
Option A, made precise. An agent is a promoted thread: its identity is its thread_id (kind research or dialogue), promoted by one typed event `agent.promoted{charter_asset_id, model_choice?}` on its own log; its charter is a derived asset `agent:<thread_id>` whose revisions carry compare-and-set through the existing §1.11 `revise` (so charter edits get the row-with-CAS discipline of §1.6/§1.14 without a new table); it belongs to projects by `write_folder_members` rows `{member_kind: investigation, member_role: agent | managed, reach: attached_only}` with owner equality (cross-owner → 403), the start-payload project_id being the home; and it reads only the charter, its own gated pack, what the operator explicitly attaches (`thread.context_attached{via: manual}`), what was merged into it under a reviewed digest (`thread.context_attached{via: merge, preview_digest, draft_digest}`, recursively through `merged_from` to a fixed depth), its own B0 children that are members of the calling project, and the calling project's session history. Conversational turns never live on the agent's own log: each project gets one long-lived session `dialogue` thread per (agent, project) with `participants: [agent_thread_id]` and `scope: {project_id}` (lane B's shape, unified with LB-27 groups, which are the same object with 2-4 participants). The hard-to-vary invariant: durable, cross-project agent state changes only through a reviewed, digest-bound commit (merge or explicit attach); conversational state is per project and never crosses a project boundary without one. Option B is rejected: it introduces an id class no provenance consumer recognises, reopens operator-confirmed C4 and both lanes' rev-9 vocabulary, costs a schema bump, a Caddy allowlist entry, a third ledger attribution column on an extension that does not yet exist on main, and its "read everything in the project" default degrades under `reuse_token_budget` into silent ranker selection, which is exactly what provenance replay must not depend on.

## rationale
1. The operator's words name the mechanism. "the combining of such threads manually will help the agent facing data landscape ... and also enriches the context of a growing subagent that can be called across projects" (REQUIREMENTS-2026-09-26.md, addendum para 1, verbatim). Enrichment is the manual combine; "called across projects" is membership plus a call. "the subagent builds context across various rounds of reading and deep research" (para 2) sits inside "if the project grows", so it is within-project accumulation, which the per-(agent, project) session carries in full. Nothing in R21, R25, R28 or R29 says an agent reads everything in a project; Option B's default is an inference layered on the text, and the operator's Q3 recommendation from lane A ("only what you explicitly attach, plus its own children and merges ... toggle later only if you want it", GROUNDING-LANE-A §5 Q3) was delegated to this decision, not ruled against.

2. Provenance. Every chunk already carries the thread as its provenance carrier: `PackChunk{chunk_id, document_id, ip_holder_id, source_investigation_id, sub_question}` (orchestration/session_evidence_pack.py:40-50@d61e5256d, VERIFIED). `MemoryItem.provenance` validates against `_REFERENCE_KEYS` containing `investigation_id` and `thread_id` and no agent id (substrate/memory/models.py:11-25@d61e5256d, VERIFIED). Under A, "what did this agent know when it said X in project P" replays P's session log plus the agent's `context_attached` receipts with their digests. Under B an `agent_id` would have to be threaded into memory provenance, ledger attribution (`reserve_dispatch` has 0 real hits on origin/main; the single grep match is `preserve_dispatch` in tests/test_provider_anthropic.py:150), `page.attribution.computed` and evidence_index, five consumers for one concept, the drift pattern the contract already documents for "companion" (§1.12 Q-A3).

3. Rights and reach. `RightsGatedPack` has 0 hits on origin/main (VERIFIED); `_owner_read_policy_tag` is server-derived and fails closed (app.py:6664-6690@d61e5256d, VERIFIED); `note_retrieval` scans every embedded node unless the caller supplies `restrict_node_ids` (substrate/context_pack/note_retrieval.py:60-82@d61e5256d, VERIFIED). Under a fixed `reuse_token_budget(role)` (knowledge_reuse.py:545), "everything in the project" cannot all reach the model; the assembler ranks and drops, and the operator cannot know which dropped item would have changed the answer. Explicit attach plus digest-bound merge is small, auditable, and replayable, and it is what O-6 requires (personal_reading and Speak items refs-only across projects; cross-project context "no" once a project is shared at G7). Option B's own risk list concedes paraphrase leakage scales with reach.

4. Storage doctrine cuts for A once the charter is a derived asset. Option B's best argument is §1.6 ("Tabs are navigation state, not provenance, so they are a row, not events") and §1.14 rev 8 (reading_state moved to a row because an append-only log "would stay last-writer-wins without a precondition of its own"). The mutable, concurrently edited agent field is the charter. `derived_assets` + `derived_asset_revisions` + `derived_asset_current_revisions` (schema.py:1246-1360@d61e5256d, VERIFIED) already give an owner-scoped entity with immutable revisions and a CAS pointer; `agent:<thread_id>` as a derived asset gets `409 revision_moved` semantics from §1.11 for free. Both advocates independently reached for this. Membership is already a row with an owner (`write_folder_members (folder_id, node_id) PRIMARY KEY`, folders.py:55-78@d61e5256d, VERIFIED), so the daemon's "which managed agents" question is an indexed read over `member_role: managed` rows, not a fold over every log; the daemon already scans the log every minute across all investigations today (orchestration/continuous/daemon.py:1-8@d61e5256d, VERIFIED), so A adds no scan class that does not exist.

5. Consistency with rulings and both lanes. C4 is operator-confirmed: "each AI agent is a tab inside it" (DECISIONS.md C4). §1.0: "agent tab | a right-pane view of exactly one thread | ... holds a thread_id, never content". Lane A: "an agent is a long-lived dialogue thread" (GROUNDING-LANE-A:22, :188, §5 Q4). Lane B: "agent | a promoted thread | [never] a store" (GROUNDING-LANE-B:718), "Lane B can meet R18 to R40 without a new store" (§1 Verdict). Two lanes converging independently is evidence the shape is hard to vary. Option B's observation that they diverge on where turns live is correct and is resolved here as a ruling (sessions), not by a table; B itself adopts the same session-thread shape for turns, so it dissolves nothing.

6. Reversibility and MVP cost. Under A, `agent_id == thread_id`. If a table is ever needed it is a projection keyed by that same id, and every event, ledger row, memory reference and tab node already resolves; A → B is additive. B → A is a table deletion and an id re-homing. A rides the already-planned LB-13 (membership as listing authority), LB-15 (merge target into agent), LB-24 and LB-26, needs one rev-9 text, and no Caddy or codegen work beyond ThreadSummary. B needs a new schema bump, `/agents*` allowlist, two lanes re-grounding LB-26/LB-28, a DESIGN-MODEL:18 revision, and re-signature of a rev 8 that is itself still "draft; unsigned" (THREAD-CONTRACT.md:23).

7. Single-writer. Turns and receipts are appends to logs; the only DuckDB writes are membership rows and charter revisions through `connect_write`. `account_memory_context` already exits the lock before dispatch (account_memory_context.py:1-10,57-75@d61e5256d, VERIFIED), and no agent path writes account memory (dark-by-default `INTERACTION_MEMORY_FLAG`, interaction_extractor.py:24-28; O-6). A first-class row touched per turn (last_seen, spent) would be new lock traffic on the platform's known stall.

8. Autonomous Research is served. O-11's envelope is one immutable, expiring, revocable consent per agent: `agent.autonomy_consented{max_cents ≤ cap, expires_at ≤ 24h}` / `agent.autonomy_revoked` on the agent's log, validated through `preflight_midnight_oil` (contracts.py:93-130@d61e5256d, VERIFIED, preflight-only today). Managed status is a membership row. Spend attribution is `(thread_id, project_id)` on every hold and settlement (§1.5, §1.13); the agent's total is a derived sum over its B0 branch children, shown as `null`/"—" when unavailable, never `0`. Lane A's revisit trigger ("scheduling or ownership a thread cannot hold") is not met by anything in R27/R28.

## decision
DECISION 3(a): OPTION A, in a precise hybrid. The draft shown before accepting a merge is a MODEL-WRITTEN merged analysis, generated once under an estimate and the §1.13 daily cap, over the free §1.10 rights-gated preview (which stays mandatory as step one and remains visible under the draft as "what the model was / was not shown"). DECISION 3(b): BOTH targets, with "Accept as new merged thread" (the §1.10 default) as the default and "Accept into agent…" as a second target that writes exactly one `thread.merged_in` append on the named target; no automatic fold into a common parent; "both in one press" is not offered (accept as new thread, then attach through ordinary context attach).

## rationale
1. The operator's words. "I want to be able to merge the sub agent analysis together. I want it to show a draft before me accepting the merge" (forensics/REQUIREMENTS-2026-09-26.md:34, verified). The object merged is "analysis"; the object shown is a "draft" of that merge. A side-by-side of member claims is the input to a merge, and the contract already names it: the §1.10 preview `items[]`/`conflicts[]`/`preview_digest` (THREAD-CONTRACT.md:470-475, verified). If the draft were the preview, the addendum would add nothing to §1.10 rev 3, which predates it. Option B's own definition ("synthesis only after acceptance") means the first merged analysis the operator sees is one he did not review before the merge landed; under signed §1.10 the commit triggers a run ("If a member's record fails, the answer is 503 and nothing dispatches", TC:487, verified), so B's synthesis is an unreviewed paid research run after lineage is written. That is the inverse of "show a draft before me accepting".

2. Option B's best evidence is real but does not settle the meaning. origin/main d61e5256d has a model-free "Draft merge" page (substrate/research_artifact/compose.py:1-11 imports only html/dataclasses/pathlib/build_body/export/paths; kicker "Draft merge review · no graph mutation · ANT-AHT"; "for review before any graph/write merge"; its conflicts are hash collisions — all verified). Its own copy calls it a pre-merge review of inputs, it has no accept step (GROUNDING-LANE-A:19), it reads build_body with no rights gate against TC:467, and the lane that wrote sprint 08 recorded it "was found insufficient" (sprints.py:872, verified; that verdict is the spec author's, not the operator's, so it carries weight only as evidence the cheap page did not satisfy the ask). Both independent groundings and the completeness critic read the addendum as A (GROUNDING-LANE-A §5 item 6 line 216; GROUNDING-LANE-B O-1 line 869; verified), and DECISIONS.md:55 delegated exactly this decision. The operator's revealed preference is paid synthesis under an estimate: rulings 13, 15 and 20 (DECISIONS.md:69-76, verified), the last being "one synthesising voice with per-sentence attribution".

3. Reproducibility. Under A the reviewed object IS the committed object: commit names `{draft_id, draft_digest}`, the server verifies the draft was generated against the current `preview_digest` (409 preview_stale / 409 draft_stale) and adopts its bytes with no dispatch. Under B "what he reviewed equals what commits" is true of the grouping only; the analysis he actually gets is produced after commit by a run whose output is not bound to anything he saw. B's argument that A adds links (preview → generation → edit → commit) is correct and is answered by binding: draft_digest = sha256(preview_digest, question, resolved model, draft text hash, parent_draft_id?), so every link is a hash the commit recomputes.

4. Provenance and the §1.11a trap: this is where B's technical critique is right and why the hybrid exists. TC §1.2 rev 8.5/8.6 (:195-200, verified) says any sourceless span is `generated` only if the connective validator's closed template set admits it, otherwise `unsupported`; §1.11a sets `mostly_generated` above 15% sourceless+unsupported words and excludes the revision from attribution (:746). Abstractive reconciliation prose over several threads would predictably trip this, and §1.11a's `research_context` admits at most 5 investigations (rev 8.7, verified), which would cap merge members at 5. So the draft must not be a §1.11a derived asset. The contract already has the right type: a "Synthesis over a thread is decided by the excerpt gate ... served when it clears, withheld otherwise ... A synthesis is never cite_only" (TC:193-194) and T7's `answer.provenance` with `cited_refs ⊆ retrieved_refs` (TC:686-689). The draft is an answer-shaped synthesis: `retrieved_refs` = the served pack items' pointers (chunk/edge/synthesis pins, each resolving to a document with `ip_holder_id`), `cited_refs` = the items the text actually cites, `claims[]` = the structured claim list each carrying item_ids → chunk_ids, prose = T7 presentation. The invariant "every claim cites chunks" is enforced at the claim list, exactly as thread outcomes already do (TC:1303), and G4 telemetry splits over `cited_refs`' documents, telemetry only (TC:691-694). Correction to advocate A: the operator's third provenance class ("supplemented with additional deep research that was merged into that knowledge base", OPERATOR-PROMPT-KIMI para 2) is about reformulations of a document and is already covered by §1.11a `research_context`; it does not require the thread-merge draft to be a §1.11a derivation.

5. Cost. B is free at draft time but not overall: it pays a full research run (retrieval + synthesis, §1.9 tier role plan, TC:482-490) after commit. A pays one synthesis-only dispatch over already-retrieved served items, bounded by input tokens and `max_tokens`, held through `reserve_dispatch`/`settle_dispatch` and refused with `402 refused_capped` before any dispatch (§1.11a Spend and Estimate patterns, TC:625-631, 755-760; ledger primitives on main budget_ledger.py per advocate A, not re-verified). A manual merge is a deliberate press rarer than the runs that made its members; abandoning after the free preview costs nothing.

6. Conflicts. Verified: the supersession detector is structural (same source_node_id + relation, different target, both valid) and its query has no investigation filter (middleware/supersession/db.py:9-13, 137-154@d61e5256d); the list route scopes by investigation only optionally (supersession_routes.py:~110). So B's grouping shows real cross-thread contradictions for free, but only structural ones; prose disagreements (numbers, dates, hedges) surface only in a written draft. The hybrid keeps both: detected contradictions side by side (never averaged, DESIGN-MODEL.md:174-176) and the draft naming tensions in prose with refs.

7. T7 and R21. T7 governs answers, and under the hybrid the draft is an answer, so the AI's presentation choice applies and is recorded; the grouping underneath is the honest evidence view (§2.10 counts). R21's "enriches the context of a growing subagent" is served by a reviewed synthesis in the agent's context (LB-26 item 3 "its accepted drafts", GROUNDING-LANE-B:526-531, verified) rather than by a refs-only recursion alone.

8. Reversibility and MVP risk. A as ruled is a strict superset of B: the grouping ships first with Accept disabled (O-1 sequencing), and if the operator later says the grouping alone is what he meant, the change is one line (commit accepts `draft: null` and the merged thread runs per signed §1.10) with no data migration. (b) New merged thread is the §1.10 default (step 4 mints it; pending pattern TC:485-487 protects members). "Accept into agent…" is R21's literal ask and both lanes recommend both (lane A §5 item 5; O-2). Under an adopted draft the into-agent path is one append `thread.merged_in {merge_id, merged_from[], accepted_draft: {draft_id, draft_digest}, preview_digest}` with the target's state unchanged (LB-24 acceptance, GROUNDING-LANE-B:485).
